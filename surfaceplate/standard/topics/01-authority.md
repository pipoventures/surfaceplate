# Topic 1 — Authority and the documentary record

Installed by Surfaceplate. Do not edit this file in an adopting repository.

*Where does truth live, and what happens when two documents disagree?*

## One canonical authority per question

Every material question — what a calculation means, what a contract is, how a screen is composed,
what the approval route is — must have exactly one canonical answer, in one named location.

Resolve authority **before** changing behaviour. Do not rely on a remembered document, a nearby
file, a code comment, or a previous conversation when a canonical authority exists.

Where the repository publishes an authority map (commonly
`documentation/governance/inventory/source_of_truth_matrix.yaml`, or an authority hierarchy in the
repository's own agent instruction file), that map is the routing authority. Consult it first.

Where no authority map exists, the repository's own agent instruction file must state the ordered
authority hierarchy explicitly. An unstated hierarchy is a control gap; report it.

**"The repository's own agent instruction file"** means whichever file this repository has told
your agent to read — `AGENTS.md`, `CLAUDE.md`, `.github/copilot-instructions.md`, or another —
never one vendor's file named as though it were universal.

## Generated and extracted content is never authority

Content generated, extracted, or converted from a canonical source is for search and navigation
only. It is never an independent authority, and neither is an agent's summary of it.

Never hand-edit generated content. Regenerate it with the documented command.

Where a generated view must stay in step with its source, the repository should provide a
`--check` mode that fails when the view is stale, and that check should run in CI or pre-commit.

## Contradictions are blocking defects

Stale, missing, contradictory, retired, or superseded authority is a **blocking defect**, not an
inconvenience to work around.

Stop. Resolve the conflict, or record the required human decision. Do not:

- pick whichever document is most convenient;
- implement both interpretations;
- proceed on the assumption that the newer file wins;
- silently prefer the code over the documentation, or the reverse.

## Supersession — how to write a correction

The rule above governs what to do when you **encounter** superseded authority. This one governs
what to do when you **create** it, and it is the more commonly missed of the two.

**Rewrite the passage that states the superseded value. Do not leave it standing under a
correction.** When a value, a date, a count, a status, or a claim changes, edit the sentence that
asserts it. Adding a banner at the top, a footnote, or a later paragraph that gives the right
answer while the original text still asserts the old one is not a fix — it is two answers in one
document, and which one a reader gets depends on where they happen to land.

**A correction whose validity depends on reading order is not a correction.** A grep, a search
hit, a link from another document, or a model reading one section returns the old value exactly as
readily as a complete read returns the new one — and nothing about a partial read announces that
it was partial. The reader who is misled is the one who had no way to know they should keep
reading.

**Where the old wording earns its keep, keep it — marked explicitly historical.** A record of what
was believed, and when, is often worth more than the correction itself, particularly where the
delay or the error is the thing a later reader needs to understand. Mark it as history in the text
itself. Do not leave it as unmarked prose that the correction merely precedes.

**This does not contradict the append-only rule below, because the two govern different objects.**
A decision or change **log** records events: what was decided, by whom, when. You never rewrite an
event, because the event happened. A document that states a **current fact** is not a log, and
correcting it in place is the whole of its job. Where one record does both — a decision record
with a status line, an activity entry with a state — the decision text is append-only and the
status is corrected in place.

## What governs when this standard and something else disagree

An adopting repository may already carry its own standing instructions — a house style, a parent
organisation's engineering policy, a personal working method the repository's owner already
follows elsewhere. Installing this standard does not erase them, and until now nothing here said
which one wins when they conflict on the same question.

**The default, absent a declaration: this standard governs the surfaces it actually specifies** —
the engineering method, the evidence and completion discipline, the security baseline, the gates
and controls it defines — **and the adopter's own instructions govern everything this standard does
not reach.** A contradiction on a surface this standard *does* specify is the blocking defect
described above, resolved the same way: stop, and record the decision.

**An adopter may declare a different order explicitly, in the application profile, rather than
leave it to the default.** This is a decision the repository's owner makes about their own
repository — never a condition this standard imposes, and never something one adopter's choice can
bind another adopter to. Nothing outside this standard's own published documents is ever a
condition of adopting it, and nothing outside them may be cited to an adopter as part of it: a
canon declaration binds the repository that declares it, and only that repository.

## Decision and change records

Material decisions and exceptions require a durable record. Decision and change logs are
**append-only**: add a new entry, never rewrite or delete history.

Use `.standards/templates/decision-record.md`.

A decision record must identify the decision, the alternatives considered, the rationale, the
accountable human, the date, and the affected authorities. A decision that is not written down did
not happen.

## Retired locations

When a documentation root is retired, it stops being authority immediately. Do not cite it, do not
update it, and do not restore content from it without a decision record.

## For agents — Authority

Installed by Surfaceplate. Do not edit this file in an adopting repository.

- Resolve authority **before** acting. Consult the repository's declared authority map or its own
  agent instruction file first — never a remembered document, a nearby file, or a vendor-specific
  filename named as though it were universal.
- Generated or extracted content, and an agent's summary of it, is **never** authority. Regenerate
  it with the documented command; never hand-edit it.
- Stale, missing, contradictory, retired, or superseded authority is a **blocking defect**. Stop.
  Resolve the conflict or record the required human decision — never pick the newer file by
  default, never implement both readings, never silently prefer code over documentation or the
  reverse.
- **Writing a correction:** rewrite the passage that states the superseded value, in place. A
  banner, footnote, or later paragraph beside unedited old text is two answers in one document. A
  log of events (decisions, changes) is append-only and never rewritten; a statement of a current
  fact is corrected in place.
- **Where this standard and the repository's own instructions disagree:** this standard governs the
  surfaces it specifies; the repository's own instructions govern the rest, unless the repository
  has declared a different order in its application profile — and such a declaration binds only
  that repository, never anyone adopting this standard elsewhere.
- Decision and change records are append-only; use the templated form; an undocumented decision did
  not happen. A retired documentation root stops being authority immediately.
