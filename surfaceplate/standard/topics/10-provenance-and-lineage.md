# Topic 10 — Provenance and lineage

Installed by Surfaceplate. Do not edit this file in an adopting repository.

*Where did this output come from?*

## Separate the kinds of knowledge

AI-generated reasoning, deterministic processing, quantitative or model outputs, and human
judgement must remain distinguishable **in code and in records** — not merged into an undifferentiated
"result".

Where an application carries values whose origin matters, classify each value. The following
taxonomy is the standard's shared vocabulary. Applications may narrow it; they must not blur it:

| Kind | Meaning |
|---|---|
| `sourced-fact` | Directly attributable to a cited external source |
| `external-forecast-or-reference` | Third-party forecast or reference series |
| `sourced-analytical-view` | Analytical view derived from cited sources |
| `human-assumption` | Explicit human assumption |
| `expert-judgement` | Recorded expert judgement |
| `ai-proposal-or-hypothesis` | Proposed by an AI system, not yet accepted by a human |
| `model-calibrated-output` | Output of a governed, versioned model or method |
| `deterministic-derived-value` | Deterministically computed from other recorded values |
| `user-override` | Deliberate manual adjustment — see below |
| `propagated-output` | Derived by propagating an accepted change |
| `open-uncertainty` | Explicitly unresolved |

**`ai-proposal-or-hypothesis` must never silently become `model-calibrated-output` or
`sourced-fact`.** Promotion between kinds is a human decision and must be recorded.

AI may assist discovery, drafting, and reasoning. AI must not own a material numerical path.
Material numerical outputs belong to governed, versioned, testable methods.

## Lineage

A material result must be traceable to: the application, the input version, the method and method
version, the configuration, the code revision, the execution or run identifier, a timestamp, and
the output.

For a completed AI-assisted run, additionally record a non-empty AI provider, model identifier, and
prompt or template version. A run that failed, was blocked, or was cancelled may legitimately have
no outputs — do not invent placeholder outputs or hashes to fill a schema.

## Overrides

Never hide a manual adjustment inside UI code or calculation code.

Every deliberate deviation from the default automated path is an override record, carrying:
classification; affected method, run, and scope; before and after values; rationale; evidence
reference; calculation and output impact; materiality; approval requirement and status; owner;
approver; approval evidence reference and timestamp where approval is asserted; review or expiry
trigger; closure condition; and rollback approach.

Rules:

- High, material, or output-affecting overrides **must** route through approval.
- `pending` and `rejected` overrides may be recorded but must never become effective.
- An `approved` override requires a named approver, an approval-specific evidence reference, and an
  approval timestamp.
- Evaluate expiry and review triggers before applying an override, and on each relevant run.

Use `.standards/templates/override-record.yaml`.

## Truthful labelling of non-live capability

Where a capability is preloaded, simulated, illustrative, precomputed, or otherwise not live, label
it **at the point of use**. A single global disclaimer is not sufficient.

Never imply live data ingestion, live AI, live calibration, completed validation, or production
readiness that does not exist.

Do not describe something as "validated" because automated checks passed. Checks passing means
checks passed.

## Assurance states stay distinct

Keep these four separate at all times, in code and in records:

- **lifecycle status** — is this catalogued and current?
- **validation status** — what validation evidence exists?
- **approval status** — what human authorisation exists?
- **run status** — what happened in one execution?

`lifecycle_status: active` means catalogued. It never means executable, validated, or approved.

Unqualified `passed` and `approved` require unconditional evidence. Where limitations or conditions
remain, use the conditional forms and record the conditions. Record limitations and findings rather
than smoothing them away.
