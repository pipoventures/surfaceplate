# Topic 8 — Confidentiality and data boundaries

Installed by Surfaceplate. Do not edit this file in an adopting repository.

*What must never leave, and what must never enter?*

## Never commit

- secrets, credentials, access tokens, connection strings, private certificates or keys;
- real client or customer data;
- private URLs, internal hostnames, or tenant identifiers that are not already public;
- uncontrolled sensitive fixtures.

Use the repository's approved environment or platform secret store. If a secret has been committed,
treat it as disclosed: stop, report it, and route rotation as an incident. Removing it in a later
commit does not undo the disclosure.

## Fixtures and examples

Use synthetic, anonymised, or approved reference data. Record the derivation or provenance of a
controlled fixture.

Never place real customer data, credentials, or private URLs in examples, tests, documentation,
screenshots, or release archives.

## AI confidentiality

Before sending content to an AI provider, classify it and apply the repository's approved handling
rule for that classification.

Do not send secrets, credentials, private certificates, client or customer data, restricted model
inputs, or unredacted sensitive prompts unless the provider, tenant, retention, and contractual
route are explicitly approved for that classification.

For material AI-assisted runs, record the provider, model identifier, prompt or template version,
relevant configuration identity, and the data-handling decision.

Do not persist raw sensitive prompts or outputs in general logs. Redact secrets and sensitive
values from traces, exceptions, audit events, fixtures, screenshots, and test output. Retention and
deletion rules apply to both provider-side and repository-side AI artefacts.

## Archives and release artefacts

Before sharing an archive: run the approved secret scan, verify it contains only intended files,
verify paths are relative and portable, and verify it matches its checksum manifest.

A checksum proves integrity **after** the digest is trusted. It proves neither authenticity nor the
absence of malicious content.

**Declare the scanner, and wire it so it can fail.** `baseline_controls.secret_hygiene.scanner` in
the application profile names the tool and the file(s) that run it. A conformance-checker finding
verifies the wiring exists and that the step invoking the scanner can actually fail the job —
because a scan whose result is discarded, by `continue-on-error` or by `|| true` on the command,
reports without gating. That is an observed failure mode, not a hypothetical one.

The scanner is the adopting repository's choice. This standard ships none, recommends none, and
reads no file looking for credentials: passing the wiring check means a scanner is wired somewhere
it can fail, and says nothing whatever about whether secrets are present.

## Human decisions — classification and AI provider approval

Data classification and AI provider approval are human decisions. Record them. An agent may
recommend; it may not classify data on its own authority or approve a provider for a classification
it has not been told is approved.

## For agents — Confidentiality and data boundaries

Installed by Surfaceplate. Do not edit this file in an adopting repository.

- Never commit secrets, credentials, tokens, private certificates, real client data, or private
  URLs. If one is committed, treat it as disclosed — stop, report, route rotation as an incident.
  Removal afterward does not undo it.
- Use synthetic or anonymised fixtures only; never real customer data, credentials, or private URLs
  in examples, tests, docs, screenshots, or release archives.
- Classify content before sending it to an AI provider, and apply the repository's approved
  handling rule for that classification. Never send secrets, client data, or unredacted sensitive
  prompts without an explicitly approved provider/tenant/retention route. Redact sensitive values
  from logs, traces, and test output.
- Before sharing an archive: run the approved secret scan, verify its contents, verify its checksum.
  A checksum proves integrity, never authenticity or the absence of malicious content.
- Data classification and AI provider approval are human decisions — recommend, never decide them
  yourself.
