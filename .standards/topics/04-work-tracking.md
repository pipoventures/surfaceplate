# Topic 4 — Work tracking

Installed by Surfaceplate. Do not edit this file in an adopting repository.

*What is owed here, and what state is it in?*

## Start from a registered activity

Work begins by naming a registered activity, for example: *"Let's work on activity WS7-13."*

Before editing:

1. verify the activity ID exists in the repository's activity or development register;
2. read its scope, dependencies, owner, reviewer, status, and definition of done;
3. stop if the activity is missing, or if its status is `done` without an explicit continuation
   request;
4. stop if a hard dependency is not satisfied.

**Do not begin unregistered work.** Register the activity first, or ask the accountable human to
make the planning decision. An agent may draft a proposed activity entry; a human authorises it.

Where a repository has no register yet, the standard requires one before `standard` or `full`
conformance is claimed. At `essential` conformance a lightweight register is still required, but it
may be a single Markdown file.

## What a register entry must carry, and how much of it depends on the level

A register is machine-readable where practical. At `standard` or `full` conformance, each activity
should record at minimum:

| Field | Purpose |
|---|---|
| `activity_id` | Stable identifier cited by every commit, test, and document change |
| `title` | What the activity delivers |
| `owner_role` | Accountable human role |
| `reviewer_role` | Who must review before it can be considered complete |
| `status` | From a controlled vocabulary — see below |
| `depends_on` | Other activity IDs |
| `dependency_type` | `hard`, `review`, or `external` |
| `decision_materiality` | Whether the activity can change material outputs |
| `judgement_level` | How much human judgement the activity requires |
| `definition_of_done` | Objectively checkable completion condition |
| `evidence_required` | What evidence must exist before it can be marked done |

**At `essential`, the register is satisfied by less: a two-value status (`open` / `done`) and a
bare dependency pointer.** `owner_role` and `reviewer_role` are declared once, at the
repository level, rather than repeated per entry — for a solo adopter both fields are otherwise
constant across every row, and a constant column carries no information. This is graded the same
way this framework's controls already are (Topic 12): a floor at every level, more expected as the
level rises, never the reverse. It corrects a defect this standard's own reference installation
demonstrated: every row of its register once read `owner_role: maintainer, reviewer_role:
maintainer`, and nothing about that repeated the requirement rather than restated a fact already
true of the whole repository.

## Status vocabulary

Keep execution status distinct from validation status and approval status. At `standard` or `full`,
a useful minimum:

`planned`, `in_progress`, `blocked`, `waiting_for_review`, `external_dependency`, `deferred`, `done`.

Derive status from dependencies rather than asserting it:

- unsatisfied **hard** dependency → `blocked`;
- unsatisfied **review** dependency → `waiting_for_review`;
- unsatisfied **external** dependency → `external_dependency`.

`done` requires the definition of done to be met **and** the required evidence to exist. Never mark
human approval, independent validation, risk acceptance, or release readiness as complete on an
agent's authority.

## Keep the register current in the same change

At each meaningful progress point, update the register **in the same commit** as the
implementation. Status, notes, evidence references, dependencies, and any human-review requirement
travel with the diff. A register updated afterwards is a reconstruction, not a record.

Where the repository generates views from the register (dashboards, dependency boards), regenerate
them in the same change and run their `--check` mode. A stale generated view fails the build.

## Traceability

Every implementation, test, and documentation change must be attributable to an activity ID. Cite
it in the work packet, the commit message, and the completion report.

Never invent an activity ID, a requirement ID, or a rule ID. If the identifier you need does not
exist, that is a planning gap to raise, not a value to fabricate.

## For agents — Work tracking

Installed by Surfaceplate. Do not edit this file in an adopting repository.

- Do not begin unregistered work. Name a registered activity first, read its scope, dependencies,
  owner, reviewer, status, and definition of done, and stop if it is missing, already `done`, or a
  hard dependency is unmet. An agent may draft a proposed entry; only a human authorises it.
- At `essential`, a two-value status and a bare dependency pointer satisfy the register — do not
  demand the full `standard`/`full` field set of a repository that has not adopted at that level.
- Derive status from dependencies (`blocked` / `waiting_for_review` / `external_dependency`), never
  assert it directly. `done` requires the definition of done **and** the evidence to exist — never
  mark human approval, validation, risk acceptance, or release readiness done on your own authority.
- Update the register **in the same commit** as the implementation, never afterwards. Regenerate any
  derived view in the same change and run its `--check` mode.
- Cite the activity ID in the work packet, the commit message, and the completion report. Never
  invent an identifier that does not exist — raise the planning gap instead.
