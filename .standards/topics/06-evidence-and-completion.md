# Topic 6 — Evidence and completion

Installed by Surfaceplate. Do not edit this file in an adopting repository.

*What counts as done, and how do I report it honestly?*

## Evidence-first completion

A completion report must separate **what was verified** from **what is assumed or recommended**.
It must contain:

- the actual changed-file list, and for material changes the actual diff or patch content;
- the exact commands run, quoted, not paraphrased;
- test output, including warnings and skipped tests;
- runtime behaviour where applicable;
- known failures, environmental limitations, and evidence gaps;
- any human review, approval, or validation still required.

A narrative summary is not evidence. Report each check as `PASS`, `FAIL - CODE`,
`FAIL - ENVIRONMENT/DEPENDENCY`, or `NOT RUN`. Do not describe a run as successful because a
wrapper returned exit code zero when the output shows failures.

Use these labels when the distinction matters:

- `FACT` — directly verified in this repository's code, configuration, tests, or current output.
- `INFERENCE` — reasoned, not directly observed or enforced.
- `RECOMMENDATION` — proposed treatment.
- `EVIDENCE GAP` — requested fact not established by available evidence.

## Prohibited

- Weakening, deleting, skipping, or rewriting tests to obtain a passing result.
- Regenerating golden or reference outputs to absorb an unexplained change. An unexpected
  deterministic output change is an audit trigger, not a fixture problem.
- Fabricating approval, independent validation, risk acceptance, production readiness, or an
  external platform control.
- Silently expanding scope beyond the work packet.
- Reporting a changed-file list in place of an actual diff for material or audit-triggered work.

## Audit triggers

Escalate for actual-diff review when a change affects:

material numerical or model outputs; material AI outputs or reasoning; public schemas or contracts;
provenance or run lineage; security boundaries; dependencies; approval state; model or tool
classification; AI provider or prompt behaviour; or a broad refactor.

Increase review depth when a change is novel, hard to test, irreversible, externally reported, or
difficult to reproduce.

For these triggers, the evidence must contain the actual diff or patch content — a changed-file
list alone is insufficient.

## The minimum review packet, and how much it scales with risk

For every bounded change, retain:

- work packet and application profile reference;
- actual diff or changed-file list for low-risk routing;
- actual diff or patch content for material or audit-triggered changes;
- tests/checks and the exact commands;
- runtime or integration evidence where relevant;
- known failures, warnings, and environmental limitations;
- dependency/security impact;
- documentation/contract impact;
- reviewer disposition and unresolved questions.

| Level | Typical change | Minimum evidence |
|---|---|---|
| 0 | Documentation or formatting only | Self-check and ordinary review |
| 1 | Low-risk implementation with no expected output impact | Focused automated checks and diff review |
| 2 | Output-affecting code, data, schema, or workflow | Regression/contract tests, output self-review, change record, reviewer |
| 3 | Methodology, material model or numerical output, material AI output/reasoning, security boundary, or externally relied-on output | Level 2 plus independent challenge, sensitivity/benchmark evidence where relevant, explicit approval |

The receiving application defines its own materiality thresholds. These levels are a routing aid,
not approval authority.

## Failure discipline

Report failed checks and warnings honestly. Distinguish code failures from environment/dependency
failures, and do not call a process successful solely because a wrapper returned exit code zero
when the test output shows failures.

**A check that did not run is not a check that passed.** This is a distinct failure from the one
above, and it is harder to see: the first produces a wrong result, this one produces *no* result
while every artefact around it — the workflow file, the commit, the step name — looks correct.

The requirement, for any repository adopting this standard:

1. **A pipeline must not silently skip its checks.** Most CI systems stop at the first failing step
   by default and record the rest as *skipped*. A summary that reports only an overall status
   cannot distinguish `skipped` from `passed`. On GitHub Actions the guard is
   `if: ${{ !cancelled() }}` on each check step — **not** `continue-on-error`, which marks a real
   failure as tolerated and turns the job green, trading a hidden non-result for a hidden failure.
2. **Something must confirm each check produced a result.** A guard that is never verified is an
   assumption. Read the per-step conclusions, not the overall tick.
3. **A green run is evidence only for the checks that actually executed.** When citing CI as
   evidence, cite the step, not the job.

Why this is stated rather than assumed: a check was once added to this framework's own repository,
wired into CI, committed, and had **never executed** — an earlier step failed, the step's
conclusion read `skipped`, and nothing distinguished that from passing. It was found by comparing
two instruments against each other, not by reading output more carefully; the output was internally
consistent and wrong. It is recorded as `F13`.

**This standard cannot check any of the above for you.** It inspects an adopting repository's
declared profile and its git history, not the semantics of its pipelines. This is an obligation,
not an enforced control, and it is stated here so the difference is visible rather than assumed.

## For agents — Evidence and completion

- Separate what was **verified** from what is **assumed or recommended**. Report the actual diff
  for material work, the exact commands quoted, test output including warnings and skips, known
  failures and evidence gaps, and what human review is still required. A narrative summary is not
  evidence. Report each check `PASS` / `FAIL - CODE` / `FAIL - ENVIRONMENT/DEPENDENCY` / `NOT RUN`.
- Never weaken, delete, skip, or rewrite a test to obtain a passing result; never regenerate a
  golden output to absorb an unexplained change; never fabricate approval, validation, risk
  acceptance, or an external control; never expand scope silently; never report a file list in
  place of a diff for audit-triggered work.
- Escalate for actual-diff review on: material numerical/model/AI outputs; public schemas or
  contracts; provenance or run lineage; security boundaries; dependencies; approval state; AI
  provider/prompt behaviour; a broad refactor. Deepen review when novel, hard to test, irreversible,
  externally reported, or hard to reproduce.
- Cite the step, not the job, when using CI as evidence — a step that did not run is not a check
  that passed, and a green overall status can hide one that was silently skipped.
