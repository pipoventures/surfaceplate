# Topic 11 — Concurrency and shared-repository discipline

Installed by Surfaceplate. Do not edit this file in an adopting repository.

*How do several agents share one repository?*

Several agents, or several sessions of one agent, can now work on the same repository at the same
time. The failures that produces are not the ones people plan for: they are quiet, they look like
success at the moment they happen, and the evidence that would reveal them is usually the thing
that was overwritten.

## One writer per working tree

**Only one agent or process may hold write access to a working tree at a time.**

**Independence of task is not independence of write path.** Two agents given genuinely
non-overlapping work can still destroy each other's output, because what collides is not the task
but the mechanism: one writes to disk directly while another holds the same file in an editor
buffer and saves later, and the later save wins with no conflict and no error. Assess the write
path, not the brief.

## Handoff is explicit and complete

Before a second agent begins work on a tree:

- the previous session is closed;
- its editor tabs and buffers are closed;
- its work is committed.

**A loaded buffer is a pending write, regardless of what any status reports.** `git status` is
clean because nothing has been saved yet, not because nothing is outstanding.

## Parallelism needs separate checkouts, and they are not free

Concurrent work needs separate checkouts — Git worktrees — never a shared one. The constraint is
one writer per tree, not one agent overall.

Cost the remedy honestly before choosing it, and do not assume a worktree isolates more than it
does:

- **Worktrees isolate the index, not the hooks.** Hooks live in the shared common Git directory,
  so one set of hooks serves every worktree. A hook added on one branch can block an unrelated
  branch in a tree that does not contain the change that added it.
- **Whether a hook runs at all is separately revocable, and leaves no diff.** `core.hooksPath`
  **replaces** the default hooks directory rather than adding to it, and it can be set at global or
  system scope, where it applies to every repository on the machine and lives outside all of them.
  So a repository-local hook can stop running with no error and nothing in version control
  recording it. The gate reads as present because the file is still on disk, while Git never calls
  it.
- **Divergent histories cost more than a second checkout.** Separate branches, merge conflicts, and
  identifiers allocated twice in two trees that could not see each other.
- **A generated, tracked artefact reconciled against its own source is a further cost, and it is
  not a merge conflict.** A conflict announces itself and refuses to merge. A generated manifest,
  register, or index resolved badly merges cleanly, and the check that reads it then passes against
  the wrong set. That is a silent false green, and it is the failure this whole document exists
  for.

**Never infer what runs from a clean diff, from an installer being present in the repository, or
from a hook file existing.** Read it: the resolved hooks path at every scope
(`git config --show-origin --get-all core.hooksPath`) and the common Git directory
(`git rev-parse --git-common-dir`).

## Serialising is a legitimate alternative

Doing one thing at a time in one tree addresses the same hazard by forgoing concurrency rather than
isolating it. It is stricter than this rule requires, and where a repository mandates it that is
permissible and inherits correctly.

Neither remedy is the default. Choose on the real cost of each.

## Re-read shared state at the moment you act on it

A session that only **reads** shared state is not the hazard. A session that **plans or instructs**
from a stale read is.

Re-read the shared state — the register, the branch list, the findings, the open work — at the
moment you issue a plan or an instruction that depends on it, and state which state you read. Two
sessions planning against one repository is frequently legitimate; serialising them usually costs
more than the hazard does. What is not legitimate is briefing from a read taken before the other
session acted.

## Missing code is a stop condition, not a task

If a required symbol, file, or interface does not exist, **stop and report**. Do not write it.

Writing the missing piece hides an upstream failure — most often that another agent's work has not
landed, or has been overwritten — and it may cross an escalation boundary the task never
contemplated. Authorisation for routine work does not extend to whatever that work turns out to
need.

## For agents — Concurrency

- **One writer per working tree.** Only one agent or process may hold write access at a time.
  Independence of *task* is not independence of *write path* — assess how the write actually
  happens, not whether the work looks separate.
- **Handoff is explicit and complete.** Before starting work on a tree, confirm the previous
  session is closed, its editor buffers are closed, and its work is committed. A clean
  `git status` does not mean nothing is pending — a loaded buffer is a pending write regardless.
- **Concurrent work uses separate checkouts (worktrees), never a shared tree.** But a worktree
  isolates the index, not the hooks, and `core.hooksPath` can be redirected at global or system
  scope with no diff to show for it. Read the resolved hooks path
  (`git config --show-origin --get-all core.hooksPath`) and the common Git directory
  (`git rev-parse --git-common-dir`) — never infer what runs from a clean diff or a file's mere
  presence.
- **A generated, tracked artefact reconciled against its own source is not a merge conflict.** It
  merges cleanly, and the check that reads it then passes against the wrong set. Treat this as a
  live risk in any worktree touching a generated register, manifest, or index.
- **Serialising work in one tree is a legitimate alternative to worktrees**, not a lesser one —
  choose on the real cost of each.
- **Re-read shared state at the moment you brief or instruct from it.** Reading alone is not the
  hazard; briefing or planning from a stale read is.
- **Missing code is a stop condition, not a task.** If a required symbol, file, or interface does
  not exist, stop and report — do not write it.
