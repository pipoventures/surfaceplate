# Decision Record

- Decision ID: DR-34
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — the result of exercising it against a second
  repository other than itself, and the corrections that result required.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change.
- Risk level: 2 — it changes what the installer tells every adopter who declines the hook, and it
  records the second piece of evidence this framework has about a repository other than itself.
- Related work item: `ACT-024`. `RELEASE_PLAN.md` item 5, phase 1.

## Decision

**The framework was exercised against Plutos, not Plyego, and passed cleanly at `essential`. Two
defects are fixed here — one the probe exposed directly, one this packet's own verification cycle
found. Plutos is not adopted, and nothing was written to it.**

1. Plyego is mid-migration to Google Cloud. Installing anything into it now, or even probing it
   with a throwaway clone that could be mistaken for touching the real thing, is the wrong moment
   regardless of risk level — `org/RELEASE_PLAN.md` item 5 still names both adopters; this record
   is why Plutos went first, not a decision to drop Plyego.
2. `install_standard.py`'s `--no-hooks` install path told every adopter to activate and rely on a
   pre-commit hook that was never written — unreachable from surfaceplate's own self-check, which
   never installs with `--no-hooks` on itself. Fixed: the "Next steps" text now names
   `history_audit` and `review` when the hook was declined, and only describes the hook when one
   was actually installed.
3. **Found while re-verifying, not while probing Plutos, and worth being precise about the
   difference**: `tests/test_install_and_check.py` failed intermittently (~1 run in 40) during this
   packet's own six-suite check, with no connection to Plutos at all. Root cause: an abbreviated
   commit SHA that happens to be all digits parses as a YAML integer unless quoted, failing the
   gate-exception schema's `string` type — and `governance/exceptions/GX-0001.yaml`'s own comment
   already documented catching this once, a lesson that had never reached the adopter-facing
   template, this test, or the checker's own error message. `F33`. Fixed in all three places.
4. **Plutos's adoption is a separate decision**, exactly as `DR-28` established for Plyego: gate and
   control decisions are the maintainer's to make with the per-gate cost in front of him, not an
   agent's to infer from a probe. This record contains observations about Plutos and no changes to
   it.

## Context and alternatives

### Why Plutos, not Plyego, this time

`org/RELEASE_PLAN.md` item 5 has named both Plyego and Plutos since `DR-7` closed the fabricated-
adopter finding. The maintainer raised the substitution directly: Plyego's Google Cloud migration
is real, ongoing operational risk, and this is deliberately the wrong moment to install anything
into it — migration or no migration. Plutos was surveyed read-only before any plan was written and
found to be a materially easier candidate on its own facts, not chosen merely because it was
available: Python-only (442 files, no UI — `builds_user_interface: false` is a real answer, not a
guess), `requirements.txt` generated by `pip-compile --generate-hashes`, CI that actually runs
`pytest tests/` in a named step, and secret-scanning CI already blocking. None of that changes what
item 5 requires — two real adopters — only the order they are approached in.

### What the gate was for, and what it returned

Against a `git clone --local` of Plutos (history and objects shared read-only, never a checkout of
the real working tree — confirmed clean before and after: `git status --short` on the real
repository shows nothing, both times):

```
Advisory (2) - not a failure:
  - dependency_lock: verified against requirements.txt
  - the pre-commit hook was declined at install: nothing checks staged changes before they are
    committed, and this repository relies on history_audit and review. A gate that claims
    local_hook enforcement anyway is still a finding (SP038).

PASS - all conformance checks satisfied.
```

At `essential`, using `--no-hooks` (this machine's global `core.hooksPath` made the default install
refuse outright, correctly — `F27`'s remedy working exactly as designed on the first repository it
has ever met that has one). The probe fixture's `secret_hygiene` scanner declaration named Plutos's
real `gitleaks` step; `check_secret_hygiene` inspected it and raised nothing, meaning the step
genuinely blocks rather than merely existing. The `work_registration` gate's precondition artefact
named Plutos's own `activity/register.md`, which is real and present, and the full-history audit
ran against Plutos's actual commits (a genuine, unshallowed local clone) and found nothing to flag
before the fixture's `effective_from`.

**Plyego's first honest probe needed two fixes before it passed (`F25`, `F26`). This one passed on
the first honest attempt.** That difference is itself evidence: Plyego is a materially larger,
older, more heterogeneous repository, and the placeholder-quoting trap `F25` found needed a
rationale sentence no probe fixture happened to write until Plyego's did. Plutos's clean pass does
not mean the checker is now proven against every edge case — it means this specific repository's
shape did not happen to hit one, the same honest reading `DR-28`'s own limitations section gives
Plyego's result.

### The first defect found, and why it was unreachable from here

`install_standard.py`'s "Next steps" block printed unconditionally: *"Run: git update-index
--chmod=+x .githooks/pre-commit"* and *"Commit the result. The installed pre-commit hook checks
staged changes"* — regardless of whether `--no-hooks` had been passed. Surfaceplate's own
self-install has run with hooks enabled every time since `ACT-001`; nothing in this repository's own
history has ever exercised the declined-hook branch of its own next-steps messaging for real. A
real adopter using `--no-hooks` — the exact route `F27` built for someone who wants to keep their
own hook system — would have been told to activate a file that does not exist, and that a hook is
checking their staged changes when nothing is.

Fixed by making the block conditional on `no_hooks`, and stating what actually enforces the
repository when the hook is declined (`history_audit` and `review`, matching the wording the
installer's own hook-conflict message already uses). A positive control was added alongside the
fix, not only a negative one: the default (hooks-enabled) path is now also asserted to still name
the hook it installed, so the conditional's two branches are both proven, not just the one that was
wrong.

### The second defect, found by re-verifying this packet, not by probing Plutos (`F33`)

Running the standard six-suite verification cycle before commit — the same cycle every packet this
session has used — `tests/test_install_and_check.py` failed once, then passed on immediate re-run.
Reproduced deliberately rather than dismissed as a one-off: 40 iterations of a faithful reproduction
of the failing section reproduced the same failure on the sixth attempt, with full diagnostic output
captured. Root cause, read directly from the captured failure: `SP043`, *"commits/0: 3516272 is not
of type 'string'"* — the test's own probe wrote an abbreviated commit SHA unquoted into a gate
exception, and that specific SHA happened to be all digits, no `a`–`f`. YAML's plain-scalar grammar
parses an all-digit token as an integer unless it is quoted; the gate-exception schema correctly
requires a string, so the record correctly failed. Roughly one seven-character hex prefix in
forty-three is entirely digits (`(10/16)^7 ≈ 2.3%`), which matches the observed frequency well
enough to treat as the whole explanation, not a coincidence layered on something else.

**This exact trap had already been found once, in this repository's own real gate exceptions,
and the lesson never left the file it was found in.** `governance/exceptions/GX-0001.yaml`'s own
comment reads: *"an abbreviated SHA that happens to be all digits - 7547482 here - parses as an
integer and the schema rejects it."* Someone hit this, understood it, quoted the value, and wrote
the explanation down — but `templates/gate-exception.yaml` (what every future adopter actually
copies) still showed the commit list unquoted, `tests/test_install_and_check.py` wrote its own probe
unquoted, and `check_conformance.py`'s error message gave no reader who had not already found that
one comment any reason to suspect YAML's grammar rather than their own SHA being wrong.

Fixed in three places, deliberately, because fixing only the test would have left the same trap
waiting for the next real adopter: the template now shows the commit entry quoted, with the reason
stated inline; `validated_exception` now detects a `commits` entry that failed validation
specifically because it parsed as an integer and appends a targeted sentence explaining why; the
test now quotes its own probe SHA. Confirmed with 10 further full-suite runs, all clean — proportionate
confirmation for a fix whose correctness does not depend on chance (a quoted value is a string every
time, not most of the time), rather than an attempt to statistically exhaust a probabilistic bug.

### What the probe found about Plutos, recorded as observation only

These are findings **about Plutos**, and Plutos's own register is where they belong if adoption
proceeds. Recorded here because they are the evidence for what adoption would cost, mirroring
`DR-28`'s own table for Plyego rather than starting a different format:

| Observation | Detail |
|---|---|
| `essential` passes cleanly today | No fix was needed to reach it, unlike Plyego. |
| `dependency_lock` has a real candidate | `requirements.txt`, `pip-compile --generate-hashes` — genuinely hash-locked, a stronger starting position than a bare pin. |
| `secret_hygiene` has a real, verified candidate | `.github/workflows/secret-scan.yml`, `gitleaks`; `check_secret_hygiene` inspected it directly and found nothing wrong. |
| `contract_tests`/`deterministic_tests` have a real candidate | `.github/workflows/ci.yml`'s `"Full suite (per-test timeout converts any hang into a failure)"` step actually runs `pytest tests/` — unlike Plyego, where 547 test files existed and nothing in CI ran them. |
| `work_registration` has a real, unconventional candidate | Plutos already runs its own activity register (`activity/register.md` plus one `activity/ACT-<n>.md` file per activity, 75 activities) — a different shape from this framework's own single-file convention, but a real precondition artefact this probe's fixture pointed the gate at successfully. |
| `authority_map` has a partial candidate, not a satisfying one | `docs/README.md` states prose precedence — `venture/` is *"the active Investing OS source of truth"* — for its five subdirectories. `core/PREREQUISITE_GATES.md:234` requires *"a machine-readable map of which document governs which path"*; prose is a real starting point, not the artefact the gate names. |
| No `CHANGELOG.md` at the repository root | Same gap Plyego had. |
| `standard`'s other two required gates have no artefact yet | `decision_before_implementation`, `change_record_before_completion` — neither surveyed further than their absence; a real cost assessment for `standard` needs the maintainer's own read of what artefact would satisfy each, not a guess from this probe. |

**The activity-register question, stated rather than resolved.** Plutos's own 75-activity register
long predates any contact with surfaceplate and was not built to satisfy `work_registration`. Two
honest paths exist, and this record does not choose between them: point the gate at Plutos's
existing register as-is (what the probe fixture did, and it worked), or treat surfaceplate's own
register conventions as a second, parallel system. The first costs nothing extra and the probe
already demonstrates it is mechanically sufficient; the second would duplicate governance Plutos
already has for no evident reason. Recorded as the maintainer's call to make when adoption is
actually decided, not settled here by a probe fixture's convenient choice.

### Alternatives rejected

- **Probe Plyego anyway, on the reasoning that a throwaway clone never touches the real repository.**
  Rejected by the maintainer's own framing: the migration makes this the wrong moment regardless of
  what a clone can and cannot affect — the caution is about timing and attention, not only about
  write access.
- **Adopt Plutos for real in this packet, since the probe passed cleanly.** Rejected: `DR-28`'s
  principle does not weaken because a probe went well. A clean pass tells the maintainer adoption
  would be *cheap*; it does not make the gate and control decisions for him.
- **Widen the fix to also correct the hook-conflict message's own wording**, noticed while reading
  the surrounding code. Not touched: it already correctly names `--no-hooks` as the third route
  (`F27`'s remedy) and nothing about it was found wrong — scope stayed to the defect the probe
  actually surfaced.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none. `schemas/gate-exception.schema.yaml` is unchanged — it was always
  correct; `F33`'s fixes are the template, the error message, and the test, not the contract.
- **Security/data:** none. Nothing was written to Plutos; the probe ran in a local clone whose git
  objects were shared read-only with the real repository.
- **Operations/release:** every future `--no-hooks` install now describes the enforcement it
  actually has, not the one it declined. Every future adopter's gate exception template quotes its
  commit entries, and a digit-only commit that is not quoted now gets a targeted explanation rather
  than a bare type error.
- **`org/RELEASE_PLAN.md` item 5** records the substitution and the probe result in the same change.

## Evidence

- The probe transcript above, reproduced in full rather than summarised.
- `git status --short` on the real Plutos repository, run before the clone and again after every
  step of the probe: clean both times.
- `tests/test_install_and_check.py`: two new checks for the `--no-hooks` fix, one per direction of
  the conditional. Two more for `F33` — an unquoted all-digit commit is caught by `SP043` with the
  new targeted hint present in the output. 174 checks total, `PASS`.
- `F33`'s reproduction: 40 iterations of a faithful standalone reproduction, failing on the sixth
  with full diagnostics captured (the exact `SP043` message, the exception file's raw content, the
  full commit log). 10 further full-suite runs after the fix, all clean.

  `PASS`.

## Limitations and follow-up

- **One repository, again, is not a sample.** Plutos shares an author and machine with this
  repository and with Plyego, the same limitation `DR-28` states plainly for its own probe.
- **`essential` is the only level demonstrated.** `standard` and `full` were assessed only by
  reading what each would require, not by constructing and running a fixture at that level — the
  same discipline `DR-28` used, and for the same reason: a fixture at a level nobody has decided to
  target would be inventing a decision, not testing one.
- **The activity-register question is named, not answered.** See above.
- **Plutos's own findings belong in Plutos's own register**, and putting them there is part of an
  adoption that has not happened.
- **Real adoption is a separate, later activity.** Either the maintainer runs
  `surfaceplate adopt --target /home/mps2210/github/plutos` directly, or does it together with an
  agent relaying the wizard's actual prompts and answering them live — never inferred from this
  probe.
