- Date: 2026-09-09
- Application: Surfaceplate (the framework itself) — how this repository tests a framework that is
  repository- and language-agnostic.
- Decision owner: Mario Pipo (maintainer), who rejected the agent's proposal to publish first and
  argued that an agnostic framework should not need many repositories to test. Drafted by the agent
  under `ACT-089`; confirmed by merging.
- Status: accepted — implemented by `ACT-089`.
- Risk level: 1 — a new test suite and the documents that count them. No behaviour changes.
- Related work item: `ACT-089`; answers the coverage boundary named in `F132`, `F142`, `F143`,
  `F144`, `F145` and in `audit/PATHWAY_SWEEP_REPORT_2026-09-09.md`.

## Decision

**Name the properties of a repository over which this framework's behaviour varies, and cover
them.** `tests/test_repository_shapes.py` declares the axes, exercises each in both directions, and
asserts one invariant the other suites do not: **that what the tool proposes is capable of
implementing the control it is proposed for.**

## Context and alternatives

In one afternoon the maintainer, driving the wizard by hand, found five defects — `F132`, `F142`,
`F143`, `F144`, `F145`, four of them `high` — that some fifty thousand automated checks could not
reach, including a 208-case matrix walking every reachable decision.

**The agent's first reading was that this called for more repositories, and it was wrong.** The
maintainer's objection is the correct one and is recorded here because it changed the work:
Surfaceplate is agnostic by design, so its behaviour cannot depend on *which* repository it meets —
only on a small set of **properties** that repository has. Enumerate the properties and a handful of
synthetic fixtures covers every repository there will ever be. The proof is that every one of the
five findings is now reproduced from a fixture of a few files. The real repositories were needed to
**find** them and are not needed to **prevent** them.

**The sharper diagnosis, once that was seen.** The matrix already had a shape axis —
`SHAPES = ("bare", "rich", "mixed")` — chosen for **how much discovery finds** (nothing, everything,
awkward), not for **which properties change behaviour**. `bare` has no dependency manifest and
`F132` still got through: the fixture had the property, and no oracle asked the question.

**Rejected: extending the matrix's own shape axis.** It would have churned a byte-compared 208-case
report, lengthened a run already at 170 seconds, and mixed two different questions. The matrix asks
*"is every reachable decision handled?"*; this asks *"does behaviour vary correctly with the
repository?"*. Separate questions deserve separate oracles and separate reports.

**Rejected: publishing first and treating the walkthrough as the standing programme.** The agent
recommended it on the grounds that external validation is the real bottleneck. That remains true and
is not urgent: nothing external depends on a date, and a reviewer's time is better spent on judgement
than on defects this repository could have found itself.

**A cross-product is not attempted, and the omission is a decision.** Ten binary axes is 1,024
combinations, most differing in nothing. Each axis is exercised against a baseline and against the
combinations where two axes genuinely interact — the same judgement `adopt_matrix.py` makes in
taking 208 cases rather than every path.

## The half that pays

Fixtures alone would not have caught `F144`. The `rich` shape *has* CI steps; what was missing was an
oracle asking **whether what was written is true** rather than whether it matched expectation. The
matrix asserts the profile matches the script and cannot notice that the script named
`Check out mnemosyne (shared generator lives there)` as the implementation of `deterministic_tests`.

`implausible(control, reference)` asks that question, conservatively — it reports only what is
clearly wrong, for the reason `F145` records about the checker's own caution: a false alarm trains a
reader to skim the real one.

## Impact

- A fifteenth suite, wired into `standard-self-check.yml` and into its "did every check actually
  run" assertion. `CLAUDE.md`'s count corrected in the same change, which is that line's own habit.
- No product code changes. The suite passes against `HEAD` and is a guard, not a fix.
- 41 checks across 3 axes, examining 27 proposals over 9 shapes × 3 levels.

## Evidence

**Both directions, on the findings it exists for.**

- Remove `F144`'s proposal filter and the invariant fails **eight times**, including on
  `manifest_and_lock/tests` — a repository that *has* proper test steps and still had the checkout
  proposed. That is the shape the matrix already covers and still missed.
- Remove `F142`'s withhold and the dependencies axis fails twice, naming the offered list.
- Restored, the suite passes at 41 checks.

## Limitations and follow-up

**Three axes are declared, not ten.** `dependencies`, `ci_steps` and `installed` are covered;
history depth, occupied paths, hooks configuration, agent channels, register fit and scanner wiring
are named in the finding record and not yet fixtured here. This is the first instalment and says so
rather than implying the axis list is complete.

**`installed` is declared and not yet exercised** in this suite: `F141`'s direction check lives in
`test_install_and_check.py`, where the installer subprocess already runs. Listing it here without
covering it would be the false green this file exists to prevent, so the axis table says what it
does and the assertions do not pretend otherwise.

**This does not cover what the interface DISPLAYS.** `F143` — a field required and never shown —
is invisible to any suite that answers the plan directly, and its regression test lives in
`tests/test_adopt_tui.py` driving real keypresses. A third kind of coverage, named here so it is not
mistaken for something this file provides.

## Approval

The maintainer rejected the agent's recommendation and gave the reasoning this record implements.
Drafted by the agent and confirmed by merging.
