# Decision Record

- Decision ID: DR-36
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — `surfaceplate/adopt/`, the interaction layer of
  the `adopt` wizard.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change (`ACT-027`).
- Risk level: 3 — it replaces a runtime dependency fixed by an earlier decision record, changes
  every screen an adopter sees, and rewrites the mechanism by which this project proves its own
  binding rule.
- Related work item: `ACT-027`. Phase 2 of `DR-35`.

## Decision

**`questionary` is replaced by `textual`, the `adopt` wizard's interaction layer is rebuilt to
deliver the interface that was actually approved, and the binding rule — "it asks, the human
answers, the tool writes" — becomes provable rather than merely asserted.**

1. **The dependency is replaced outright, on a recorded human decision.**
   `.github/skills/dependency-update/SKILL.md:49-54` makes "removing or replacing a dependency that
   is part of a documented methodology or control" a mandatory stop, and `questionary` was fixed by
   `DR-32`. The maintainer was asked and chose replacement over keeping a fallback, on the grounds
   that a second, rarely-exercised interface is the same failure shape `F34`/`DR-34` had just found
   in the `--no-hooks` branch. `InteractivePrompt` and `prompting.py` are deleted.
2. **The interaction layer is rebuilt on Textual, mockup-faithful.** `DR-35` established that
   `DR-32`'s "linear, not a dashboard" reasoning was wrong against the design that was actually
   approved. A three-method `Prompt` cannot express a screen showing three gates with chip rows and
   conditional follow-ups, so the collaborator gets coarser — `Interview.collect`, a section at a
   time — while keeping the shape that made the old one useful.
3. **The binding rule is proven three ways, because one was never enough.** See below; this is the
   part of the packet that outlives the interface.

## Context and alternatives

### The seam: `wizard.run` stays synchronous

`App.run()` is Textual's blocking entry point and creates its own event loop — checked against the
real API, not assumed (`inspect.iscoroutinefunction(App.run)` is `False`). So the entire async
surface of this package is one worker inside `tui/app.py`; `cli.py`, `wizard.py` and every test
remain ordinary synchronous code, and this repository still contains no `asyncio` outside the TUI
and its tests.

The app owns screen *sequencing* only, because the sequence is data-dependent: `level` cannot be
planned until `mode` and `builds_user_interface` are known, `gates` not until `level` is. It owns
nothing else. Assembly, verification and writing stay in `wizard.py`, and the only disk the app
touches is the draft file, through a callback.

**Verification runs twice, deliberately.** The app is handed a `preview(state)` closure so the
review screen can show a `WriteRefused` as a message rather than a traceback; `wizard.run` then
re-assembles, re-renders and re-verifies before writing. Both passes are pure, so the second is
free — and it means a defect in the interface cannot put an unverified profile on disk, however
convincing the screen looked.

### The binding rule was never actually proven, and this repository already knew

Worth stating plainly because it reframes what this packet is for. `tests/test_adopt.py:222-226`
has said, since `ACT-022`: *"a scripted test could not have caught that, because `ScriptedPrompt`
only objects to a call it wasn't given an answer for, never to a value written without any call."*
That is exactly how `F32` got in — rationale text invented for seven controls and gates, with every
scripted test passing — and it had to be caught by a Gemini review instead.

The replacement is three layers, and each closes what the others cannot:

| Layer | Proves | Blind to |
|---|---|---|
| `tests/test_provenance.py` — sentinel walk | No string reaches a profile that no answer supplied | Whether the plan was fully answered |
| `ScriptedInterview` — keyed, two-sided | The plan was fully answered and nothing extra was | Whether the screens ask the plan |
| `tests/test_adopt_tui.py` — screen↔plan join | Each screen renders exactly its plan's field ids | What the values mean |

The sentinel walk is the headline. `sections.py` is now pure `build_*(answers) -> fragment`
functions, so a whole profile can be assembled from answers in which every free-text field carries a
unique token; anything in the result without one was contributed by the tool. The legitimate
contributions are enumerated in an allow-list — schema version, `"Blocking."`, `"required"`, gate
and control ids, the statuses the schema allows, every value a dropdown can take, and the three
values read from `INSTALL.json` or today's date. **That allow-list is the honest, reviewable answer
to "what does this wizard write on its own?"**, it is 48 entries, and widening it is a code-review
event. Its own negative control injects a plausible fabricated rationale and confirms the walk
objects.

### Three things only building it revealed

Recorded because each would have shipped as a defect, and because they are the kind of thing a
design document cannot anticipate:

- **Textual's `Input` starts with its whole value selected and re-selects on focus**, so the first
  keystroke replaces a preset value. Every example answer `example_answers.py` offers is a preset
  value, so this would have silently undone `DR-35`'s recognition-over-recall feature the moment
  anyone typed. Fixed with `select_on_focus=False`; collapsing the selection in `on_mount` was tried
  first and does not hold. `test_example_defaults_survive_being_typed_into` is the regression.
- **The mockup's `[g] jump to section` cannot work as drawn.** A focused text field consumes
  printable characters, so a bare letter binding is typed into a rationale instead of jumping. It is
  `Ctrl+G`, and the hint line says so rather than promising a key that does nothing — the `F35`
  lesson that a named route must be a route the reader can actually take.
- **A control the level requires must not be an unticked tick box.** The first cut rendered all nine
  controls as checkboxes with the floor pre-ticked; unticking one would have produced a profile the
  checker rejects. Floor controls are now stated, not offered — the same treatment a level-mandatory
  gate's status already gets.

### Dependency governance

`.github/skills/dependency-update/SKILL.md` applied in full:

| Step | Result |
|---|---|
| Justification | `DR-35`'s recorded decision; the approved mockup is not renderable otherwise |
| Provenance / health | `textual` 8.2.8, author Will McGugan, the author of `rich`; not a typosquat |
| Licence | MIT |
| Exact pin | `adopt = ["textual==8.2.8"]`; the CI install line updated by hand |
| Vulnerability scan | `pip-audit` against both sets: **before** (`questionary==2.1.1`) *"No known vulnerabilities found"*; **after** (`textual==8.2.8`) *"No known vulnerabilities found"* |
| Full suite | All eight suites run, not a focused subset |
| Output impact | None — the wizard's written profile is byte-identical in shape; `render.py` is untouched |

**The cost, stated rather than buried.** `textual` brings seven transitive packages (`rich`,
`markdown-it-py`, `mdit-py-plugins`, `mdurl`, `linkify-it-py`, `platformdirs`, `pygments`) where
`questionary` brought two. `DR-32` rejected `ruamel.yaml` as "more supply-chain surface than the
problem justifies", and that posture is what is being traded here — knowingly, for an interface that
a real adopter could not use as it stood. It lands only on someone who installs the `[adopt]` extra,
never on an adopting repository's CI, and keeping it out of `[project.dependencies]` is what makes
that true.

### Alternatives rejected

- **A Textual-backed `Prompt`, keeping the three-method protocol.** Cheapest by far, and it would
  have preserved every existing test unchanged — but one call, one answer cannot render a screen
  showing three gates at once, so it would have delivered a prettier version of the thing that was
  already wrong.
- **Keep `questionary` as a non-TTY fallback.** Rejected by the maintainer: two interfaces means two
  test matrices and one that nobody exercises. `adopt` now refuses without a TTY, naming a route.
- **Split Phase 2 into two packets.** Rejected: a half-migrated wizard does not run at all, so the
  split would have produced a long-lived branch rather than two releases.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none. `application-profile.schema.yaml` is untouched, and `render.py` — the
  code that writes the file — is unchanged by this packet.
- **Security/dependencies:** one optional runtime dependency replaced; net +6 transitive packages on
  the `adopt` extra only. Scanned clean before and after.
- **Operations/release:** `surfaceplate adopt` now requires a real terminal and says so when it does
  not have one. Everything an adopting repository's CI runs is unaffected.
- **`org/RELEASE_PLAN.md` item 2** is updated: the wizard it describes now has the interface that was
  approved for it.

## Evidence

- All eight suites pass: `validate_contracts` (167), `test_install_and_check` (179), `test_adopt`
  (59, up from 53), `test_provenance` (5, new), `test_adopt_tui` (23, new), `check_identifiers`
  (131), `check_code_registers` (10), `check_vendored_current` (57 files).
- **The negative control on the dependency removal:** `questionary` and `prompt_toolkit` were
  uninstalled from the environment, `import questionary` confirmed to raise `ModuleNotFoundError`,
  and all three adopt suites re-run green. The removal is real, not just unreferenced.
- **The join, sized:** the gate catalogue screen renders 138 field ids and its plan declares the
  same 138; the controls screen 31; every other screen exact.
- **Highlight is not selection**, driven by real keystrokes: three `Down` presses on the level
  screen followed by quitting records no level.
- **The gate catalogue behaves as the mockup drew it:** 19 gate blocks on screen at once, a
  free-choice gate holding no status until a chip is pressed, follow-ups hidden until a status calls
  for them, only the chosen chip lit, and a counter that moves 8 → 9 of 19 when one is answered.
- `pip-audit` output for both dependency sets, quoted above.
- The no-TTY refusal, run and read back: it names the command to run in a real terminal and states
  that any saved draft is untouched, exiting 2.

## Limitations and follow-up

- **No real, unscripted session has been driven by a human yet.** The Pilot proves the mechanism;
  it cannot establish pacing or approachability, which is what the complaint that started `DR-35`
  was actually about. That remains the maintainer's to judge, and it is the point of the packet.
- **The mockup's `[⇧Tab] back` is Textual's ordinary focus traversal**, not a bespoke
  edit-a-previous-answer affordance. Within a section that is genuinely free movement; between
  sections, going back is resuming a draft rather than stepping backwards, which the mockup never
  drew and this packet did not invent.
- **`--web` mode** remains `DR-32`'s disclosed deferral, and a `deferred` path through
  `control_decisions` remains unbuilt.
- **A Phase 1 draft cannot be resumed by Phase 2.** The two store different shapes, so drafts carry
  a `format` and a foreign one is not offered; the run overwrites it on its first completed section
  rather than deleting anything.
