## Decision

Surfaceplate is a git-native tool distributed as a Python package. It holds no state outside the
adopting repository.

Committed to:

- **Distribution by pip; a `surfaceplate` command-line tool.** `DR-10` already decided the pinning
  mechanics this depends on (a wheel-file digest, disambiguated by `adoption.distribution_channel`,
  with the checker committed to staying vendored per-adopter). This record is what makes that
  decision non-hypothetical: pip distribution is now committed scope, not a scenario `DR-10`
  reasoned about in the abstract.
- **Agent-neutral: `AGENTS.md` as the canonical emitted instruction file, with per-agent emitters.**
  `DR-11` already decided the integrity mechanics this depends on (the `generated_files` structure,
  generalised from the existing `conformance_block_digest`/`SP008` precedent). Same relationship:
  this record commits to the artefact `DR-11`'s mechanism was built to protect.
- **Task skills in the open Agent Skills format they already use.** Today's
  `standard/.github/skills/*/SKILL.md` files already use a `name`/`description` frontmatter shape
  structurally compatible with that wider convention — confirmed by reading all seven — but this
  repository has never cited it as such: `README.md:49` and `RECONCILIATION.md:7-8` attribute the
  instruction-file shape to Copilot specifically, and `INSTALL.md:12` describes the skills only by
  what they are for, with zero citation to any named external skills specification anywhere in the
  tree (exhaustively grepped). This decision closes that citation gap going forward. It does not
  claim the shape has changed; it claims what it should be understood as, and cited as, from here.
- **Enforcement, where wanted, via the adopter's own GitHub primitives** — required status checks on
  their organisation ruleset, their CI, their infrastructure, their support burden. This is not a
  new mechanism; it is naming what `org/ROLLOUT_RUNBOOK.md:34-40`'s enforcement ladder already
  describes as rung 3: *"Required by ruleset | The organisation requires the check on every
  in-scope repository. | Only an organisation owner"* can apply it or bypass it. Surfaceplate
  publishes `org/ruleset-standards-conformance.json` for an adopter's organisation owner to apply;
  it does not, and will not, apply, host, or operate that ruleset on anyone's behalf.
- **Apache 2.0, publicly readable.** Already true today — `LICENSE` is the unmodified Apache 2.0
  text. The copyright-holder line remains unfilled boilerplate (`LICENSE:189`); filling it and
  adding a contributor licence agreement are release-plan work, not this record's concern — this
  record commits to the licence choice and public readability remaining unchanged.

## Permanently out of scope

Stated here because it is the point of the record: naming these once, permanently, is what prevents
the rejected delivery model below reappearing later as a series of individually reasonable
features. Each reason given is architectural, operational-capacity, or governance-independence —
never commercial.

1. **No hosting, servers, user accounts, authentication, or database. Ever.** The reasons are given
   under "Rejected: a hosted multi-tenant service" below, since this item and that alternative are
   the same question asked two ways.
2. **No storage of adopter data of any kind.** The entire verification mechanism reads git history
   *locally*, on the adopter's own machine or CI runner. Storing any adopter data anywhere else
   would be a new attack surface and a new trust obligation the architecture was never designed to
   secure, taken on for no corresponding gain in what gets verified.
3. **No claim of prevention. Detection only.** The local hook is bypassable and always will be.
   `README.md:112-113` already states the honest ceiling: *"This is weaker than prevention and
   stronger than most things called enforcement. Describe it in those terms and not in stronger
   ones."* `core/PREREQUISITE_GATES.md:29-30` gives one concrete, general reason prevention is
   architecturally unclaimable as things stand: *"`git commit --no-verify` defeats any client-side
   hook; github.com does not offer pre-receive hooks."* Closing that gap server-side would require
   the kind of always-on infrastructure item 1 already forecloses. Detection — the local hook and
   the history audit reading a permanent commit graph, the top two rows of `:45-51`'s four-layer
   table — is the ceiling this architecture can honestly claim, and no higher.
4. **No certification or validation service.** `org/decisions/README.md:16-18` already states why,
   as this repository's own standing convention, repeated in every decision record's Approval
   block: *"Independent validator: not assignable. Independence requires someone not involved in
   the work. No such person exists for this repository at present, and self-approval would not be
   independence."* A certification service the framework's own author operated would be exactly
   that defect, wearing a product's clothes — a governance-independence reason, not an architectural
   or capacity one.
5. **No vulnerability or dependency scanning.** `README.md:119-120` already commits this framework
   to stack neutrality: *"It does not prescribe a language, framework, database, deployment
   platform, or product architecture."* A scanner is necessarily stack-aware. Building one would
   mean abandoning the neutrality the rest of the design depends on, for a problem domain already
   served by tools built for exactly that purpose.
6. **Not a code reviewer. It checks governance, not code.** `core/CONTROL_PRINCIPLES.md:11`
   (principle 9) requires "a durable decision record and actual-diff review" as a human control —
   something the framework mandates must happen, not something it performs. `actual_diff_review` is
   one of the three baseline controls every conformance level requires
   (`core/CONFORMANCE_LEVELS.md:18-20`). Surfaceplate verifies that a repository has declared this
   control and carries the artefacts the declaration implies; it does not read a diff and judge it.
7. **Git only. The history audit reads a commit graph; this is a permanent boundary.**
   `core/PREREQUISITE_GATES.md:67-69` names the actual mechanism: `git log --since=<effective_from>
   -- <gated_activity.paths>`, asking of each returned commit whether its precondition artefacts
   existed in that commit's tree. This is not a preference for git over another version-control
   system; it is the literal operation the entire prerequisite-gate audit is built from. A
   repository on a different VCS would need a different, unbuilt mechanism, and every existing gate
   in `core/PREREQUISITE_GATES.md`'s catalogue would need re-deriving against it. Stating the
   boundary now is better than letting an adopter discover it by trying.

## Context and alternatives

**Rejected: a hosted multi-tenant service as the delivery mechanism.** The principal alternative,
and the one this whole record exists to permanently close off. Three reasons, none commercial:

- **Governance and operational-duty capacity.** `org/decisions/README.md:16-18` already
  establishes, and every decision record in this directory's Approval block already states, that
  this project has one maintainer and no independent validator, technical reviewer, or release
  authority. A multi-tenant service holding other organisations' compliance-relevant data carries
  custody, availability, and breach-notification obligations that need a staffed function and
  someone independent to check the operator's own conduct — neither of which this project's
  governance structure has, or claims to have.
- **Mechanism duplication with no capability gain.** The verification mechanism this framework
  already has is built entirely around reading the *adopter's own* local git history
  (`core/PREREQUISITE_GATES.md:67-69`, `:45-51`). A hosted service would have to either mirror that
  same history server-side, which buys nothing a local read does not already provide, or invent a
  different, unbuilt mechanism — at which point it is silently verifying something else, and the
  guarantee this framework currently makes no longer holds.
- **No elevated trust required, by design.** No organisation-level GitHub permission is ever
  guaranteed to this standard's distributor for an arbitrary adopter's organisation, and the
  git-native model requires none — it needs only what the adopter's own local clone or CI runner
  already has. A hosted service would require adopters to grant a third party access they do not
  currently need to grant for the tool to work at all.

**Rejected: a GitHub App**, as the more plausible middle ground short of full hosting — it could, in
principle, reach closer to prevention than a bypassable local hook. Rejected for the same root
reason as the hosted service, in a smaller instance of it: an installed app still requires operating
always-on infrastructure (webhook endpoints, token management, availability) that inherits the same
unstaffed, unreviewed operational-duty problem named above, just at smaller scale.

**Rejected: the status quo — clone plus `install_standard.py`, no package manager, kept
indefinitely.** This is not a straw man; it is what this repository does today, and abandoning it
without saying why would leave a gap. `DR-5`'s finding F2 already recorded the concrete cost of
keeping it as the *only* mechanism: a PEP 668 "externally-managed-environment" failure on the
default Python of current Debian/Ubuntu and the CI runners this project already uses, requiring a
disposable virtual environment every adopter must construct themselves. Dependency resolution and
environment isolation are exactly the problem pip's own tooling exists to solve; git-clone is not
retired by this decision (`DR-10` keeps its meaning of `framework_digest` unchanged), but it stops
being the only route.

**Rejected: multi-ecosystem distribution (also publish as an npm package, a Go module, and so on),
or a single dependency-free script instead of a Python package.** This looks like the natural
extension of stack neutrality, but conflates two different things: the *content* this framework
governs is stack-neutral (instructions, skills, gates apply to any adopter's stack); the *mechanism*
that fetches and vendors that content is a separate concern from what it governs, and does not need
to match every stack it governs. Maintaining parallel packaging pipelines across ecosystems
multiplies exactly the unstaffed maintenance surface the governance-capacity reasoning above already
rules out, for a benefit — one fewer `pip install` for some adopters — that does not change what the
tool actually does once installed.

**Rejected: a certification or validation service run by the maintainer.** Same reasoning as
out-of-scope item 4 — not a capability the maintainer can independently provide, so building it
would manufacture a false signal rather than fill a real gap.

**Rejected: a vulnerability or dependency scanner.** Same reasoning as out-of-scope item 5 — would
require the framework to become stack-aware, directly contradicting its own foundational
neutrality, for a problem domain already well served by dedicated tools.

## Impact

- Numerical/model output: none.
- Contracts/schemas: none directly. `DR-10` and `DR-11` already specify the schema and record-shape
  changes pip distribution and generated-file integrity require; this record is what makes both
  in-scope rather than anticipatory.
- Security/data: the "no adopter data storage, ever" and "no hosting, ever" commitments are the
  strongest security posture this framework can take — there is no server-side store of anyone's
  compliance data to be breached, because none is ever created.
- Reproducibility/lineage: none beyond what `DR-10`/`DR-11` already record.
- Operations/release: this record is the architectural spine the release plan (`org/RELEASE_PLAN.md`)
  is built against. Nothing here is implemented; the release plan orders the implementation work
  this record makes possible.
