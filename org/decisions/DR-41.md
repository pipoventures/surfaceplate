# Decision Record

- Decision ID: DR-41
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — what `surfaceplate adopt` asks an adopter for.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change (`ACT-032`).
- Risk level: 3 — it removes questions every adopter used to answer and replaces some adopter prose
  with the framework's own, which is adjacent to the one thing this package forbids. It also fixes a
  proposal that produced a gate passing while guarding nothing.
- Related work item: `ACT-032`. Closes `F40` and `F41`.

## Decision

**Ask only what a human holds; derive what follows from it. A level is a floor, and a consequence is
not a question.**

1. **One opt-in for controls above the floor**, replacing eight separate `<control>.declared`
   booleans. Choosing a level already declines everything above it.
2. **Four gate fields are derived**: `precondition_description` from `catalogue.GATE_CATALOGUE`,
   `gated_description` from the pathspec already answered, `effective_from` as today,
   `enforcement` as `history_audit` + `review`. A supplied answer still wins.
3. **The level is recommended from two world-facing questions and confirmed by the adopter** — never
   derived silently, because `core/CONFORMANCE_LEVELS.md` forbids that.
4. **`F40`**: a precondition artefact is proposed only from a candidate that actually matched the
   gate. No match, no proposal, and the question is asked.

## Context and alternatives

### The measurement changed the priority, and that is the substance of this record

The maintainer's challenge was whether the package is itself easy enough to be worth adopting:
*"why so many parameters? can't we just make decisions for the user according to best practice? if
they had a good system in place they wouldn't be using this package."*

Four personas were walked through every route. The obvious culprit was the gate catalogue, which
dominates for every persona above `essential`. It is not the answer for the persona that matters
most. A solo maintainer with one Python file sits at `essential`, faces **6** gate fields, and was
still asked **40** questions — because `controls` asked 15 of them, and **8 were tick boxes for
controls above their own floor**. `defaults.propose_controls` computed `False` for every one of
those without asking. The wizard knew the answer and asked anyway.

**A first measurement of this was wrong and is corrected here rather than quietly dropped.** The
initial persona figures (57/152/172/140) counted *planned* fields. `FieldSpec.depends_on` already
hid roughly half of them, so the numbers an adopter actually faces were 40/75/95/135. The corrected
figures are smaller and they moved the priority: the gate reduction is worth more than the controls
reduction for three personas out of four, and less for the one that needs help most.

Questions actually shown, before and after:

| Persona | Before | After |
|---|---|---|
| A · solo tool, nothing in place (`essential`) | 40 | **31** |
| B · team with CI and docs (`standard`) | 75 | **57** |
| C · product with a UI (`standard`) | 95 | **61** |
| D · quantitative / AI output (`full`) | 135 | **77** |

### Why deriving prose does not breach the binding rule

`org/RELEASE_PLAN.md` binds this wizard: *it asks, the human answers, the tool writes*.
`tests/test_provenance.py` enforces it by feeding sentinels through every field and allow-listing
what the framework legitimately contributes. Moving a gate's `precondition_description` from an
adopter's textarea to `catalogue.GATE_CATALOGUE` is exactly the kind of change that test exists to
catch, and it caught it immediately.

The allow-list grows by **`GATE_CATALOGUE.values()` and the two enforcement values, and nothing
else**. Three properties keep that honest:

- the entries are read from the catalogue, not restated in the test, so no string can be added by
  editing the test file — a new sentence must first be a gate definition in
  `core/PREREQUISITE_GATES.md`;
- the prose exemption names those two sources exactly, rather than becoming "prose is allowed";
- a new check asserts the definitions are distinct per gate, so one gate's profile entry cannot end
  up describing another.

The line this holds: **a fact about the framework may be written; a judgement about the adopter may
not.** A gate's published definition is the former. It is also, literally, the sentence the gate
screen already printed directly above the box asking the adopter to paraphrase it.

### `enforcement` is the borderline one

*How* a gate is enforced is a real decision for a repository with CI, and this record should not
pretend otherwise. It is derived because `history_audit` + `review` was already the field's default
**and** already what `defaults.py` computed, so it was asked without ever being a live question; and
because the written profile is a file the adopter edits afterwards, which the run's closing message
already tells them. A repository that wants `ci` changes one line. That is a residual cost of this
decision, not an absence of one.

### Why the level is recommended rather than derived

`core/CONFORMANCE_LEVELS.md:214-216` is explicit:

> *"The level is a human decision recorded in the adoption decision record. It is not derived
> automatically from the stack, the repository size, or the data classification, because materiality
> depends on intended use and reliance, which only the application owner can judge."*

So the two new questions change the **vocabulary**, not the authority. They are not a heuristic of
ours: `catalogue.LEVEL_BLURBS` already defines `essential` as *"anything whose output nobody outside
the team relies on"*, `standard` as *"anything a colleague or a customer depends on"* and `full` as
*"material quantitative or AI output that other systems consume as fact"*. The wizard now asks those
definitions as questions instead of asking an adopter to map themselves onto a word they have not
yet learned.

The caret starts on the recommendation; the field pre-selects nothing; `nothing is chosen yet` still
shows; `Enter` is still required. **This is the one change in the packet that adds questions** — two
of them, for every persona. It is a trade of count for comprehension and is recorded as such rather
than folded into the reduction figures.

### Alternatives rejected

- **Derive the level silently from the answers.** The fastest route to a shorter wizard and a direct
  breach of the document above.
- **Guess harder when discovery finds little.** `F40` is what that looks like: with nothing relevant
  in the repository, the best-ranked candidate is simply the only file, and proposing it produced a
  gate satisfying `SP032` while guarding nothing. A confidently wrong answer is worse than a blank
  field, because the blank field announces that something is missing.
- **Drop the above-floor controls entirely.** A level is a floor and not a ceiling; removing the
  capability would be a narrower framework, not a shorter wizard.
- **Keep asking the four gate fields with better defaults.** Already the situation. A field with a
  default nobody has a reason to change is a prompt, not a question.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none. The written profile is unchanged in shape, and byte-identical for an
  adopter who declares nothing above the floor — asserted.
- **Security/dependencies:** none.
- **Operations/release:** every adopter is asked between 23% and 43% fewer questions, and the level
  question becomes answerable without first learning the framework's vocabulary.

## Evidence

- Nine suites pass: contracts 167, installer 183, adopt 82, provenance 6, adopt-tui 33, render 17,
  discover 18, identifiers 145, registers 10 (41 F codes).
- **`F40` seen to fail first**, reporting `README.md` proposed with the detail *"the closest match in
  this repository for this gate"* — for a file that matched nothing.
- **The opt-in property seen to fail**: ignoring the ticked list makes the byte-identity check
  report `['dependency_lock']`.
- **The app-wiring test seen to fail**: not passing `recommended=` puts the caret at 0 where 2 is
  expected.
- **`F41`'s render test passed against the unfixed widget on its first writing.** It compared each
  row's whole prefix, and the field label sits on the first row only. Narrowed to the four
  characters of the button, it reports `'▐X▌ ' vs '▐X▌ '`. `DR-37`'s seen-to-fail requirement caught
  a defect in a test written to honour it.
- Screens read back as rendered text: the controls opt-in, the enforcement list, and the level
  screen with its recommendation.

## Limitations and follow-up

- **This packet does not give persona A a register.** After it they are asked fewer questions and
  proposed nothing dishonest, but `work_registration` still has no artefact to name and their
  profile will not pass the checker until one exists. A failing check is the true answer;
  **`ACT-033` is the gap** — offering to create a missing artefact from a template rather than
  asking an adopter to name what they do not have. That packet was deliberately separated because it
  makes `adopt` write files beyond the profile, which is a different class of action.
- **The framework ships no register or change-log template.** `surfaceplate/templates/` holds five:
  application profile, decision record, gate exception, override record, work packet. `ACT-033` will
  have to author what it scaffolds, not merely place it.
- **The recommendation is only as good as two yes/no answers**, and an adopter who misjudges
  reliance gets a confident recommendation for the wrong level. This is why it is a recommendation
  with its reasoning shown rather than an answer.
- **`adoption` still asks 6 questions of every persona**, including `decision_record_id` — an
  identifier for a record a first-time adopter has not written. Measured and not addressed here.
- **The defaults route has still not been driven by a human**, and every previous round of this
  wizard was corrected by a real run.
