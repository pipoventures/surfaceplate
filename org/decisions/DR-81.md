# Decision Record

- Decision ID: DR-81
- Date: 2026-09-09
- Application: Surfaceplate (the framework itself) — what an adopter must do after an upgrade, and
  who asserts which version their profile was assessed against.
- Decision owner: Mario Pipo (maintainer), answering `H23` with route (2). Drafted by the agent
  under `ACT-092`; confirmed by merging.
- Status: accepted — implemented by `ACT-092`.
- Risk level: 2 — a new command that writes an adopter's profile.
- Related work item: `ACT-092`; **closes `F146`** and `H23`; reads against `DR-45`.

## Decision

**`surfaceplate adopt --repin` sets `adoption.framework_version` and `adoption.framework_digest`
from `.standards/INSTALL.json`.** The installer does not.

## Context and alternatives

Every upgrade left both fields stale **by construction**: the installer reports
`keep governance/application-profile.yaml (yours; never overwritten)` and the next command reports
`SP048` and `SP049`. The adopter clears them by hand-copying a 64-character digest out of a JSON
file the installer itself wrote. This framework's own repository did it twice in one day, and the
maintainer met it again on the first real upgrade of an adopting repository.

**Rejected: the installer re-pins silently.** It removes the friction and quietly weakens an
assertion. `DR-45` reads `framework_digest` as **the adopter's claim** about the distribution they
assessed against, and `SP049` exists to catch a profile claiming an install that is not present. An
installer that re-pinned on its own would let a version change through with nobody re-reading the
profile — the assertion `review_by` exists to make.

**Rejected: leave it and document the two fields in the upgrade's "Next steps".** Honest, and a
permanent two-finding tax on every upgrade forever. It also leaves a 64-character value to be copied
by hand, which is a class of error nobody should be exposed to twice.

**Chosen: separate the claim from the clerk.** Running the command is the deliberate act, and that
is what `DR-45` wants asserted. The *value* was never the adopter's contribution — it is the
installer's own record of what it wrote — so typing it accomplishes nothing but the chance of typing
it wrong.

**This is why the sidecar records `fact of record` and not `typed`.** The adopter chose to re-pin;
they did not choose the digest. Recording it as typed would say they had.

## Impact

- `surfaceplate adopt --repin`, and `wizard.repin(repo)` behind it. Idempotent: run twice and the
  second says `Already pinned … nothing to change.`
- **The two lines are substituted, not re-rendered**, and this framework's own profile is why. The
  first implementation re-rendered the whole file as `--edit` does, and refused on this repository:
  *"the rendered YAML does not round-trip to what was assembled"*. The guard was right and the
  design was wrong — a hand-maintained profile carries whatever its adopter put there, and
  re-rendering passes every line through a renderer that only knows what `adopt` writes. So the
  population that most needs `--repin` — anyone who has edited their profile directly, which after
  an upgrade is anyone who cleared `SP048` by hand — is exactly the population it would have
  refused. The substituted text is then **parsed back and checked** against the values it was
  given, and verified, rather than assumed.
- Both fields gain a sidecar entry with `origin: fact of record` and a reason naming what moved,
  and the edit joins the sidecar's history.
- `SP048` and `SP049` are unchanged. They still catch a hand-edited profile, which is the case they
  are actually for.

## Evidence

- On the real adopter that produced `F146` — a copy of the one repository that has adopted this
  standard, upgraded `0.16.0` → `0.18.0`: `WARN` with `SP048` and `SP049`, one command,
  `PASS - all conformance checks satisfied`.
- `tests/test_adopt.py::test_repin_clears_the_two_findings_an_upgrade_guarantees`, which stales a
  complete profile the way an upgrade does, asserts the fixture really is stale before asserting
  anything about it, and checks the origin recorded is `fact of record` rather than `typed`.
- Idempotence asserted: the second run writes nothing and says so.

## Limitations and follow-up

**Nothing makes an adopter run it.** The upgrade's "Next steps" and the two findings point at the
state; the command is the remedy and not a prompt. A future change could have the installer *offer*
it, which would keep the act deliberate while removing the discovery problem — deliberately not done
here, because an installer that suggests a command is a smaller change than one that runs it and
this record should not smuggle in the second.

**`--repin` re-pins to whatever is installed, without asking whether the adopter has read the
changes.** That is the honest limit of the split this record makes: it moves the clerical half and
cannot move the reading half. `review_by` remains the field that asserts a profile has been re-read,
and nothing here touches it.
