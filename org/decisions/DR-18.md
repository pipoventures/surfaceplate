# Decision Record

- Decision ID: DR-18
- Date: 2026-08-31
- Application: Surfaceplate (the framework itself) — a decision about a published control.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change.
- Risk level: 2 — "output-affecting code, data, schema, or workflow", per the risk table in
  `core/REVIEW_AND_EVIDENCE.md`. It adds an obligation every adopting repository must satisfy
  at every conformance level.
- Related work item: `ACT-005`, registered in `activity/register.md`. Item 4 of
  `org/RELEASE_PLAN.md`.

## Decision

**`secret_hygiene` gains verification: the profile declares a scanner and where it is wired, and
the checker verifies the wiring exists, invokes the scanner, and can fail the job.**

Two new codes, both graceable:

- **`SP046`** — no scanner named; or `wired_in` is empty, names a file that does not exist, names
  a file that never mentions the scanner, or names a workflow in which no step invokes it.
- **`SP047`** — the invoking step cannot fail the job: `continue-on-error: true`, or the scanner's
  command discards a non-zero status.

Surfaceplate satisfies its own new control in the same change: `.github/workflows/secret-scan.yml`
is added and declared.

## Context and alternatives

### Why this was the item to do

`core/CONFORMANCE_LEVELS.md` requires `secret_hygiene` at **every** level, unconditionally, and
nothing verified it. `grep -ci secret scripts/check_conformance.py` returned **0**. `CHANGELOG.md`
had recorded the gap since 0.9.2 and `org/RELEASE_PLAN.md` names it not cuttable — *"a false claim
of a floor that is not there."*

The gap was wider than the control. **No baseline control was verified at all**: the checker never
referenced `baseline_controls`, so all three were schema-shaped declarations and nothing more. This
record closes one of the three and says plainly, in `core/CONFORMANCE_LEVELS.md`, that the other two
remain unverified — because a reader who learns that one baseline control is now checked will
otherwise assume the others are too.

### What the control does not do, stated first

**It does not scan for secrets, and a pass says nothing about whether secrets are present.** This
framework's only runtime dependencies are PyYAML and jsonschema. Bundling a scanner, or
reimplementing one, would be both out of proportion and worse than the tools that exist.
`core/SECURITY_BASELINE.md` already placed the scanner with the adopter — *"run the receiving
repository's approved secret scanner"* — and this decision keeps it there.

The risk in a control like this is not that it fails to work; it is that it reads as stronger than
it is. That is the same overclaim `ACT-201` removed from the README banner, and it would be worse
here because it would sit inside a control rather than beside one. Every message the check emits
talks about wiring; none mentions findings.

### Why "a scan step exists" is not enough — the evidence

A workflow can run a scanner, print `no findings`, and stay green while the scanner found several.
This is observed, not hypothetical: a run in a sibling repository printed **both**
`leaks found: 4` and `gitleaks: no findings.`, because the summary step ended in `|| echo 0` and an
unreadable report was indistinguishable from a clean one. Eleven consecutive "clean" runs meant
nothing, and the workflow was flipped to blocking on the strength of them.

A control that confirmed only that a scan step existed would have passed that workflow. It would
measure the presence of a control rather than its effect — the defect `core/CONTROL_PRINCIPLES.md`
principle 9 exists to name. Hence `SP047`.

### Alternatives considered and rejected

- **Ship a scanner with the framework.** Rejected: disproportionate, and it would put this
  repository in the business of maintaining detection rules it has no advantage in maintaining.
- **Require the scanner in the schema rather than the checker.** Rejected, and the reasoning
  generalises: a schema violation is un-graceable, so making `scanner` a required property would
  hard-fail every existing profile the day it shipped. A new obligation must arrive through the
  grace mechanism this framework already provides, or it is an obligation nobody can adopt. The
  property is therefore optional in the schema and required by the checker, graceably.
- **Regex the workflow text for bypass patterns.** Rejected in favour of parsing the YAML and
  inspecting only steps that actually invoke the named scanner. `F14` is four days old and was
  exactly this mistake: a shape-based match over whole file text that could not tell context from
  content. `|| true` in an unrelated step is not this control's business.
- **Scan the pushed range or all of history in surfaceplate's own workflow.** The workflow blocks
  on the pushed range with a full-history fallback where the range cannot be determined. History
  here is immutable, so failing a build over a historical finding blocks work that cannot fix it —
  the remedy for a leaked credential is rotation, not a red build.

### Where surfaceplate's own workflow deliberately differs from the portfolio

The equivalent workflow in the sibling repositories checks out a shared gitleaks configuration from
another private repository using a repository secret. Surfaceplate's does not, and uses the
scanner's own rules instead. This repository is meant to be read and copied by people with no
access to that configuration, and a framework whose own security workflow cannot run in the
reader's checkout demonstrates the wrong thing. The cost is real and recorded rather than glossed:
this repository does not inherit the portfolio's tuned rule set, and may see false positives the
others have already triaged.

The scheduled full-history sweep those repositories also carry is **not** copied here, and the
reason is measured rather than assumed. When this was first written it said no `schedule` event had
ever been observed to fire in this account. **That premise was falsified hours later and is
rewritten rather than footnoted.** Measured on Monday 2026-08-31 at 12:19 UTC, with five workflows
across four repositories all carrying `0 6 * * 1` and therefore all due at 06:00: **one fired, six
hours late; four were still overdue.**

So schedules are not disabled, and the decision does not rest on a broken mechanism. It rests on an
unreliable one. A trigger that fires for roughly one in five due runs, six hours late, cannot bound
a detection interval: a sweep described as weekly may run monthly, and nothing in the record would
say otherwise. That is the defect a scheduled control exists to remove, so adopting it here would
buy the appearance of a bounded interval and not the interval. Tracked as `mnemosyne#ACT-056`, whose
open question is now a decision — is best-effort weekly adequate? — rather than a diagnosis.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** `secret_hygiene` moves to its own `$def` carrying an optional `scanner`
  object. Additive and backward-compatible — an existing profile still validates.
- **Security/data:** the framework reads workflow files it did not previously read. It looks at
  structure, never at values, and writes nothing.
- **Reproducibility/lineage:** `.standards/` reinstalled in the same change so the two checker
  copies do not diverge (`F12`).
- **Operations/release:** an adopting repository with no declared scanner now sees `SP046` at
  `WARN`, becoming a failure when its grace window ends. Both worked examples under `examples/`
  are updated to show the shape.

## Evidence

Every failure mode was made to fail before the control was trusted, and so were the guards.

**The control fires:**

| Probe | Result |
|---|---|
| `scanner` block removed | `SP046` — no scanner named |
| `wired_in` names a non-existent file | `SP046` — wired to a file that does not exist |
| Workflow mentions the scanner but no step runs it | `SP046` — names it but no step runs it |
| Scan step carries `continue-on-error: true` | `SP047` — cannot fail the job |
| Scan command discards its exit code | `SP047` — discards its exit code |
| Correctly wired scanner | neither code; `PASS` |

**The guards fire:** removing the `check_secret_hygiene` call from the checker fails all five
positive tests; sabotaging the control to report "no scanner" unconditionally fails the negative
test. Without the second, all five positives would pass a control that fired on everything.

Suite counts: `test_install_and_check.py` 101 → 107. `validate_contracts.py` unchanged at 90.
`check_conformance.py --repo .` returns `PASS` on both the source and the vendored copy after
reinstalling.

**Surfaceplate's own workflow was verified to have actually scanned, on both code paths.** A green
scan step is the artefact `F13` warns about, so the job's conclusion was not treated as the
evidence:

| Run | Trigger | Range resolved from | Result |
|---|---|---|---|
| `33389160561` | `pull_request` | `github.event.pull_request.base.sha` | `2 commits scanned`, no leaks |
| `33390248673` | `push` to `main` | `github.event.before` | `2 commits scanned`, no leaks |

The two paths compute the range differently, so a workflow correct on one can be broken on the
other; the push path would otherwise have gone untested until it mattered. Both resolved a real
incremental range rather than falling back to a full scan, and the summary step reported the report
as read with zero entries rather than reporting silence as cleanliness.

What this evidence does **not** establish, stated because the table invites the wider reading: that
this repository contains no secrets. It establishes that the scanner ran over a non-empty range and
that its result reached the job.

## Limitations and follow-up

- **Detection, not proof, and only for workflows.** A file that is not a parseable GitHub Actions
  workflow gets existence-and-mention checking only; no `SP047` is raised for a shell hook. The
  check does not claim otherwise, and `core/SECURITY_BASELINE.md` says so.
- **The bypass list is not exhaustive.** `continue-on-error`, `|| true`, `|| :`, `|| exit 0` and
  `|| echo` are the forms that discard a status outright. A step could still neutralise a scanner
  by other means — a wrapper script, a config that disables every rule, a trap. This is a floor.
- **A declared scanner is not an approved one.** The framework takes no position on whether the
  named tool is fit for the repository's risk, and cannot: `core/SECURITY_BASELINE.md` leaves
  approval a human decision.
- **The other two baseline controls remain unverified**, now stated in
  `core/CONFORMANCE_LEVELS.md` rather than left to inference.
