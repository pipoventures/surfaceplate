## Decision

1. **Version parity before the first question.** `adopt` — interactive, `--propose` and
   `--answers` alike — refuses to run when the tool's framework anchor differs from the install
   record's, naming both versions and digests and the upgrade command, and `doctor` reports the
   same comparison on its own line. The wizard keeps validating against the installed schema:
   the adopter's checker reads that copy, so a profile the tool's own schema accepted would
   fail on the next run. The comparison, not the schema choice, is the fix (`F78`).
2. **An opening screen.** Before the first question: the tool's name, version, licence and
   publisher from package metadata; the installed version, digest and framework maintainer
   from the install record; what the run will write and where, that nothing is written before
   the review, and the keys. Package metadata is held in one module and asserted equal to
   `pyproject.toml` (`F81`).
3. **A stated minimum on every field.** Each presented field carries, beside what it asks,
   what the answer decides and what a wrong answer costs, drawn from the same plain-English
   register as the explanations; they are shown beside the focused field. A coverage test
   fails on any presented field, at any level, lacking either (`F82`).
4. **Every choice from the repository is described when selected.** For an artefact: what was
   seen in the file (its first heading), whether it matched the gate's words, and whether the
   checker would reject it. For a workflow: which step runs the scanner. A gate's status row
   states what each status commits the team to, and `required` names what the checker will then
   audit (`F80`).
5. **The wizard proposes nothing the checker rejects.** Scanner workflows are candidates only
   where a step runs the named scanner, and the field's validator refuses any other file
   (`SP046`, `F83`). An artefact that is empty or carries a placeholder token is never proposed,
   is described as one the checker would reject, and the validator refuses it (`SP032`, `F84`);
   `authority_map`'s discovery words drop `inventory`, which matched a work inventory and not
   an authority map. Both rows join the parity table.
6. **A refusal names the line and the keys.** A schema refusal on the review is reported in the
   review's own words with the profile path it concerns, `Ctrl+E` goes to it, and the hint
   names the key that writes once the refusal clears (`F79`). The closing report states the
   checker's verdict as the checker gave it: a pass, or the number of graced findings and the
   date the grace ends (`F85`).
7. **The snapshot goldens change for cause.** A new snapshot for the opening screen; changed
   snapshots for every screen whose help text or status meanings gained rows. Each regeneration
   carries this record as its cause and the delta in the commit that makes it.

## Context and alternatives

The maintainer's first run stopped at the review on a version mismatch reported in the
validator's vocabulary, and finished with two checker findings caused by values the wizard had
proposed: a CI workflow that never mentions the scanner, and a file matched on the word
`inventory` that is not an authority map and quotes placeholder tokens. He also reported that
the artefact choices explain nothing about cost or benefit, that the wizard has no opening
screen, and that its own author could not always say what a question was for (`F78` to `F85`,
each with his words as evidence).

Alternatives considered: validate against the tool's own schema (rejected: the adopter's
checker reads the installed copy); warn on a version mismatch and continue (rejected: the
interview is lost at the review, as it was); hide artefact candidates the checker would reject
(rejected: `DR-38`'s rule that the adopter chooses from everything found; they are described
and not proposed instead); a help overlay per screen (rejected: the minimum belongs beside the
field, where `F67` already put the help).
