# Decision Record

- Decision ID: DR-33
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — a decision about the shape of a published
  contract, `schemas/application-profile.schema.yaml`.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — no code changed as a result.
- Risk level: 1 — it declines to change a published contract, and records why rather than leaving
  the question open for the next reviewer to raise again from nothing.
- Related work item: `ACT-023`. Raised by Gemini's adversarial review (`ACT-021`, `F32`).

## Decision

**`application-profile.schema.yaml` does not gain conditional (`if`/`then`/`allOf`) blocks tying
`conformance_level` to which `control_decisions` keys must be present.** The schema continues to
validate structural shape only — types, required top-level fields, enums, per-entry field shapes.
Which controls a given level requires stays sole Python data, in `check_conformance.py`'s
`CONFORMANCE_LEVELS`, checked at runtime rather than restated in the contract.

## Context and alternatives

### What was proposed, and by whom

Gemini's adversarial review (`ACT-021`) filed a material finding: *"The YAML schema alone cannot
detect if a user declares `full` but omits all required controls... A user bypassing the validation
script can trivially forge a higher conformance tier."* Its recommended remediation: *"Introduce
conditional `allOf`/`if` blocks in `application-profile.schema.yaml` to enforce the presence of
required controls directly at the schema level based on the chosen `conformance_level`."*

The claim about the schema alone is accurate — nothing in `application-profile.schema.yaml` today
ties `conformance_level` to `control_decisions`' contents. Whether building the recommended fix
would close anything is the question this record answers, checked against the code rather than
taken on the report's authority (`org/FINDINGS.md`'s `F32` entry records why that check matters:
two of this same report's other findings did not survive it).

### The scenario the finding describes does not exist in this project's actual pipeline

`check_conformance.py` runs schema validation as part of its own execution, not as a separate step
someone could invoke instead of the checker. `check_profile_schema` (`check_conformance.py:502`) is
called immediately before `check_profile_semantics` (`check_conformance.py:3088-3089`), inside the
same `main()` run. There is no tool in this project's actual CI wiring, or documented for an
adopter's use, that validates *only* against the schema and stops there. `standards-conformance.yml`
— the workflow this project installs into every adopting repository — runs
`check_conformance.py --repo .`, which always performs both.

So "a user bypassing the validation script" to forge a higher tier does not describe a real gap in
how this framework is used: the validation script *is* the schema check, plus the semantic checks,
run together. Someone who skips the checker entirely skips schema validation with it — adding
conditionals to the schema does not create a second, independent gate that survives that skip,
because nothing currently runs the schema alone.

### What the schema genuinely cannot do, regardless of how much conditional logic it gains

Even a fully-elaborated `if`/`then` block requiring the right *keys* to be present in
`control_decisions` could only ever check that a key exists with the right shape — never that what
it points at is real. `check_conformance.py`'s actual per-control checks need information no single
YAML document can carry:

- **Pattern A** (`dependency_lock`, `assurance_findings`) — the named `implementation_reference`
  file must exist on disk.
- **Pattern B** (`contract_tests`, `deterministic_tests`) — the named CI step must exist, by name,
  in a workflow file.
- **Pattern C** (`overrides`, `method_registry`, `run_lineage`, `provenance`) — the named register
  directory's contents must each validate against a further schema.
- Every prerequisite gate's `effective_from` must never have moved forward across the repository's
  own git history (`SP034`) — checkable only by reading commits, which a schema validator run over
  one document never sees.

A schema addition covering only "the key is present" would narrow, but not close, the gap Gemini
described, while reading — to anyone who has not traced how the two are actually run together — as
though it had closed something it had not. `core/REVIEW_AND_EVIDENCE.md`'s own materiality
definition names exactly this failure mode: a control described as stronger than it is.

### The cost side: a second, hand-maintained copy of `CONFORMANCE_LEVELS`

`CONFORMANCE_LEVELS` (which controls each level requires) is Python data in `check_conformance.py`,
with no generator producing schema text from it — every schema in this repository is hand-authored
YAML. Encoding the same rule a second time, by hand, as `if`/`then` conditionals would create
exactly the shape `F23` and `DR-6`/`DR-9` have each independently identified and closed elsewhere
in this project: two statements of one fact, agreeing on the day both are written and silently
free to drift apart on the next change to either. A level gaining a new required control (as `full`
did across `ACT-011`–`ACT-015`) would need updating in two places, with nothing in this repository
currently positioned to catch a forgotten second edit to a schema clause.

### Alternatives considered

- **Build the conditional schema blocks as proposed.** Rejected above: closes nothing the checker
  does not already close in this project's real pipeline, and opens a drift risk with a known,
  recorded history of causing exactly this project's own findings.
- **Build a generator that derives the schema's conditionals from `CONFORMANCE_LEVELS`.** Would
  remove the drift risk, at the cost of a build step and a generated-vs-authored split none of this
  repository's other schemas have. Not rejected outright — a real option if the marginal defense-in-
  depth value were higher — but not pursued here because the underlying gap (per the section above)
  is not real for this pipeline as it stands today.
- **Do nothing, and don't record why.** Rejected: the same idea would predictably be raised again by
  a future reviewer with no visibility into this reasoning, and re-litigating it from nothing each
  time is the cost this record exists to avoid.

## Evidence

- `check_conformance.py:502` (`check_profile_schema`) and `:3088-3089` (its call site, immediately
  before `check_profile_semantics` in `main()`) — read directly to confirm the ordering claim above,
  not assumed from memory.
- `.github/workflows/standards-conformance.yml:38` and
  `surfaceplate/standard/.github/workflows/standards-conformance.yml:38` — both run
  `python .standards/check_conformance.py --repo .`, never the schema in isolation.
- No file in this repository generates schema text from `CONFORMANCE_LEVELS` — confirmed by the
  absence of any such reference in `scripts/build_release.py` or the schema files themselves.

## Limitations and follow-up

- **This does not mean the schema is complete, or that nothing should ever be added to it.** It
  means this specific proposal, as stated, does not close the gap it was proposed to close. A
  different schema addition, aimed at a genuinely schema-checkable gap, would be evaluated on its
  own terms.
- **The generator-based alternative remains open**, not rejected, should the underlying calculus
  change — for instance, if a future distribution channel someday validates a profile against the
  schema without running the checker, which does not exist today.
