# Decision Record

- Decision ID: DR-21
- Date: 2026-08-31
- Application: Surfaceplate (the framework itself).
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change.
- Risk level: 1 — it changes what this repository offers as producer evidence, and removes a
  document an auditor was pointed at. No code behaviour changes.
- Related work item: `ACT-006`. Closes `F10`.

## Decision

**Retire `audit/VALIDATION_RESULTS.md` as producer evidence. The test suites are the evidence.**

The file is kept, marked historical and frozen at `0.7.0`, with every row that is no longer true
annotated **inline**. It is not regenerated and will not be maintained. `audit/AUDIT_README.md`,
which pointed an auditor at it as *"the producer's current check record"*, now points at the suites
instead.

## Context and alternatives

### What was wrong

`audit/VALIDATION_RESULTS.md` said it *"records checks run by the package producer for the current
release"*. Verified against the tree on 2026-08-31, with `VERSION` at `0.14.0`:

| Claim | Reality |
|---|---|
| `Current release: 0.7.0` | Seven releases stale |
| `PASS - 5/5` schemas, twice | There are **6** |
| Verify `dist/surfaceplate-0.7.0.zip` | Does not exist |
| `Version consistency … PASS` | **`DR-6` abolished this rule.** `VERSION` is `0.14.0`, the namespace segment `0.7.0` |
| `Secret-pattern scan … PASS - no matches` | This repository had **no** automated secret scanner until `DR-18`, four days ago |

The fourth row is why this ranked first among the open findings. It is not staleness — it is a
**passing result reported for a check that was deliberately removed**. A reader takes it as evidence
that two values agree, when the framework's own decision record says they are decoupled by design
and correctly differ.

The fifth is worse in kind, if not in consequence: a "no matches" result from a method nobody named,
produced by no repeatable control, presented in a table of controls.

### Why retire rather than regenerate — the evidence, not a preference

**Regeneration was already tried, and the defect recurred.** `CHANGELOG.md:75` records fixing
`PRE-AUDIT-0.6.0/F2` by regenerating this exact file, which then described `0.5.0` while `0.6.0`
shipped. Seven releases later it describes `0.7.0` while `0.14.0` ships. Applying the same remedy a
second time and expecting a different outcome would be the definition of not learning from the
register.

The structural reason it recurs: a hand-written evidence document must be updated by a human on
every release, and nothing fails when they do not. It is an artefact whose accuracy depends entirely
on discipline, in a repository whose entire thesis is that discipline is not a control.

**Its function is now genuinely served.** When this file was written it was the only record of what
the producer had checked. Today five suites run on every push and pull request, each reporting the
number of checks it actually executed — `validate_contracts.py`, `test_install_and_check.py`,
`check_identifiers.py`, `check_code_registers.py`, `check_vendored_current.py` — alongside
`build_release.py --verify-manifest` and `check_conformance.py --repo .`. The self-check workflow
additionally confirms each step produced a result, so a check that never ran cannot be mistaken for
one that passed (`F13`). That is strictly better evidence than a table: it is re-runnable by anyone,
it is dated by the commit, and it cannot go stale without going red.

### Why the file is kept rather than deleted

Two reasons, and the second is the load-bearing one.

It records what was claimed at `0.7.0`, which is history worth keeping — the `DR-5` precedent.

More importantly, **its "Checks NOT performed" and "Outstanding" sections are still true**, and
`F6` and `F8` cite the latter by line for the statement that the audit gate is undischarged and the
pre-audit was not independent. Deleting the file would break live citations to make a tidier tree.

### Why the annotations are inline

Marking the file historical at the top and leaving the table untouched would produce a correction
whose validity depends on reading order. A grep for `Version consistency` lands on the row, not on
the banner. So each stale or abolished row is annotated in the row itself. The banner is for the
reader who arrives at the top; the annotations are for the reader who does not.

### Alternatives rejected

- **Regenerate against the current tree.** Rejected on the recurrence evidence above. It would also
  require re-running and re-establishing every row to be honest — and several rows name checks that
  no longer exist, so they could not be re-established at all, only deleted.
- **Delete the file.** Rejected: breaks `F6` and `F8`'s citations and destroys the historical
  record.
- **Automate its generation.** Rejected as the wrong shape. A generated, tracked artefact reconciled
  against the code it describes is a known hazard — it merges cleanly when resolved badly and the
  checker then passes against the wrong set. The suites already emit their counts at run time; a
  file restating them adds a second place to be wrong.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none.
- **Security/data:** none.
- **Operations/release:** an auditor following `audit/AUDIT_README.md` is now directed at
  re-runnable suites and a CI run rather than a document. `AUDIT_README.md` also named
  `engineering-control-kit.zip` — the pre-`0.12.0` product name, for an archive not produced under
  that name since the rename — which is corrected in the same change.

## Evidence

- Every claim in the table above verified against the working tree today, not taken from `F10`'s
  own text. That precaution is not ceremonial: `F5`'s entry had asserted a defect corrected several
  releases earlier, so a finding's description of reality is not itself evidence about reality.
- `CHANGELOG.md:75` is the record of the prior regeneration, and is what makes the recurrence
  argument a measurement rather than a prediction.
- Counts confirmed by direct enumeration: 6 `schemas/*.schema.yaml`, 3 files in `examples/`.

## Limitations and follow-up

- **This removes a document; it does not add a control.** The suites existed before this decision.
  What changes is that the repository stops offering a stale document as evidence and stops pointing
  auditors at it.
- **The historical file can still mislead a careless reader.** The banner and the inline
  annotations are what stand between it and that outcome. Nothing enforces them; if a future edit
  removes the annotations, nothing fails.
- **`F8` is not closed by this change.** Its documentation half is discharged in the same commit —
  three `README.md` claims about the history audit corrected — but the structural remedy is
  `DR-15`'s ruleset posture, which cannot be demonstrated on this repository's plan.
