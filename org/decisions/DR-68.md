# Decision Record

- Decision ID: DR-68
- Date: 2026-09-08
- Application: Surfaceplate (the framework itself) — whether an adopting repository is told that
  the standard it installed is no longer the published one.
- Decision owner: Mario Pipo (maintainer). Drafted by the agent under the approved `ACT-067`
  packet; confirmed by merging, per the convention `DR-64` records.
- Status: accepted — the mechanism implemented by `ACT-067`. **The trigger is not decided; see
  Limitations.**
- Risk level: 2 — it adds a second outbound request to `doctor.py` and a new advisory adopters
  will see. It does not change what any control means, and `check_conformance.py` is untouched.
- Related work item: `ACT-067`; finding `F124`, which this **narrows and does not close**.

## Decision

**Currency is reported by `surfaceplate doctor --online`, as an advisory, never as a failure.**

1. `check_conformance.py` is **not** changed. Its offline guarantee is a property adopters rely
   on, and adding an opt-in network call to it would weaken a stated claim to buy a convenience.
2. `doctor.py` gains `check_standard_currency`, behind the existing `--online` flag: it reads the
   installed version from `.standards/INSTALL.json` and compares it against the version
   `pypi.org` publishes. No credential is sent and none is needed.
3. **Advisory, never a failure.** Pinning a version is a legitimate decision, and a check that
   failed on it would be telling adopters that deliberate version control is a defect.
4. **Ahead is a different fact from behind and is reported as one.** The publisher's own
   repository is always ahead by construction, because it installs from its working tree.
5. **Unreachable is `warn`, not `ok`.** An unanswered question is not a passing one; reporting
   `ok` because the network was down is the false green this framework exists to find.
6. The version comparison is numeric per segment, so `0.9.0` sorts below `0.17.0` — which a
   string comparison gets backwards, and which this repository would have hit first.

## Context and alternatives

`F124`'s finding is that `check_conformance.py` establishes an install is **unedited** —
`MANIFEST.sha256`, and `SP049`'s recomputation of the anchor — and has no notion of whether it is
**current**. It cannot have one: it runs inside the adopting repository with no network, and
`DR-45` states plainly that the anchor *"records the manifest of the tree installed FROM, which is
a historical fact, not a live invariant"*. A repository can therefore sit any number of versions
behind, indefinitely, while its check passes and says nothing.

**Rejected: teach `check_conformance.py` to go online behind a flag.** The checker's offline
behaviour is not an implementation detail; it is what makes a conformance result reproducible from
the repository alone, and `DR-4` rejected runtime dependence on anything outside version control
for that reason. A flag that could reach the network would have to be reasoned about by every
adopter reading the checker, to buy a fact a second command already answers.

**Rejected: vendor `doctor.py` into the payload.** It would add a module an adopting repository
does not otherwise need, to run a check that has no bearing on conformance.

## Impact

- Contracts/schemas: none. Numerical/model output: none. Conformance semantics: none.
- Security/data: **a second outbound request**, to `pypi.org`, behind `--online`, sending no
  credential. `doctor.py`'s module docstring is amended in the same change to name both requests
  as the whole of its network surface — a third added without amending it would be `F55`'s drift.
  `--report` remains offline and deliberately incompatible with `--online`.
- Operations: an adopter running `doctor --online` sees one more line.

## Evidence

**Verified by effect against the live index, in all three directions**, on 2026-09-08:

| Installed | Published | Result |
|---|---|---|
| `0.16.0` | `0.16.1` | `warn` — the case `F124` names, reproduced exactly |
| `0.16.1` | `0.16.1` | `ok` — **a current install produces no signal** |
| `0.17.0` | `0.16.1` | `ok`, reported as *ahead*, not as an upgrade instruction |

The middle row is the one that makes the first worth anything: a check that fired on everything
would have detected nothing.

`0.9.0 > 0.17.0` compares `True` as strings and `False` keyed, asserted directly.

## Limitations and follow-up

**`F124` is narrowed, not closed, and the remaining half is a decision this record does not
take.** The mechanism exists; nothing *triggers* it. An adopter who never runs
`doctor --online` is in exactly the position the finding describes, and the obvious trigger — a
step in the installed conformance workflow, which runs in every adopter's CI where a network
exists — is not built here because it would:

- make **every adopting repository's CI** call out to `pypi.org` on every run; and
- be **uneditable by the adopter**, since the installed workflow is integrity-checked, so a
  repository that did not want the call could not remove it without failing its own check.

That is a change to what adopters' infrastructure does and to an outbound network boundary, which
this standard's own rules reserve to a human. Recorded as `H20`.

Not tested against a pre-release version string (`0.18.0rc1`), which `_version_key` orders by
falling back to text comparison — wrong in general, and never worse than not answering, since the
only consequence is an advisory phrased as "behind" when it is "ahead".
