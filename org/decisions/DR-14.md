## Decision

**Adopt `sha256(MANIFEST.sha256)` as the distribution-identity anchor**, replacing the release
archive's own SHA-256 in that role. `adoption.framework_digest` becomes channel-neutral: one
meaning, computed the same way, whether the code arrived by git clone, by `pip install` from an
index, or by `pip install git+…`.

Consequently, **`adoption.distribution_channel` is dropped.** `DR-10` introduced it for exactly one
purpose — *"to disambiguate which meaning a given profile is using"* (`DR-10.md:29-30`) — and with
a single channel-neutral meaning there is nothing left to disambiguate. It was never implemented:
exhaustive grep finds it in decision-record prose only, with zero occurrences in any schema, script,
test, template, or example.

**This decision takes up an option `DR-10` deferred; it does not reverse a rejection.** `DR-10`
named this exact candidate and declined it on scope grounds alone, calling it
*"a real, ready-made improvement to git-clone Layer 1 that this decision does **not** make"*
(`DR-10.md:84-91`) and listing it in its limitations as *"a concrete, already-evaluated candidate
waiting"* (`:246-248`). Recording that accurately matters: presenting this as a fresh idea would
misrepresent the record.

**What it does not do.** It does not close finding `F6` (`org/FINDINGS.md`). See "Does this close
the anchoring gap, or relocate it?" below — the honest answer is that it closes one half and
narrows the other, and this record does not claim more.

## Context and alternatives

### Why the archive digest fails the criterion it was chosen for

`DR-10` set the governing question as *"by what evidence can an adopter later prove which version of
the framework they conformed to, on a machine that is not theirs?"* The archive digest cannot answer
it, and `DR-10` says so itself (`:79-84`): `build_release.py:85-88` writes zip entries with
`zipfile.ZipFile.write`, which embeds each file's mtime, so *"the maintainer's own tooling cannot
reproduce the artefact whose digest a tag message or an adoption record cites, only re-verify the one
already built."*

Verified independently for this record: `sha256()` (`build_release.py:43-48`) hashes raw bytes with
no metadata; `write_manifest` (`:74-77`) emits one line per payload file over the path-sorted list
from `:40`, with `newline="\n"` forced. No clock, mtime, or ordering non-determinism enters it — the
module imports only `hashlib, subprocess, sys, zipfile, pathlib`. **`MANIFEST.sha256` is a pure
deterministic function of tree content, and therefore so is its digest.** The archive is not.

### The argument that was not in the original rationale

`scripts/verify_release.py` **never verifies the archive.** It verifies the manifest against the
payload in both directions (`:74-84`) and merely *prints* the archive digest for transcription
(`:87`). So the value `DR-10` makes canonical is the one thing the verifier does not check, while
the manifest — the thing it actually exercises — is not what gets recorded. Manifest-anchoring makes
the recorded identity coincide with what the tooling already verifies.

It also removes a dependency on the archive existing at all. `verify_release.py` cannot run without
a zip; `sha256(MANIFEST.sha256)` is computable from any checkout or unpacked tree with one command.

### Does this close the anchoring gap, or relocate it?

**It closes the external-verifiability half and narrows, but does not close, the local-record half.**
Stating that plainly is the point of this section.

*Closed:* a third party, on a machine that is not the adopter's, can now recompute the anchor from a
published tree and compare. Under the archive digest they could not — they could only re-verify a
copy of the artefact if they happened to have one.

*Not closed:* an adopter can still edit their own `adoption.framework_digest`, and nothing in the
checker reads it (`F7`). The anchor is only as good as an out-of-band comparison someone actually
performs.

**And three structural obstacles block the tempting next step** — using the manifest to validate
`.standards/INSTALL.json` and thereby close `F6`. All three were established by direct reading and
none is cosmetic:

1. **The two digest schemes are not interchangeable.** The manifest hashes raw bytes
   (`build_release.py:43-48`); the install record hashes line-ending-normalised text
   (`install_standard.py:50-56`). They agree on LF files and diverge on CRLF. A naive cross-check
   would raise false tamper reports on Windows checkouts — precisely the failure the normalisation
   exists to prevent, and `DR-10.md:243-245` already records the two schemes as unreconciled.
2. **The path namespaces differ by a rename, not a prefix.** Manifest entries read
   `surfaceplate-0.14.0/scripts/check_conformance.py`; the corresponding install-record key is
   `.standards/check_conformance.py`. Any cross-check needs a mapping table, which is itself code
   that can drift from the thing it maps.
3. **The vendored payload is a strict subset of the release payload, and the record is in neither.**
   `build_payload` (`install_standard.py:62-103`) ships a subset; `INSTALL.json` is generated at
   install time and appears in neither the manifest nor its own `files` map.

So this record anchors *distribution identity*. Closing `F6` is separate work with a real design
problem in front of it, and is not decided here.

### Does it make `pip install git+…` coherent?

Yes, and this exposes a gap `DR-10` did not notice. `pip install git+https://…` is a **third
channel** that `DR-10`'s binary `git | pip` enum does not name. It produces no release archive, so
there is no archive digest; and the wheel pip builds locally from the checkout is neither published
for a stranger to compare against nor free of the build-time non-determinism `DR-10.md:80-83`
condemns in the zip. Under `DR-10` that route has no well-defined `framework_digest` and no honest
`distribution_channel` value.

`sha256(MANIFEST.sha256)` is well-defined for it, because the manifest is a committed file present
in any checkout. **Caveat, stated so it is not mistaken for a guarantee:** this holds only once the
`git+` URL itself pins a commit — `git+https://…@<sha>`. Against a branch, pip resolves whatever the
branch points at, and no digest recorded afterwards establishes what was installed.

### Reproducible builds, and version sensitivity

**Reproducible archive builds become desirable rather than required.** Nothing this record adopts
depends on the zip being byte-reproducible. Making it so would still be worth doing — it would let an
adopter who holds an archive re-derive it — but it stops being a prerequisite for a trustworthy pin.

**Version sensitivity is preserved, which matters more than it first appears.** The manifest embeds
the version in every path prefix, and `VERSION` is itself an entry (`MANIFEST.sha256:11`), so the
anchor changes on every release whether or not any content did. That is the property `DR-6.md:54`
and `NAMESPACE.md:71-73` both rely on: *"what actually reproduces a validation result is the release
digest recorded in `adoption.framework_digest`, which already changes on every release whether or
not any schema does."* Manifest-anchoring preserves it rather than disturbing it.

### Rejected alternatives

**Rejected: keep the archive digest.** It fails the reproducibility criterion `DR-10` itself set, and
it is the one value `verify_release.py` never checks (`:87` prints it; nothing compares it). Keeping
it would mean continuing to record, as an adopter's primary evidence, a number that neither the
publisher's tooling nor the adopter's can independently re-derive.

**Rejected: anchor on the installed-payload digest.** `DR-10.md:120-127` already rejected this and the
objection stands unchanged: *"it has no external anchor — a stranger auditing the claim, on a machine
that is not the adopter's, has nothing to compare the recorded digest to except trusting the
adopter's own computation."* This record does not disturb that; `INSTALL.json`'s `files` map remains
Layer 2, useful for proving what landed *here* and not for identity.

**Rejected: sign the manifest, or adopt PEP 740 attestations.** These add *authenticity* — who
published this — on top of the *identity* this record settles. They are worth revisiting, and
`DR-10.md:164-169` already names PEP 740 as an open question. Rejected here because key custody and
a signing process are infrastructure, which `DR-12`'s permanent boundary forecloses, and because
solving identity and authenticity in one record would settle neither carefully.

**Rejected: retain `distribution_channel` as provenance metadata.** Tempting, since knowing how an
adopter installed is useful for support. Rejected because `DR-10` never claimed that purpose, and
retaining a required-shaped field on a justification invented after the fact is how schemas
accumulate. If provenance is wanted later it should be argued for on its own terms.

### What this contradicts in DR-10, stated precisely

`DR-10.md:158-163` rejects *"retiring the git-clone meaning of `framework_digest` in favour of a
single pip-shaped meaning"*, reasoning that *"a single field whose meaning depends on an
undisambiguated context is worse than two disambiguated meanings behind one new field"*.

That **rejection** stands — this record does not adopt a pip-shaped meaning. But its **reasoning
premise** does not survive: a channel-neutral anchor is neither of the two meanings and removes the
undisambiguated-context problem rather than managing it. The premise assumed the only options were
one context-dependent meaning or two labelled ones; a third option — one meaning that is the same in
every context — was not considered there. This record supersedes that reasoning and nothing else in
`DR-10`.

`DR-10`'s checker-vendoring commitment (`:42-48`) is untouched and must stay: `DR-11`'s remediation
soundness depends on it (`DR-11.md:141-152`), and manifest-anchoring is orthogonal to it.

## Impact

- Numerical/model output: none.
- Contracts/schemas: `schemas/application-profile.schema.yaml:59-62`'s `framework_digest`
  *description* changes; no pattern, type, or required-field change, and no new property. **This is a
  strictly smaller schema impact than `DR-10`'s**, which would have added `distribution_channel` and
  therefore hit the vendored-schema backward-compatibility problem `DR-10.md:177-193` documents at
  length. Dropping the field dissolves that problem rather than solving it.
- Security/data: improves the evidential value of an adoption claim for a third party. Does not
  change what any code verifies, because nothing verifies these fields today (`F7`).
- Reproducibility/lineage: this is the record's whole subject. The anchor becomes recomputable from
  source by anyone; the archive's non-reproducibility stops being load-bearing.
- Operations/release: `build_release.py` would need to print the manifest digest, and prose in
  `SETUP_GUIDE.md`, `README.md`, `templates/application-profile.yaml` and the two example profiles
  would need amending. None of that is done here.

## Limitations and follow-up

- **Decided, not implemented.** No schema, script, or documentation change is made here. The
  description change, the manifest-digest output in `build_release.py`, and the prose amendments are
  scoped to a later release.
- **`F6` remains open.** This record narrows it and explicitly does not close it. The three obstacles
  in "Does this close the anchoring gap" are the design problem any future attempt must solve.
- **`F7` remains open.** Nothing here makes anything verify `framework_digest`; it changes what the
  value should be, not whether it is checked.
- **The externality is weaker than a third-party registry, and this should be expected as an
  objection.** `MANIFEST.sha256` is a file in this repository's own published tree, not a record held
  by an independent party the way PyPI holds a per-file hash (`DR-10.md:128-142` praises exactly that
  property). Its externality is "anyone can fetch the public tree and recompute", which is real but
  is not third-party attestation.
- **The two digest schemes are still unreconciled**, as `DR-10.md:243-245` already recorded.
- Whether to also make the archive build reproducible is left open, now as an improvement rather
  than a prerequisite.

## Implementation, added 2026-08-31

This record stood as decided-not-implemented. It is now implemented, and the shape of the
implementation is worth stating because one part of the decision could not be carried out as
written.

**Done as decided.** `scripts/install_standard.py` computes `sha256(MANIFEST.sha256)` from the
source tree and records it in `.standards/INSTALL.json`. `scripts/check_conformance.py` compares
`adoption.framework_digest` against it (`SP049`) and `adoption.framework_version` against the
recorded `standard_version` (`SP048`). Both graceable, because this record *changes the meaning* of
a field already in use: every profile written under the previous definition carries an archive
digest and would fail on the day the check shipped. An obligation arriving without grace is one
nobody can adopt.

**A gap in the decision, found by implementing it.** `MANIFEST.sha256` is **not** part of the
install payload — `build_payload` never referenced it, and still does not. So an adopter cannot
recompute the anchor from their own repository; they can only compare against the value the
installer recorded for them. External verifiability, the half this record claimed to close,
therefore requires the adopter to hold or fetch the *published tree*, not merely their own. That is
still a genuine improvement over the archive digest, which nobody could recompute from anything.
But the claim in "Does this close the anchoring gap, or relocate it?" was written as though the
adopter's own checkout would suffice, and it does not.

Installing the manifest would fix that and was not done here: it widens the payload, and `DR-20`
has just settled payload membership against a stated principle. A file that lets an adopter
independently recompute their own pin has a strong case under that principle, and it is left as an
open question for whoever revisits `DR-20` rather than smuggled in alongside an implementation.

**`adoption.distribution_channel` needed no work.** As this record noted, it was never implemented
in any schema, script, test, template or example. Dropping it was already true.
