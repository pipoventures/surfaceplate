- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in

- Status: accepted — implemented in the same change that lands self-conformance (DR-13 item 0)
- Risk level: 2 — "output-affecting code, data, schema, or workflow", per the risk table in

## Decision

**Surfaceplate installs the standard into itself normally, and excludes `.standards/` from its own
release build.**

The publisher vendors the full set exactly as any adopter does — all 43 payload files — and passes
`check_conformance.py` by the same path as any adopter. `scripts/build_release.py` excludes
**everything the installer writes**, so the installed copies stay local and never enter
`MANIFEST.sha256` or the release archive.

**The exclusion is 43 files, not 27.** An earlier draft of this record said `.standards/` alone. That
was wrong, and the error is worth recording because it was the same shape of mistake this repository
keeps finding: 27 files land under `.standards/`, but a further **16 land outside it** — six
`.github/instructions/`, seven `.github/skills/*/SKILL.md`,
`.github/workflows/standards-conformance.yml`, and two `.githooks/` — each a byte-copy of content
under `standard/`. Excluding only `.standards/` would have left 16 duplicates in every manifest while
the record claimed the problem solved.

**The exclusion is derived, not restated.** `build_release.installed_paths()` calls
`install_standard.build_payload(ROOT)` and excludes exactly those target paths. A hardcoded list
would agree with the installer on the day it was written and silently stop agreeing afterwards —
precisely the defect `DR-6` recorded as F4 and `DR-9` as F5. `.standards` additionally remains in
`EXCLUDED_DIRS`, because `INSTALL.json` is *generated* by the installer and is therefore not a
payload entry that `build_payload` could report.

**Excluded by path, never by name.** `EXCLUDED_FILES` matches `rel.name` at any depth, so excluding
`standards-conformance.yml` by name would also drop
`standard/.github/workflows/standards-conformance.yml` — the source template adopters install *from*.
That would break every adopter in order to tidy the publisher's manifest. Verified after
implementation: all four `standard/` source templates, `scripts/check_conformance.py`, `core/`, and
this repository's own `standard-self-check.yml` remain in the payload.

**This is not a carve-out in the standard.** The exclusion lives in `scripts/build_release.py`,
which is the *publisher's release builder*. No adopter runs it — adopters install and check; they do
not build releases. The exclusion is therefore invisible in the standard, creates no exemption in
the conformance model, and grants this repository no relief from any control. It is a build
configuration in one repository declining to package a directory whose contents that repository
already ships from source.

## Context and alternatives

### Why the question arises at all

`DR-13` gates all further implementation on this repository conforming to what it publishes, and
already draws the distinction this record depends on — `DR-13:22-24`: *"Self-conformance, not
self-installation — a distinction that must be stated precisely, because the two are easy to
conflate and the code itself invites it."* `DR-13:65-73` names the mechanism as undecided and
already anticipates "installed into a separate working copy and merged back". `DR-10:109-118`
already recorded that the `target == source` guard is pure path equality and is walked around by a
differing `--source`, and already proposed a content-based replacement. None of that is restated
here as new.

What was *not* recorded anywhere — verified by exhaustive grep across `org/decisions/*`,
`CHANGELOG.md`, `README.md`, `INSTALL.md`, `org/RELEASE_PLAN.md`, `org/FINDINGS.md` and `audit/*` —
is the interaction between self-installation and the release payload. That is this record's first
contribution.

### The duplication finding

`scripts/build_release.py:21`:

```python
EXCLUDED_DIRS = {".git", "dist", "__pycache__", ".venv", ".ruff_cache", ".scratch", ".pytest_cache"}
```

`.standards` is not in it, and `payload_files()` (`:29-40`) is an unconditional `rglob("*")` filtered
only by that denylist. It demonstrably catches dotted paths: `.gitattributes` and
`.github/workflows/` are already manifest entries today.

So a self-install without this decision would place **43 files** that are **byte-identical** to
content this repository already ships from source — 27 under `.standards/` (copies of `core/`,
`schemas/`, `templates/`, `examples/`, `adapters/`, `scripts/check_conformance.py`, `VERSION`,
`standard/conformance-block.md`) and 16 outside it (copies of `standard/.github/instructions/`,
`standard/.github/skills/`, `standard/.github/workflows/standards-conformance.yml`,
`standard/.githooks/`) — and ship both copies of each. `MANIFEST.sha256` would carry every one of
those bytes twice, under two names, in every subsequent release.

It does not compound. `build_payload` (`install_standard.py:62-103`) reads canonical directories and
writes vendored ones, never the reverse, so an adopter installing from that archive gets
`adopter/.standards/` built from the canonical dirs and not `adopter/.standards/.standards/`. The
recursion terminates at depth 1. Duplication, not regress — stated precisely so the defect is not
overclaimed.

### Rejected: shrink the vendored set to what is mechanically read

Only three files under `.standards/` have a reader in the checker: `INSTALL.json`,
`schemas/application-profile.schema.yaml` (`check_conformance.py:40`, loaded by
`check_profile_schema`), and `check_conformance.py` itself as the entry point the hook
(`standard/.githooks/pre-commit:9`) and the installed workflow
(`standard/.github/workflows/standards-conformance.yml:33`) invoke by that exact path. A fourth,
`schemas/gate-exception.schema.yaml`, is read on the `--staged` path. The other ~23 have no reader.

Rejected, for two reasons.

**It would fix a publisher-specific problem by changing what every adopter receives.** The
duplication exists *here* because this repository already contains the canonical originals. In an
adopter's repository all 43 installed files are new content that is not otherwise present. There is
no duplication for adopters, so there is nothing to fix on their side.

**The ~23 unread files are not merely a convenience copy.** They are version-matched and
digest-protected, and `.standards/VERSION` travels with them (`install_standard.py:82`) with
`standard_version` recorded in the install record (`:358`). An adopter pinned at a given release
reading their vendored `core/CONFORMANCE_LEVELS.md` reads the rules they actually adopted. Pointing
them at published documentation would give them whatever is current, which moves — and this is
evidenced, not assumed: `core/PREREQUISITE_GATES.md` has five revisions across releases, including
`975a93b`, *"0.10.0: make the interface gates a conditional floor"*, a real change to a normative
rule. An adopter pinned before that, reading current docs, would be reading a rule they never
adopted. For a framework whose whole model is *pin a version and conform to it*, that is a
regression, not a cleanup. It also matters offline and in air-gapped environments.

The burden therefore sits on any future proposal to shrink the set, not on the status quo. See the
open question below.

### Rejected: hand-author a minimal `.standards/` containing only what is read

This would mean hand-authoring `.standards/INSTALL.json`, which is precisely the artefact whose
trustworthiness findings `F6` and `F7` concern. A hand-forged install record would make the
adversarial review's central claim true by demonstration, in the repository that exists to refute
it. Rejected outright, and recorded as a binding constraint on the implementation: the install
record is produced by the installer or it is not produced at all.

### Rejected: a self mode in the installer

Adding a `--self` flag that bypasses the `target == source` guard would be *implementation*, and
therefore circular under `DR-13`, which gates implementation on the very work this record enables.
It would be permissible only by amending `DR-13` to authorise it explicitly as part of item 0 —
a larger change than this needs, given that installing from a separate working copy already works:
the guard is pure path equality (`install_standard.py:424-426`) and does not fire when `--source`
names a different path, as `DR-10:109-118` already recorded.

## The two-checker-copies question

Vendoring `check_conformance.py` means this repository will hold **two copies** of the checker: the
live source at `scripts/check_conformance.py` and the frozen snapshot at
`.standards/check_conformance.py`. This is a live correctness question, not a tidiness one, and it
bites during ordinary development rather than at release time.

**Which copy executes.** Every automated route runs the *vendored* copy:

| Route | Path invoked | Copy |
|---|---|---|
| Local pre-commit hook (`standard/.githooks/pre-commit:9,17`) | `$repo_root/.standards/check_conformance.py` | vendored |
| Installed workflow (`standards-conformance.yml:33`) | `.standards/check_conformance.py` | vendored |
| This repository's own CI (`standard-self-check.yml`) | — | **neither** |

The hook and the installed workflow both hard-fail if the vendored file is absent; neither falls
back to `scripts/`. This repository's own CI invokes no checker against itself at all — a fact
`DR-13:87-90` already records.

**The staleness.** `check_integrity` digests `repo / rel` where `rel` is
`.standards/check_conformance.py` (`check_conformance.py:281-291`). `scripts/check_conformance.py`
is not a key in `files` and is never opened — the checker contains **zero** references to `scripts/`
across its 1882 lines. So editing the source leaves the vendored digest matching, and `SP004` and
`SP005` stay silent.

**The consequence, stated concretely.** Add a new finding to `scripts/check_conformance.py` that
this repository violates, do not reinstall, and the hook and installed workflow run the *old*
vendored checker, which cannot emit it. The self-check **passes**, while
`python scripts/check_conformance.py --repo .` would **fail**.

**Nothing surfaces it.** No `filecmp`, no diff, no digest comparison between the two copies exists
anywhere in the tree. `--verify-manifest` is the near miss and deserves precision: after
self-install both files are separate manifest entries, so editing the source *does* make the
manifest stale — but the remedy is to regenerate the manifest, after which it records two different
digests for two different files and passes. It detects *"the manifest is stale"*, never *"the two
copies differ"*, and by design cannot become a drift detector. It **masks** the divergence rather
than revealing it.

**Recorded as `F12` in `org/FINDINGS.md`.** The finding is not that two copies exist — that is
`DR-10:42-48`'s deliberate and well-reasoned design. It is that `DR-11:143-152`'s load-bearing
guarantee — *"the code that recorded a digest is guaranteed, by that same digest protection, to be
the code now checking it"* — is **scoped to the adopter boundary**, where exactly one copy exists and
there is no source tree. The publisher self-installed holds both. The guarantee still holds
pointwise, and that is exactly what makes the self-check answer questions about a checker that is no
longer the one under development. **`DR-11` treats the frozen snapshot as purely protective; in the
self-install case the same property becomes the staleness vector.** Neither `DR-10` nor `DR-11`
considers this case.

**Mitigation, decided here.** This repository's own CI runs
`python scripts/check_conformance.py --repo .` — the **source** copy — so the publisher's self-check
exercises the checker under development. The hook and the installed workflow continue to run the
vendored copy exactly as an adopter's would. Two routes, two purposes, stated rather than accidental.
This does not close `F12`: it means the publisher's CI notices what the hook alone would not, and
leaves the general source-vs-vendored drift unguarded for anyone else. `F12` stays open.

## Open question — NOT decided here

**Should the vendored set shrink from 27 files to what is mechanically read?**

This concerns the 27 files under `.standards/` only — the adopter's local reading copy. It does not
concern the 16 installed outside it (`.github/instructions/`, `.github/skills/`, the workflow, the
hooks), which an adopter genuinely needs at those exact paths for Copilot, Actions and Git to find
them, and which are not a reading copy of anything.

Both sides, stated fairly:

- *For:* only three files are read by code (four counting the `--staged` path). Twenty-three are
  shipped, digest-pinned, and consumed by nothing. That is real weight in every adopter's repository
  and in every integrity check.
- *Against:* they are read by *people*, at the version they pinned, offline, with the rules they
  actually adopted rather than whatever is current. The evidence above shows those rules do move
  between releases.

**The zero-adopter window is a reason to decide this soon, not a reason to decide it now, and not a
reason to decide it in a particular direction.** Changing the vendored set is free today
(`DR-7` establishes there are no adopters) and stops being free with the first one. It affects every
future adopter and deserves its own decision record with proper consideration. It must not be
answered as a side effect of a packet whose objective is getting the publisher conformant.

## Impact

- Numerical/model output: none.
- Contracts/schemas: none. No schema, template or example changes.
- Security/data: neutral. The vendored copy remains digest-protected in the adopter's repository
  exactly as before; excluding it from the *publisher's* archive removes nothing an adopter relies
  on, because an adopter's `.standards/` is generated by their own install, never unpacked from ours.
- Reproducibility/lineage: improves the release archive by keeping 43 redundant entries out of it
  that would otherwise be digested twice under two names. Under `DR-14`,
  `sha256(MANIFEST.sha256)` is the distribution anchor, so a manifest carrying duplicate content
  would have made that anchor larger and noisier for no gain.
- Operations/release: `scripts/build_release.py` gains one entry in `EXCLUDED_DIRS`. The self-check
  is added to `standard-self-check.yml`.

## Limitations and follow-up

- **`F12` is recorded, not fixed.** The CI mitigation means the publisher's own CI notices
  source-vs-vendored divergence; nothing guards it generally, and nothing guards it for an adopter
  who edits their vendored checker's *source* — which they do not have. Whether that matters outside
  this repository is not established here.
- **The vendored-set question is open**, above.
- **The self-install guard remains path-based.** `DR-10:109-118` proposed a content-based
  replacement; this record relies on the path-based behaviour rather than fixing it, and installing
  from a separate working copy is precisely the gap `DR-10` recorded. That is a deliberate use of a
  known weakness, and it is stated rather than quietly relied upon.
- **`hook_configuration_conflict` blocks installation on the maintainer's machine** because global
  `core.hooksPath` is set. That is environmental, blocks installing into *any* repository there, and
  is not a self-install control. It is handled per-invocation, never by changing global config.
