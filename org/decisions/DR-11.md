## Decision

Extend the mechanism this repository already has for a partially-generated file — the Copilot
marked block — into a general one, rather than inventing something new for AGENTS.md or any other
future per-agent file.

Generalise the scalar `conformance_block_digest` field in `.standards/INSTALL.json` into:

```
generated_files: {
  "<relative-path>": {"digest": "<sha256hex>", "markers": ["<begin>", "<end>"] | null}
}
```

`markers: null` for a fully-generated file (the AGENTS.md shape — the whole file is standard
content); non-null `[begin, end]` for a marked-region splice into an otherwise adopter-owned file
(the Copilot shape, unchanged in behaviour, just renamed into the general structure). This is a
clean-cut migration, not a dual-emission: zero adopters exist (`DR-7`), so there is no cost to
retiring the scalar field outright, the same reasoning `DR-8` used for `SDS`→`SP`.

**A declared generated file always has a recorded digest — this is closed, not inherited as a
gap.** Today, `check_conformance_block`'s `if expected and sha256_text(...) != expected` silently
skips the comparison when `conformance_block_digest` is absent from the record — and the same gap
exists, separately, in the staged twin (`check_staged_integrity`, `check_conformance.py:952`,
`if expected_block and ...`). Both must close together under the new mechanism: an entry present in
`generated_files` with no digest, in either the working-tree record or the staged one, is itself a
finding — not a silent no-op.

**An adopter with no agent still declares the key, empty, not absent.** `generated_files: {}` is
written by the installer even when nothing is generated, the same way `files` and
`executable_files` are always present. Absence of the key is deliberately never treated as "nothing
to check" — see "Limitations" for why this distinction is load-bearing rather than cosmetic.

**New finding codes, not reused ones.** `SP044` (a declared generated file is missing) and `SP045`
(a declared generated file no longer matches its recorded digest) — the next free codes after
`SP043`, following `DR-8`'s convention of checking the tree first (confirmed by grep: neither string
exists anywhere today). Each carries its own title and remediation text distinct from `SP004`/`SP005`
— see "Context and alternatives" for why reuse was rejected. `check_integrity` is extended to walk
`generated_files` in addition to `files`, using the marker-extraction logic (`markers` non-null) or
a whole-file digest (`markers: null`) as appropriate, but reports through the new codes.

**How the check is made to fail, and how that is tested.** After install, modify a generated file's
on-disk content (or, for a marked-region file, the content inside the markers). The digest
recomputed from the current content will not match the recorded one; the extended `check_integrity`
raises `SP045`, non-graceable. Tested by extending the existing `tests/test_install_and_check.py`
"tamper evidence" block, which already runs three parallel cases — a fixed skill file (`SP005`), a
fixed instruction file (`SP004`), the Copilot block (`SP008`) — with a fourth: modify a generated
file, assert `SP045` and "never graced" in the output, exactly as the three existing cases already
assert for their own codes.

**Determinism is a requirement of this decision, not an implementation detail left open.** Any
future generator must be a pure function of {declared agent set, the standard's own generation
rule/version} — no adopter-specific free text as input — so that re-running it reproduces
byte-identical output. This is required for two independent reasons: the existing
"second install changes nothing" idempotency assertion (`tests/test_install_and_check.py:223-226`)
already depends on it for every payload file, and the once-recorded-digest approach this decision
adopts is only valid evidence if regenerating from the same inputs is guaranteed to reproduce the
same bytes.

## Context and alternatives

**The constraints, restated:** tampering with an installed control must still fail — non-negotiable.
The check must be able to fail, and that must be demonstrated. It must work for an adopter running
no agent at all.

**What the code does today, established by reading it.** The only generated or partially-generated
artefact in the system today is `.github/copilot-instructions.md`'s marked region. Its generator,
`upsert_conformance_block` (`install_standard.py:216-245`), is a splice, not a true generator: its
only input is one static file, `standard/conformance-block.md`, read verbatim
(`install_standard.py:333`) — identical for every adopter. `build_payload`
(`install_standard.py:62-103`) maps every payload entry to a source **file**; there is no code path
that synthesises content today, and no `AGENTS.md` or per-agent generator exists anywhere (confirmed
by exhaustive grep for `AGENTS`, `per-agent`, and related terms — zero hits). `check_conformance_block`
(`check_conformance.py:335-375`) is a three-stage check — file existence (`SP006`), marker presence
(`SP007`), then digest of the extracted region only (`SP008`) — proven by an existing test,
"altered conformance block fails" → `SP008` (`tests/test_install_and_check.py:245`). The Copilot
file itself is excluded from `files` (never added to `payload`); it is represented solely by the
scalar digest. This three-way split — fixed payload / marked-region splice / adopter-owned content —
is the precedent this decision generalises rather than replaces.

**Rejected: digest the generator's inputs and the generation rule, not the emitted bytes.** This
does not verify the file on disk at all without re-running the generator at check time to produce
something to compare against — which collapses back into digesting emitted bytes anyway, just one
step later and with more moving parts. It also cannot detect tampering of the artefact itself
without that re-run, so it does not meaningfully differ from the rejected regenerate-and-compare
alternative below; naming it separately here because the work packet listed it as its own option.

**Rejected: treat generated files as adopter-owned, outside the integrity boundary.** Kills the
"tampering must still fail" constraint in one line: a generated file still carries a control — the
same rules, re-rendered for a different agent — and excluding it from the boundary means that
control can be silently stripped with nothing to catch it. This is precisely the defect shape this
repository has spent several releases hardening against (`DR-8`'s `graceable=False` posture,
`check_integrity`'s existing `SP004`/`SP005`). Rejected outright, not weighed.

**Rejected, and worth stating why given this decision's own determinism requirement makes it
tempting: regenerate-and-compare instead of a recorded digest.** Once the generator is guaranteed
deterministic (which this decision requires anyway), re-running it at check time and diffing the
result IS a viable design, and it has one real advantage the recorded-digest approach does not:
it would also catch *staleness* — a generator upgraded since install, whose emitted content should
now differ, but whose file on disk still matches the digest recorded at the older install time.
Rejected anyway, for reasons independent of that trade-off: it requires the full generation logic to
be an ambient, correctly-version-matched dependency of the checker at check time, not a frozen fact
recorded once — the same "ambient dependency on a mechanism it does not own" shape `DR-1` already
rejected for hook-chaining. It also risks false positives where generation legitimately depends on
adopter state that has since changed for unrelated, proper reasons. The staleness detection it would
buy is real and is named honestly as a capability this decision's chosen mechanism does not have —
not hidden, just outweighed by the hermeticity cost.

**Rejected: reuse `SP004`/`SP005` rather than allocate new codes.** Considered, because "missing"
and "modified" are the same defect shape regardless of why the expected digest existed. Rejected on
inspection for four concrete reasons, not aesthetics: both codes' titles say "standard-owned files",
which is false for content that is legitimately adopter-variant by design — the same "a claim that
doesn't match what it describes" defect class `DR-7`/`DR-8` exist to punish, just aimed at a finding
title instead of a document. `SP005`'s remediation text — "raise it against the standard so every
repository gets it" — is meaningless for a file that is *supposed* to differ per adopter; remediation
text is part of the emitted contract a reader relies on, not incidental commentary. `check_integrity`
emits one joined finding per code with all offending paths in a single detail string
(`check_conformance.py:293-315`), so a generated-file drift and a fixed-file tamper would be
indistinguishable in the same report. And it would make the "the check must be able to fail, and
that must be tested" constraint only nominally satisfiable: a test asserting `"SP005" in
result.stdout` (the existing pattern, `tests/test_install_and_check.py:231`) would pass whether the
fixture actually exercised the generated-file path or accidentally tripped the fixed-file one —
the greppability `DR-8` treats as the entire value of a finding code would be lost exactly where a
reviewer would want it most.

## The cross-record interaction (reasoned together with DR-10, not decided in isolation)

**The load-bearing one: the checker travels vendored inside `files`, and this decision's
remediation text depends on that continuing.** `install_standard.py:81` copies
`scripts/check_conformance.py` into the adopter's own `.standards/check_conformance.py`, and that
copy is itself one of the paths in `files`, digest-protected like every other fixed payload file.
The practical effect: the code that recorded a digest is guaranteed, by that same digest protection,
to be the code now checking it. That guarantee is what makes this decision's remediation instruction
— "re-run the installer to restore a generated file" — actually sound: re-running restores the
*original* generator, producing the *original* bytes, because the generator itself cannot have
drifted without `check_integrity` already having flagged `check_conformance.py`'s own tampering
first.

**This guarantee is free for `files` and load-bearing for `generated_files`, for different reasons.**
A fixed payload file's correct bytes are always recoverable from the pinned source regardless of
which checker is currently asking — a stranger could recompute them independently. A generated
file's correct bytes exist **nowhere except what the original, correctly-versioned generator would
produce** — there is no independent restore source. If the vendored-checker guarantee ever broke
(an ambient console-script checker resolved fresh from whatever `pip install -U surfaceplate`
happens to have most recently installed, rather than a frozen per-adopter snapshot), "re-run the
installer to restore it" would stop being sound advice for `generated_files` specifically: the
installer being re-run might itself already be a newer version than what originally generated the
file, and would then produce *different*, not restored, bytes — a repair that silently changes the
file rather than fixing it.

**This is exactly why `DR-10` decides, explicitly, that the checker continues to be vendored under
pip distribution rather than becoming an ambient console script.** That decision is not incidental
plumbing; it is the precondition this record's remediation text relies on. Stated in both records
rather than assumed silently in either, per the work packet's instruction to reason about them
together.

**The secondary interaction:** `files` and `generated_files` must stay separate keys, because
`generated_files` entries are legitimately adopter-variant while `files` entries are adopter-invariant
across every adopter of the same version. This is what keeps `DR-10`'s Layer 2 usable as
cross-adopter-comparable installed-payload evidence at all. The incompatible combination this
guards against: if a future decision ever revisited `DR-10`'s Layer 1 and chose "aggregate local
payload digest" (rejected there) without this record's fixed/generated split existing first, that
aggregate would be contaminated by adopter-variant content and would stop being comparable across
adopters — the split is a precondition for that rejected-but-nameable Layer-1 alternative ever being
viable, not merely a nice-to-have.

## Impact

- Numerical/model output: none.
- Contracts/schemas: `.standards/INSTALL.json`'s record shape changes (`conformance_block_digest`
  retired, `generated_files` added) — an internal, machine-managed file, not a schema this
  repository publishes for adopters to author against, so no `application-profile.schema.yaml`
  change follows from this record.
- Security/data: directly affects whether a generated file can be tampered with undetected. Today
  it can be, trivially, because no such file exists to protect; this decision states the boundary
  before the first one ships, rather than discovering the gap after.
- Reproducibility/lineage: the determinism requirement is itself a reproducibility commitment —
  stated explicitly so a future generator design cannot quietly violate it and only be caught later
  by a failing idempotency test with a confusing cause.
- Operations/release: no adopter-facing change yet, and no adopter exists to be affected (`DR-7`).
  Two new finding codes are reserved (`SP044`, `SP045`) but emit nothing until a generator exists.

## Limitations and follow-up

- **Decided, not implemented.** No installer change, no checker change has been made. Implementation
  is scoped to whichever release first ships a per-agent generator.
- **`.standards/INSTALL.json` itself is not tamper-protected as a whole.** `check_staged_integrity`
  asserts the staged record equals the working-tree record, which catches a *partial* edit, but
  nothing stops a coordinated edit of both a generated file and its own recorded digest together.
  This is not a new weakness this decision introduces — `files` already carries the identical
  exposure today, unaddressed — but it is sharper for `generated_files`, because (per the
  cross-record interaction above) there is no independent restore source for generated content the
  way there is for fixed payload. Recorded as a bound on the whole mechanism, not solved here.
- The staged counterpart (`check_staged_integrity`) needs the same `generated_files` extension and
  the same required-once-declared fix as the working-tree checker — stated as a requirement in the
  Decision above, but its exact staged-index implementation is not designed in this record, to keep
  scope proportionate to what the packet asked for.
- `generated_files: {}` being always-present rather than sometimes-absent is a small design choice
  with a real reason (see Decision) — worth flagging so a future implementer does not "simplify" it
  back to an optional key.
- See "The cross-record interaction" above for the dependency this decision has on `DR-10`'s
  checker-vendoring commitment, and the combination of the two decisions that would not be sound.
