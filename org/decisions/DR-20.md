# Decision Record

- Decision ID: DR-20
- Date: 2026-08-31
- Application: Surfaceplate (the framework itself).
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change.
- Risk level: 2 — it settles what every adopting repository receives, and adds a control.
- Related work items: `ACT-002` (the vendored set) and `ACT-003` (`F12`), both raised by `DR-16`.

## Decision

**Keep the vendored set whole. Govern its membership by a stated principle. Separate the
review surface. Detect drift.**

Four parts, landing together:

1. **The set is not shrunk.** All 27 files continue to install into an adopting repository.
2. **Membership follows a principle**, stated below, so future additions are decided rather
   than accreted.
3. **The installer reports what changed by review class** — enforcing, contract, reference —
   so an upgrade can be reviewed in proportion to what it can actually break.
4. **`tests/check_vendored_current.py`** fails if this repository's vendored copy has drifted
   from source. This closes `ACT-003` and moves `F12` from mitigated to detected.

## Context and alternatives

### A correction to `ACT-002`'s own framing

The activity asked whether the set should "shrink to what is mechanically read". That question
contains a false premise, and answering it as asked would have produced the wrong decision.

`check_integrity` digests **every** file listed in `INSTALL.json.files`
(`scripts/check_conformance.py`), so all 27 are mechanically read. What is limited to four is
files whose *content is interpreted*: `INSTALL.json`, `check_conformance.py`,
`schemas/application-profile.schema.yaml`, and `schemas/gate-exception.schema.yaml`.

So shrinking would not remove unused files. It would remove **23 files from integrity
protection** — a different act with a different cost.

### Why keeping is correct, on evidence rather than preference

- **Conformance is version-scoped, and the rules move.** "This repository conforms to 0.14.0"
  means nothing unless 0.14.0's rules can be retrieved. `core/PREREQUISITE_GATES.md` has **seven
  revisions**, one of them normative — at 0.10.0 the interface gates became a conditional floor.
  An adopter pinned at 0.9.x who reads the published documentation instead of their vendored copy
  gets **a rule they never adopted**. That is a correctness property, not a convenience.
- **Tamper-detection extends to the documents.** A human reading a modified
  `core/CONTROL_PRINCIPLES.md` follows the wrong rules, and nothing would say so. Files outside
  `INSTALL.json` are not protected.
- **Offline availability.** An adopter without network access — or with a corporate proxy in the
  way — still needs the rules they are being held to.
- **The footprint argument does not survive measurement.** 264K across 28 files.

### The real cost of keeping, and what is done about it

Footprint is not the objection. The objection is the **review surface**: on every upgrade the
adopter sees a 27-file diff, mostly prose they will not read. That trains a reviewer to wave
installer diffs through — and the same diff carries `check_conformance.py`. Rubber-stamping the
documentation means rubber-stamping the executable.

That is a genuine long-term quality risk and it argues for changing the *presentation*, not the
contents. The installer now reports:

```
What changed, by review class:
    1  enforcing  (code that runs - review this closely)
    2  contract   (parsed by the checker - changes what validates)
    6  reference  (read by people - changes what the rules say)
```

and states explicitly when nothing that executes or validates changed. The classification is
**derived** from `check_conformance`'s own path constants rather than restated, so the installer
cannot come to disagree with the checker about which schemas are parsed (`DR-6`).

**A guard was written for this and removed, and the reason is worth recording.** The first version
asserted that the installer's `contract` class equalled the checker's constants. It cannot fail:
`classify()` derives from those same constants, so mutating the checker moves the expected and
actual values identically. It was verified to pass under exactly that mutation before being
removed. Derivation is what removes the drift; a test that both sides then agree is a tautology,
and a tautology that reads as a control is worse than no control — it is the defect shape this
register has now recorded five times, written by hand while documenting the fix for another
instance of it. What replaced it is falsifiable and covers a bug the derivation does *not* prevent:
every schema the checker parses must actually be shipped, or an adopter installs a checker that
cannot find its own schema.

### The membership principle

A file belongs in the payload when an adopting repository cannot correctly apply, verify, or
understand the version it pinned without it. Concretely, one of:

1. **Enforcing** — it executes: the checker, the hook, the installed workflow.
2. **Contract** — the checker parses it: the profile and exception schemas.
3. **Reference** — a human must read it *at the pinned version* to know what they adopted, or
   must author a document against it: the normative documents, templates, examples, adapters,
   the remaining schemas, agent instructions and skills.

A file that fails all three does not belong. Adding one is a decision recorded here, not an
edit to `build_payload`.

Note that the four schemas the checker never references — `assurance-evidence`,
`method-registry-entry`, `method-run-lineage`, `override-record` — qualify under (3) and are not
dead weight. They are the contracts an adopter at `full` authors records against, and `SP004`'s
remedy tells an adopter in as many words to "record an approved override".

### Alternatives rejected

- **Shrink to the four interpreted files.** Rejected on the three properties above. It optimises
  a cost nobody has incurred against correctness properties that are load-bearing.
- **Split, with documentation behind an installer flag.** Rejected: the default becomes reality
  for most adopters, so it is shrinking with extra steps — plus a second code path to test, and
  an adopter who declines reaches the same failure by choice rather than by decision.
- **Keep, and change nothing.** Rejected: it leaves the review-surface risk unaddressed, and
  leaves membership determined by whatever `build_payload` happens to copy.
- **Trim the adapters to the adopter's declared stack.** Rejected as disproportionate: three small
  files, against installer complexity and a new failure mode when the declaration is absent or
  wrong.

### What could reopen this, and why it is not left open

Item 1 of `org/RELEASE_PLAN.md` makes the payload package data under a wheel install. That changes
where reference files *can* live — a package directory is version-matched and offline by
construction — and so it may change the right answer for part (1) of this decision without
touching parts (2)–(4). This is recorded as an **input to item 1**, not as an open activity:
`ACT-002` closes, and item 1's decision record must state what it does to the payload rather
than changing it silently.

### `ACT-003`: why a new check, and why the existing ones do not cover it

`F12` was mitigated by having CI run the source checker. That leaves the divergence undetected —
it only ensures one route exercises current code.

Neither existing control detects drift, and each looks as though it might:

- **The integrity check (`SP004`/`SP005`)** digests `.standards/<file>` against
  `.standards/INSTALL.json`. Both sides were written by the same install, so editing source
  afterwards leaves the vendored digest matching its vendored file perfectly. It answers *has the
  installed copy been tampered with*, never *is the installed copy current*.
- **`build_release.py --verify-manifest`** is the near miss. Editing source does make the manifest
  stale, but the remedy is to regenerate it, after which it records two different digests for two
  files and passes. It detects *manifest stale*, never *the copies differ*, and by design cannot
  become a drift detector. It **masks** the divergence.

`tests/check_vendored_current.py` compares each payload path's source against its installed copy,
deriving the set from `install_standard.build_payload` rather than restating it. It is
publisher-only by nature: an adopter holds one copy and has no source tree to compare against.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** unchanged. No `SP0xx` code added — this is a repository test, not a
  conformance finding, because an adopting repository cannot violate it.
- **Security/data:** none.
- **Reproducibility/lineage:** improved. The condition that made a self-check answer questions
  about a checker no longer under development is now detected rather than reasoned about.
- **Operations/release:** an upgrade diff is now reviewable in proportion to what it can break.
  `install_standard.py` gains an import of `check_conformance`; both ship in the same archive and
  the checker has no module-level dependency beyond the standard library.

## Evidence

- **The split, measured**: 4 interpreted, 27 integrity-protected, 264K total.
- **The rules move**: `core/PREREQUISITE_GATES.md`, 7 revisions on `main`, one normative.
- **Classification, verified** against each class: the checker, hook and workflow classify as
  `enforcing`; the two parsed schemas as `contract`; `core/CONTROL_PRINCIPLES.md` and
  `schemas/override-record.schema.yaml` as `reference`.
- **The classification guard, seen to fail** — misclassifying the checker as `reference` fails
  `validate_contracts.py`; pointing the checker at an unshipped schema fails it too. The
  tautological first version is described above and is not counted as evidence, because it never
  could have been.
- **The drift check, seen to fail three ways**: editing `scripts/check_conformance.py` reports
  `[enforcing] .standards/check_conformance.py <-- this is the checker itself`; editing
  `core/CONTROL_PRINCIPLES.md` reports `[reference]`; deleting `INSTALL.json` fails with a
  message saying self-conformance is gone rather than that there is nothing to compare.
- **It was not written speculatively.** The exact condition occurred twice on 2026-08-31 while
  implementing `DR-18`: `schemas/application-profile.schema.yaml` was edited and the checker
  rejected the new field as unknown, because it was parsing the stale vendored schema. Nothing
  reported drift; the symptom was a confusing `SP016`.

## Limitations and follow-up

- **The drift check is publisher-only and is not part of the standard.** An adopter with a stale
  vendored copy relative to a newer published release is a different problem — that is what
  `adoption.review_by` and `framework_version` are for, and `F7` records that the digest anchor is
  checked against nothing.
- **Classification is a three-way split of a spectrum.** `.github/instructions/*` shape agent
  behaviour and are classed `reference`; that is defensible but not obviously the only reading.
- **The report helps a reviewer who reads it.** It cannot make anyone read a diff, and this
  framework does not claim to — `core/CONTROL_PRINCIPLES.md` principle 9 places that beyond what a
  tool may assert.
- **Membership is governed by a principle, not by a check.** Nothing mechanically rejects a payload
  addition that fails all three tests. Whether that warrants a check is not decided here.
