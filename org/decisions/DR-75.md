- Date: 2026-09-09
- Application: Surfaceplate (the framework itself) — whether an adopter can complete a shipped
  template, and whether they can leave.
- Decision owner: Mario Pipo (maintainer), who directed that the two adoption-facing findings of
  the pathway sweep's held set be resolved before 1.0. Drafted by the agent under `ACT-081`;
  confirmed by merging.
- Status: accepted — implemented by `ACT-081`.
- Risk level: 2 — one change makes the checker accept input it previously rejected; the other adds
  a command that deletes files, gated by the install record.
- Related work item: `ACT-081`; **closes `F137`, `F138`**; adjudicates `PW-09` and `PW-13`'s

## Decision

1. **Dates in hand-written records are normalised on load.** `rules.dates_as_strings` converts
   `date`/`datetime`/`time` to ISO 8601 text at all four points where `check_conformance.py`
   parses a hand-written YAML record.
2. **`surfaceplate uninstall` exists**, with `--target` and `--dry-run`. It removes what
   `.standards/INSTALL.json` records that the installer wrote, and nothing else.

## Context and alternatives

**`F137`.** The gate-exception template says `raised_on: replace-me  # YYYY-MM-DD`, and doing
exactly that produces a YAML date object, which every schema here rejects as `not of type 'string'`.
The template warns about quoting a **SHA** and not about quoting a **date** — the case was thought
about once and not generalised. Adjudicating it here found the same trap on `adoption_date` in the
application-profile template, which is the path of an adopter filling the profile **by hand**, the
documented alternative to the wizard.

**Rejected: quote the placeholders in the templates.** It works, and it relies on the adopter
reading a comment. A normaliser does not. Nothing is lost by normalising: a `datetime.date` can
only have come from a date-shaped scalar, and `.isoformat()` is the value `format: date` wanted.
The `commits:` quoting warning stays, because an all-digit SHA prefix parsing as a number is a
different defect that this does not fix.

**`F138`.** There was no removal path at all — no command, no flag, no document. Established rather
than assumed: the search that found nothing did find the installer's own *"remove … (no longer part
of the standard)"* line, so it could have found a removal path had one existed.

**Rejected: document a manual procedure.** Every installed file is integrity-checked, so an adopter
deleting them by hand fails their own conformance check on the way out; and a hand-written list
goes stale the moment the payload changes. **The installer already records what it wrote**, so an
exact removal was cheaper than a procedure and cannot drift.

**Why the record and not `build_payload()`.** Removal reads `INSTALL.json`, so it takes out exactly
what was installed — including files a newer payload no longer ships, and excluding anything the
adopter added since. Deriving the list from the current payload would delete by guess.

## Impact

- `rules.py` gains `dates_as_strings`; four load sites in `check_conformance.py` call it. Strictly
  a relaxation: input that used to fail now succeeds, and nothing that used to pass now fails.
- `install_standard.uninstall` and a `surfaceplate uninstall` subcommand. Exit `2` for "not
  installed", matching `check`, so a wrapper can tell that from a failure.
- `INSTALL.md` and `SUPPORT.md` say how to leave. That is the half `PW-13` was actually about.
- **Never removed, and each stated in the output:** the adopter's content outside the managed
  blocks; `governance/application-profile.yaml`; anything not in the record. `core.hooksPath` is
  unset only where it points at `.githooks`.

## Evidence

- `F137` reproduced before the fix — `raised_on: datetime.date(2026, 9, 9) is not of type 'string'`
  — and the profile's `adoption_date` shown to share it. After: both validate.
- `F138`, 17 checks in `tests/test_install_and_check.py`: every recorded file gone and `.standards/`
  with it; the adopter's source, manifest, profile and their own words in `AGENTS.md` intact; the
  checker then reports not-installed with exit 2; removing what is not there is exit 2 rather than
  an error; the standard installs again afterwards. A dry run writes nothing and says so.

## Limitations and follow-up

**A file edited since install is removed, not preserved.** It is standard-owned by contract, and
leaving it would leave the repository half-uninstalled. It is **named in the report** so anything of
the adopter's that ended up inside it can be recovered from git — detection, not prevention, as
everywhere else here.

**Removal does not undo an adopter's own commits.** It removes files from the working tree; the
history of having adopted remains, as it should.

**`PW-13`'s other half is still open** in `F136`: `RECONCILIATION.md` cannot be followed literally
by an adopter who installed from pip, because its paths assume a clone.
