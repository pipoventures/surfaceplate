# Decision Record

- Decision ID: DR-25
- Date: 2026-08-31
- Application: Surfaceplate (the framework itself).
- Decision owner: Mario Pipo (maintainer).
- Status: accepted — architecture only; no validator is implemented by this record.
- Risk level: 2 — it fixes the shape every control validator must follow, and changes what a
  conformance result reports.
- Related work item: `ACT-010`. Raised by `F20`.

## Decision

**Controls become provable through four patterns, and `implementation_reference` is where an
adopter says how.**

| Pattern | What is proven | Controls | Mechanism |
|---|---|---|---|
| **A — declared artefact** | The named file exists, is not blank, is not a template, is tracked | `dependency_lock`, `assurance_findings` | `SP032`'s existing artefact logic |
| **B — declared CI check** | The named status check exists, is required, and **can fail** | `deterministic_tests`, `contract_tests` | `SP046`/`SP047`'s existing logic |
| **C — declared records** | Records validate against the schema this framework already ships, and are tracked | `overrides`, `method_registry`, `run_lineage`, `provenance` | New |
| **D — already a gate** | Checked today | `documentation_authority` | `authority_map` |

**`implementation_reference`** — an optional string already present on every `control_decisions`
entry and used by nothing — becomes the adopter's statement of *where the control lives*: a path for
pattern A, **a CI step name** for B, a directory for C.

> **Amended 2026-08-31 (`ACT-012`), in place rather than footnoted.** This originally read *"a
> status-check name for B"*. Implementation showed step granularity is correct, and this record
> states that a pattern which does not fit means the record is wrong — so it is corrected here.
>
> A status check is a **job**. In this repository one job runs every suite, so `deterministic_tests`
> and `contract_tests` would both have named it and been given an identical check, losing the
> distinction between them entirely. A step is specific: *Validate the control contracts* is the
> contract tests and nothing else.
>
> Whether a job is a *required* status check also lives in forge settings rather than the
> repository. Reading it would make the checker forge-aware, which `DR-12` forbids.

> **Amended again 2026-08-31 (`ACT-014`), in place, on two points pattern C's implementation
> disproved.** This record said the first validator built is the real test and that a pattern which
> does not fit means the record is wrong. Both of these are that.
>
> **Currency is not provable, and the table above no longer claims it.** Pattern C originally read
> *"are current, and reference what they describe"*. None of the three record schemas carries an
> expiry or a review date; `method-registry-entry` has `revalidation_trigger`, but it is a free-text
> condition rather than a deadline. There is nothing declared to check against — the same shape as
> the gate exceptions `F22` left open, found again one packet later in a different contract.
>
> *"Reference what they describe"* is separated out rather than dropped: cross-references are
> checkable, and are `C2`'s work rather than `C1`'s.
>
> **`provenance` and `run_lineage` would have collapsed into one control.** This record correctly
> establishes that one *record type* serves both. It does not follow that one *check* serves both,
> and if it did, declaring `provenance` would have precisely the same effect as declaring
> `run_lineage` and `full` would list two controls where one does the work. They are separated by
> which optional fields each obliges on a completed run — `provenance` the traceability pair,
> `run_lineage` the reproducibility set — using the schema exactly as published. `C2` implements it.

**Nothing is implemented here.** This record fixes the shape. Four packets follow it, each agreed
separately.

## Context and alternatives

### The finding this answers

`F20`. Claiming a conformance level proves nothing about the controls it demands. `SP021`/`SP022`
verify only that a control appears in `control_decisions` and reads `required`. Nothing asks whether
the thing exists.

Demonstrated rather than argued: this repository was made to claim `full` and declare `provenance`,
`run_lineage`, `method_registry` and `overrides` while containing no such records. **The checker
raised zero objections about them.** Every finding it produced concerned *gates*.

The asymmetry is exact and worth stating in those terms: **a gate is checked against reality; a
control is checked against itself.** And it is uniform — `dependency_lock` at `essential` is as
unverified as `provenance` at `full`.

### Why not remove the unverified controls instead

The reviewed sequence originally proposed stripping the unverified controls out of `full` until each
was checked — honest, immediate, and consistent with how this project has handled every prior
self-caught overclaim.

Rejected, on two grounds.

**It cuts on an accident.** `provenance` has no schema of its own, so a rule of "remove the ones
with unvalidated schemas" would have kept `provenance` and removed its four neighbours — a boundary
drawn by which files happen to exist rather than by any principle. Applied consistently it removes
all five, and `full` becomes `standard` plus nothing.

**It discards the destination to avoid describing the journey.** The controls name real obligations.
The defect is not that they are demanded; it is that a reader may infer they are verified. That is
fixable by saying which are checked — done in this packet — while the verification is built.

### What cannot be proven, and why the documents must say so

A tool can establish that a record **exists, is well-formed, is current, and is linked** to what it
describes. It cannot establish that the record is **true**. It can check that a run-lineage record
was written for run 412; it cannot check that run 412 happened that way.

This is not a limitation to be engineered away later. It is the same boundary
`core/CONTROL_PRINCIPLES.md` principle 9 already draws, and the same one that stopped `SP046` from
claiming a repository has no secrets. Every pattern below proves the shape of a record and never its
honesty, and the level tables will say so.

### Why no new schema is needed

`provenance` — *"a material result must be traceable to its inputs"* — appears at first to need its
own record type, and writing one would have been the largest and least evidenced part of this work.

It does not. `schemas/method-run-lineage.schema.yaml` already requires `input_references`
(`minItems: 1`) and `input_hash`, alongside `output_hash`, `implementation_revision` and
`configuration_hash`. Traceability to inputs is already a mandatory property of that record.

So `provenance` and `run_lineage` are **two properties of one record type**, not two record types:
provenance is its traceability, run lineage its reproducibility. One validator serves both, and no
contract is designed speculatively.

### Why `implementation_reference` rather than a new field

It already exists, in the schema, on every control entry, with no consumer. Adding a parallel field
would leave two places to say the same thing and no rule about which wins — the contradictory
authority defect this framework names more often than any other.

Its current type is a free string, which is deliberately kept. Different patterns need different
referents — a path, a status-check name, a directory — and constraining the shape per control would
put stack-specific knowledge into the schema, which `DR-12`'s neutrality forbids. The **checker**
interprets it according to the control's pattern; the schema stays a string.

### Alternatives rejected

- **Run the adopter's checks and judge the result.** Rejected: it makes the framework stack-aware,
  requires executing arbitrary commands from a profile, and is the tool judging rather than
  recording — the line the reviewed scope drew when deferring per-change risk classification.
- **Require `implementation_reference` in the schema.** Rejected: a schema violation cannot be
  graced, so it would fail every existing profile the day it shipped. Optional in the schema,
  required by the checker, graceably — the same asymmetry `DR-18` chose for `scanner`, for the same
  reason.
- **One monolithic packet.** Rejected: eight validators landing together would be reviewed as one
  diff, and a wrong pattern would be replicated eight times before anyone noticed.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none in this record. Later packets add no schema; they consume the four
  that exist.
- **Security/data:** the checker will read files an adopter names. It validates shape and never
  interprets content as instruction.
- **Operations/release:** what `full` costs an adopter changes materially. Today it is nine lines of
  YAML. Afterwards it is producing override records, a method registry and run-lineage records in a
  defined shape and keeping them current — or failing the build. That is the intent, and it is a
  real burden that should be stated in the levels documentation rather than discovered.

## Evidence

- The demonstration above, run against this repository: `full` claimed, four controls declared, no
  records present, **no finding raised about any of them**.
- `implementation_reference` confirmed present in `schemas/application-profile.schema.yaml` and
  referenced by nothing in `scripts/`, `tests/` or `examples/`.
- `method-run-lineage.schema.yaml` confirmed to require `input_references` and `input_hash`, which
  is what makes a separate provenance schema unnecessary.
- Patterns A, B and D confirmed already implemented — `SP032`, `SP046`/`SP047` and the
  `authority_map` gate respectively. Only pattern C is new work.

## Limitations and follow-up

- **This record proves nothing by itself.** It fixes a shape. The honesty gap is closed in the same
  packet by stating which controls are checked; the verification arrives across four later packets.
- **The patterns are asserted to fit, not demonstrated to.** A, B and D are reused from working
  code, which is good evidence but not proof they suit these controls. The first validator built is
  the real test, and if it does not fit, this record is wrong and should be amended rather than
  worked around.
- **Surfaceplate must satisfy its own controls under these patterns.** It sits at `standard`, so it
  will have to produce genuine references for `dependency_lock`, `deterministic_tests`,
  `contract_tests` and `documentation_authority`, plus `assurance_findings` which it declares above
  the floor. If it cannot, that is evidence against the design rather than a case for an exemption.
- **Every pattern is now built** — D and A at `ACT-011`, B at `ACT-012`, C1 at `ACT-014` — and the
  limitation above about patterns being *asserted* to fit is discharged for three of them and
  partly discharged for C. Two of this record's claims did not survive contact; both are amended
  above rather than left standing under a correction.
- **Code allocation is left open.** Whether each pattern gets its own `SP0xx` or one code carries
  several messages, as `SP032` does, is settled when the first validator is built rather than
  guessed here. Next free is `SP051`; `SP044`/`SP045` remain reserved for `DR-11`.
