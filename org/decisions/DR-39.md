# Decision Record

- Decision ID: DR-39
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — `check_conformance.py`'s prerequisite-gate
  history audit, which runs in every adopting repository.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change (`ACT-030`).
- Risk level: 3 — it changes what a published control (`SP035`) reports in every adopting
  repository, and it puts a heuristic inside a control.
- Related work item: `ACT-030`. Closes `F30`.

## Decision

**The history audit looks for a precondition artefact under every name it has ever had, and states
which rename chain it followed.**

`F30` recorded the defect and its candidate remedy four packets ago, and deliberately left it
unbuilt: *"`--follow` is heuristic, single-path, and its results would have to be trusted by a
control."* That objection is the substance of this record. It is answered by two properties, not by
deciding the heuristic is probably fine.

1. **The rename lookup can only ever ADD names to search.** `historical_paths()` returns the
   current path plus every earlier one; the audit reports a violation only when *none* of them
   existed at that commit. So the change can clear a false violation and cannot hide a commit where
   the artefact was genuinely absent under every name it has ever had.
2. **Every followed rename is disclosed on the run.** A cleared violation is never silent. This
   repository's own output now carries the chain its two renames created:
   `test_convention: precondition surfaceplate/standard/agent-instructions/tests.md followed through
   2 rename(s): … <- standard/agent-instructions/tests.md <- standard/.github/instructions/tests.instructions.md`

Where git cannot answer, the strict pre-`F30` behaviour stands.

## Context and alternatives

### Why this was worth building now

`F30` was raised at `ACT-018`, fired again at `ACT-019`, and was recorded rather than fixed both
times — correctly, because building it as a side effect of an unrelated packet is the scope creep
this project's working method exists to catch. What changed is the evidence: the same mechanism has
produced false violations twice, from renames this repository chose for its own good reasons
(`DR-30` made the agent instructions agent-neutral; `DR-31` packaged the payload for pip), and it
has filed two exception records for work that violated nothing. `DR-22`'s warning applies directly —
*"a growing pile of these records is evidence that the gate is wrongly scoped or the process is
wrong."* An adopter reorganising their documentation would have met the same wall.

### The directory case, found by driving it rather than by reading

`--follow` takes a single file. Pointed at a directory it does not error: it silently traces some
file *inside* the directory and reports that file's former path as though it were the directory's.
The effect here is harmless — a file existing at a commit implies its directory did — but a control
that relies on an accident is a control that has stopped meaning what it says, and the first
implementation's docstring claimed a directory fallback the code did not actually have. Directories
now keep the strict check explicitly, and the code matches its documentation.

### What was done with the two exception records

`GX-0001` and `GX-0002` were filed to clear exactly the violations this change removes. They now
cover nothing. They are **kept and marked superseded** rather than deleted:

- Deleting an exception record is the retrospective edit `core/PREREQUISITE_GATES.md` says an
  exception must never be able to make invisibly. The point of the mechanism is that it leaves a
  permanent, attributable mark.
- Leaving them unmarked would be worse than either: both files open by explaining that *"the history
  audit resolves the precondition by its CURRENT path"*, which is no longer true, and a future
  reader would take two exceptions as evidence of two real violations.

So each carries a header saying it is superseded, why, and that everything below describes the audit
as it behaved before the remedy — the supersession treatment this project's working method asks for:
keep what earns its keep as a record, but mark it explicitly historical.

### Alternatives rejected

- **Resolve the path as at each commit, per commit.** More precise in principle and much heavier:
  a log walk per commit rather than one per artefact, for a result that differs only in cases where
  the same path was reused by an unrelated file. Rejected as more machinery than the risk justifies.
- **Compare blob content rather than paths.** Would follow a file through a rename *and* an edit,
  but a precondition is about a document existing, not about its bytes being unchanged; a legitimate
  edit would look like a disappearance.
- **Do nothing and keep filing exceptions.** The status quo for four packets, and the thing `DR-22`
  names as evidence that a gate is wrongly scoped.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none. `SP035`'s meaning is unchanged — a gated path may not change while
  the precondition is absent. What changed is that "absent" no longer means "absent at the name it
  happens to have today".
- **Security/dependencies:** none. One additional `git log --follow` per required gate's artefact.
- **Operations/release:** every adopting repository gets this on upgrade. A repository that has
  renamed a precondition artefact stops reporting false violations; one that has not sees no change
  beyond a note where a rename exists in its history.

## Evidence

- A new fixture in `tests/test_install_and_check.py` (183 checks, up from 179): a gate whose
  artefact is renamed no longer reports its pre-rename history, and the rename is named on the run.
- **Both negative controls hold.** A genuine violation committed *after* a rename is still reported
  and still names the offending commit; an artefact that never existed resolves to itself alone.
- **Seen to fail:** reverting the lookup to the single current path re-fails the rename checks
  immediately.
- This repository's own audit, run before and after: the two renames `DR-30` and `DR-31` created are
  followed and stated.
- Ten suites pass; manifest rebuilt; vendored checker re-synced (the drift guard caught it, which is
  `F12`'s remedy working); both checker copies `PASS`.

## Limitations and follow-up

- **Rename detection remains a similarity heuristic**, at git's default threshold. The two
  properties above bound what it can do wrong; they do not make it exact. A file rewritten wholesale
  in the same commit as its rename may not be followed, in which case the strict check applies and
  the adopter sees a violation to explain — the safe direction.
- **A path reused by an unrelated file** could, in principle, be treated as a former name. The
  disclosure line is what makes that visible rather than silent; nothing detects it automatically.
- **Directory preconditions get no rename following at all.** Stated rather than hidden.
