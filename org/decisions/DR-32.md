# Decision Record

- Decision ID: DR-32
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — a decision about the CLI and the interactive
  adoption wizard.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change.
- Risk level: 2 — it decides how every future adopter fills in `governance/application-profile.yaml`,
  and retires the discovery/authoring phases of an existing prompt in favour of it.
- Related work item: `ACT-020`. Item 2 of `org/RELEASE_PLAN.md`. Implements `DR-12`'s CLI
  commitment. Resolves the naming collision `org/RELEASE_PLAN.md` named without deciding.

## Decision

**`surfaceplate` becomes a real console-script with three subcommands.** `install` and `check` are
thin wrappers over the existing `install_standard.py`/`check_conformance.py` — zero behaviour
change, both already accepted `argv`. `adopt` is new: an interactive terminal wizard, built on
`questionary`, that walks a human through every decision `governance/application-profile.yaml`
requires and writes it — nothing else. No method registry entries, no CI wiring, no code.

**The wizard's binding rule, stated in `org/RELEASE_PLAN.md` before any of this was built and
treated as non-negotiable throughout**: *it asks, the human answers, the tool writes.* It never
selects a conformance level, invents a rationale, or sets a date.

**`prompts/github-copilot-adoption-wizard.prompt.md` is retired**, replaced by
`prompts/copilot-implementation-assistant.prompt.md`. See "The naming collision" below.

## Context and alternatives

### The naming collision, resolved

`org/RELEASE_PLAN.md` named the problem without deciding it: `prompts/github-copilot-adoption-wizard.prompt.md`
already existed, already called itself "the wizard," and was stale — it predated the `0.12.0`
rename and omitted `core/PREREQUISITE_GATES.md`/`core/CONFORMANCE_LEVELS.md` entirely, both central
to what the standard now requires.

Its seven phases split cleanly on one line: Phases 1–3 (discovery, human questions, profile
authoring) are exactly what `surfaceplate adopt` now does, deterministically instead of by an LLM's
judgement — **retired**. Phases 4–7 (bounded implementation, focused validation, human review
gates, completion report) have no CLI equivalent and were never in this item's scope — **kept**,
rewritten to *consume* a profile `surfaceplate adopt` already produced rather than compete to
produce one. The file is renamed to `prompts/copilot-implementation-assistant.prompt.md`, which
does not claim the word "wizard" for itself anywhere in its own text — a repository-wide,
case-insensitive sweep after the rewrite confirms every remaining occurrence of the word either
names `surfaceplate adopt` (correctly, since that is what it now unambiguously means) or sits in a
historical record (`CHANGELOG.md`, `org/FINDINGS.md`'s `F18` entry) that is deliberately left
unedited.

The new prompt opens with an explicit precondition check: if `governance/application-profile.yaml`
is missing or still the untouched template, it stops and tells the human to run `surfaceplate
adopt` first, rather than falling back to authoring one itself. Two tools that could each author
the same file, with no stated precedence, would be the contradictory-authority defect this
framework exists to catch — the same shape `core/AUTHORITY.md`'s "one canonical authority per
question" already names for documentation.

### Terminal, not a browser form — decided collaboratively, before this record, not assumed

Before any code was written, three representative moments of the flow — identity, the
conformance-level choice, and one section of the 19-gate catalogue — were built as a clickable
comparison artifact rendering both a terminal TUI and a web form, and walked through with the
maintainer directly. The maintainer's own framing of the problem drove the comparison's existence:
*"how does someone answer in a prompt back — would be great if you could actually get like a pop up
or html or something better visually to complete the form."*

**Terminal, built as a real TUI (`questionary`) rather than raw `input()` prompts, was chosen.**
Reasoning, agreed at the time: `DR-12`'s commitment is to a CLI, not an incidental detail; the
environments this needs to run in — SSH, headless CI, agent sessions — make a browser-only tool
fail outright in exactly the cases that matter most; and a browser wizard would need a local HTTP
server, a browser-launch path, *and* a terminal fallback underneath anyway, meaning building both
for the price of one before any adopter had asked for either. `--web` mode is not built here — see
Limitations.

### The `Prompt` protocol — what makes the binding rule testable, not just stated

Every section function (`surfaceplate/adopt/sections.py`) calls `Prompt.text`/`.select`/`.confirm`
rather than `questionary` directly. In production that is `InteractivePrompt`, a thin wrapper over
real `questionary` calls. In tests it is `ScriptedPrompt`, which consumes pre-set answers strictly
in order and raises if the wizard asks for more than the script provides (`AssertionError`, not a
silent default) or if the script finishes with answers unconsumed (`assert_exhausted()`).

This is the concrete mechanism behind "nothing missing, nothing extra": every value in the written
profile provably traces to something a `Prompt` call returned, because asking and doing are
different objects and a test can watch the seam between them. Without this separation, "the wizard
never invents a value" would be a claim about the code's intent, not a property a test can fail on.

### The write mechanic — a purpose-built renderer, not `yaml.safe_dump`

`templates/application-profile.yaml` is essential-only: one gate (`work_registration`), one control
(`dependency_lock`), both filled with `replace-me` placeholders. Producing a `standard` or `full`
profile means *generating* blocks the template does not contain, not filling blanks in place — a
flat `yaml.safe_dump` of an assembled dict would also be comment-less, inconsistent with the house
style every hand-authored profile in this repository follows (the template itself, both worked
examples, this repository's own profile). A `ruamel.yaml` dependency for round-trip comment
preservation was rejected as more supply-chain surface than the problem justifies (D4) — the wizard
already knows exactly what it is writing, having built every field from a structured answer, so it
writes its own explanatory comments as it assembles the file, the same way `install_standard.py`'s
`upsert_conformance_block` already prefers targeted, controlled writing over a generic engine.

`surfaceplate/adopt/render.py` renders individual **values** through `yaml.safe_dump` — so escaping
and quoting are never hand-guessed — and places those correctly-escaped values inside hand-written
structure and comments. Two real defects surfaced at exactly that seam during development, both
described below because they are the direct justification for the round-trip check that caught
them.

### The profile is verified before it touches disk — and that verification is not decorative

`wizard.py:_verify` re-parses its own rendered text with `yaml.safe_load`, asserts the result
equals the dict that produced it, validates the re-parsed result against
`schemas/application-profile.schema.yaml` with format checking, and scans every string value for a
template placeholder token (`check_conformance.PLACEHOLDER_PATTERN`) before returning control to
`wizard.run`. Any failure raises `WriteRefused` and nothing is written. This is not a hypothetical
safety net: two of the four defects below were caught exactly this way, as a write refusal on the
first attempted run, not as a corrupted file discovered afterwards.

### Four defects the wizard's own verification caught during development

1. `Prompt.confirm` had no `help` keyword in its Protocol signature while a call site
   (`sections.ask_stack`) passed one — a plain `TypeError` on the first scripted run.
2. PyYAML appends a literal `\n...` document-end marker when a bare scalar is dumped as its own
   top-level document (a container does not get one). `.strip()` does not remove it, because it is
   not trailing whitespace — it is real content, and it corrupted every line it was embedded in.
   Fixed by stripping the marker explicitly (`render._strip_document_end`).
3. PyYAML wraps a plain scalar onto a continuation line past its default 80-column width, and
   computes that continuation line's indent for a scalar dumped at column 0 — wrong the instant it
   is embedded after a `key: ` prefix at any other indent. Fixed with a no-wrap width
   (`render._NO_WRAP = 100_000`) and an explicit refusal for any value containing a literal newline,
   since the whole rendering strategy depends on every value being single-line.
4. `status_rationale` was `None` in the assembled profile dict (set unconditionally in
   `sections.ask_adoption_identity`) but correctly **absent** from the rendered YAML (the renderer
   omits the key rather than writing `null`, since the schema does not require it outside
   blocked/deferred adoption status) — so the round-trip comparison correctly failed. Fixed at the
   source: the key is now genuinely absent from the assembled dict when it does not apply, matching
   how `independent_validator` — typed `[string, "null"]` in the schema, and always written
   explicitly — is deliberately handled the opposite way.

None of these reached a written file. All four were found and fixed before the wizard's first
successful end-to-end run.

### A fifth defect, unrelated to the wizard, found by the same verification discipline

`CLAUDE.md`'s own working instructions require reinstalling from a clean release copy after
changing anything the standard ships, not just re-running the suites — and doing exactly that
surfaced a genuine, pre-existing bug in `scripts/build_release.py`'s release-archive step, not the
wizard.

`build_zip` writes every payload file's archive path from `f.relative_to(ROOT)` — correctly nested
under `surfaceplate/` since `ACT-019` moved the payload there — except one: the line writing
`MANIFEST.sha256` itself still hardcoded `f"{top}/MANIFEST.sha256"`, the path it lived at *before*
that move, when it sat at the repository root beside the payload rather than inside it. `ACT-019`'s
own sweep updated the constant that locates the file on disk (`MANIFEST = ROOT / "surfaceplate" /
"MANIFEST.sha256"`) but not this one archive-write call using a different, hand-written path
string for the same file — the kind of gap a full-repository grep for a moved *directory* does not
catch when only one specific line still spells out the old location by hand.

**The consequence was real, not cosmetic.** A ZIP built this way places `MANIFEST.sha256` as a
sibling of the `surfaceplate/` package directory inside the archive, not inside it — so
`install_standard.py`'s `framework_anchor()`, which looks for `MANIFEST.sha256` relative to
`--source` (the `surfaceplate/` directory), finds nothing there. Reproduced directly: extracting
the built archive and self-installing from it produced `SP049` — *"the profile declares a framework
digest that cannot be verified"* — from a checker with nothing wrong to report about the wizard at
all. Fixed with the same `relative_to(ROOT)` pattern every other payload file already uses; the
fixed archive was extracted and self-installed again, and `MANIFEST.sha256` resolved correctly on
the first attempt.

This repository's own `governance/application-profile.yaml` needed its `adoption.framework_digest`
re-pinned to match afterwards — the same self-reference `DR-31`'s own evidence section already
describes, and the operational step its comment already tells the next reinstaller to expect.

### `questionary` is an optional extra, not a hard dependency — found while wiring CI, not assumed

`pyproject.toml`'s `dependencies` list is swept by `tests/validate_contracts.py`, which asserts
every declared dependency appears in every workflow's `pip install` line — including
`.github/workflows/standards-conformance.yml`, **the workflow this project installs into every
adopting repository**. That workflow only ever runs `check_conformance.py`; it never runs `adopt`.
Declaring `questionary` as a hard dependency would have put it on every adopter's CI pip-install
line for a command their CI never invokes — an unjustified dependency footprint the check itself
surfaced, not something reasoned about in the abstract beforehand.

`[project.optional-dependencies] adopt = ["questionary==2.1.1"]` instead. Verified directly: a real
wheel was built and its `METADATA` inspected — `Requires-Dist: questionary==2.1.1; extra == 'adopt'`,
absent from the unconditional `Requires-Dist` lines. `cli.py`'s `adopt` subcommand checks for the
import explicitly and prints `pip install surfaceplate[adopt]` rather than a bare traceback when it
is missing. This repository's own CI (`standard-self-check.yml`, which runs `tests/test_adopt.py`)
installs it directly, since it is the one workflow that actually exercises `adopt`.

### Alternatives rejected

- **A browser form (`--web`).** Rejected above, per the collaborative decision; not built here.
- **Real resumability (`--resume`).** No adopter has asked for it, and a 19-gate `full` walk that
  fails partway through is currently a clean, total re-run — worse than resumability, but simple
  and correct, which the evidence available today does not yet justify trading for.
- **A single "smart" `Prompt` implementation that both asks and answers via detected defaults.**
  Would have made the binding rule unfalsifiable by construction: a detector that got
  `builds_user_interface` wrong would read identically to a human's own wrong answer. `detect.py`
  exists to save typing, shown back for confirmation, never written silently — the same reasoning
  `core/CONFORMANCE_LEVELS.md` already states for why that field is not descriptive.
- **`questionary` as a hard dependency.** Rejected above, found via the existing dependency-lock
  check rather than assumed acceptable.
- **Splitting `sections.py` into one module per section**, as the approved plan's file list
  literally specified. The seven asking-functions share three small helpers
  (`_nonempty_text`, the pattern-A/B/C control-question dispatch, the gate-question shape) and total
  under 400 lines; splitting them would have spread that sharing thinner across more files, not
  made it clearer. Recorded here as a deliberate, disclosed departure from the plan's literal text
  rather than a silent one (I2).

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none changed. The wizard produces profiles that validate against the
  existing `application-profile.schema.yaml` unmodified.
- **Security/dependencies:** one new optional runtime dependency (`questionary==2.1.1`, pulling in
  `prompt_toolkit` and `wcwidth`), scoped to the `adopt` extra and never installed as part of the
  workflow this project ships to adopters.
- **Operations/release:** `pip install surfaceplate` now gives a real `surfaceplate` command.
  `install`/`check` work immediately; `adopt` needs `pip install surfaceplate[adopt]`.
  `INSTALL.md`, `README.md`, and `SETUP_GUIDE.md` document it as the recommended route to a filled
  profile, with the manual steps kept as the documented fallback.
- **Documentation authority:** `prompts/github-copilot-adoption-wizard.prompt.md` retired;
  `prompts/copilot-implementation-assistant.prompt.md` is now the sole live authority for the
  bounded-implementation phase, and the sole document referring to itself as consuming (never
  authoring) the profile.

## Evidence

- **`tests/test_adopt.py`, 23 checks, `PASS`.** A scripted `essential`-level run (29 answers,
  hand-verified) writes a profile that `assert_exhausted()` confirms used every answer and asked
  for nothing else, that matches the typed values exactly on re-parse, and that the real
  `.standards/check_conformance.py` — run as a subprocess against a repository with the named
  artefacts actually seeded — raises zero schema-shape findings against. A `full`-level,
  UI-building run (an answer sequence generated by walking `catalogue.py`'s own data, not hand-typed
  — a fixture-generation convenience, not a correctness oracle, since the test asserts real
  properties of the *output*: every level-mandatory gate is `required` and never anything else, all
  19 gates and all 9 controls are present, and the result validates against the schema
  independently). An interrupt mid-flow (`Cancelled` raised partway through section 2) leaves the
  profile and every other file in the repository byte-for-byte and set-for-set unchanged. `adopt`
  refuses a repository without `.standards/INSTALL.json`, and refuses to overwrite a real
  (non-template) profile, in both cases leaving existing content untouched. `_verify` refuses a
  profile whose only defect is a template placeholder token, proven by mutating an
  already-schema-valid profile rather than a synthetic one that would fail schema validation first
  for an unrelated reason.
- **`catalogue.sectioned_gates()` sums to `len(GATE_CATALOGUE)` (19)** and contains no duplicate
  gate ID across sections — the one drift guard this package's own docstring commits to, since the
  six-section grouping has no machine-readable source to derive from (`core/PREREQUISITE_GATES.md`
  states it only as prose headings).
- **All six suites pass together**: `validate_contracts.py` (164), `test_install_and_check.py`
  (170), `test_adopt.py` (23), `check_identifiers.py` (123), `check_code_registers.py` (10),
  `check_vendored_current.py` (57).
- **The wheel's built metadata** confirms the `questionary` extra split: `Requires-Dist:
  questionary==2.1.1; extra == 'adopt'`, and no unconditional `Requires-Dist` line for it.
- **An environment finding, recorded rather than smoothed over**: the machine this was built on has
  a `python3` with no `pip` at all, and apt-installed `jsonschema==4.10.3`/`PyYAML==6.0.1` — older
  than this project's own pins (`4.26.0`/`6.0.3`). Every verification command in this packet ran
  through a repository-local `.venv` (already `.gitignore`d) built with the pinned versions, once
  this was discovered — `F21`'s divergence, reproduced live on the maintainer's own machine, not
  merely a risk described in the abstract.

## Limitations and follow-up

- **`--web` mode is not built.** Deferred, evidence-led, per the collaborative decision above.
- **No resumability.** An interrupted `full`-level, 19-gate run must be re-run from the start.
- **`adopt` never offers `deferred` as a `control_decisions` choice** — only the level's mandatory
  controls (always `required`) and, optionally, controls declared above the floor (also always
  `required` in this version). `adoption.deferrals` is therefore always empty in a wizard-produced
  profile. The schema supports a genuinely deferred control with an owner and a revisit date; this
  version does not expose that path, and an adopter who needs it edits the profile by hand. Recorded
  as a disclosed simplification, not a silent gap: least complexity the objective currently
  justifies, not every path the schema allows.
- **`org/RELEASE_PLAN.md`'s naming-collision section is updated in the same change** that marks
  item 2 complete, once this record and the rest of the packet exist to update it against.
