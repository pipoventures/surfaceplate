## Decision

Adoption pinning evidence is two layers, not one, and both must exist:

**Layer 1 — distribution identity.** What `adoption.framework_digest` and
`adoption.framework_version` mean today, unchanged for git-clone adoption: the SHA-256 of the
pinned release archive, and the framework version string — with the archive's own non-reproducibility
recorded as a pre-existing limitation, not fixed here (see "Context and alternatives"). For
pip-based adoption, the same two fields carry a **channel-specific** meaning: `framework_version`
is the PyPI-published package version; `framework_digest` is the SHA-256 of the specific **wheel**
file pip fetched — the wheel specifically, not "wheel or sdist" (see the rejected alternative on
artefact-kind ambiguity). This is the same hash pip's own `--require-hashes` mechanism already
carries in a lock file, and the same hash PyPI records against that exact filename for as long as
the file remains published. A new, optional field, `adoption.distribution_channel: git | pip`, is
added to disambiguate which meaning a given profile is using. `framework_digest`'s schema
description (`schemas/application-profile.schema.yaml:59-62`, currently "SHA-256 of the pinned
release archive") is reworded to be channel-neutral: "SHA-256 of the pinned distribution artefact
(release archive under git-clone adoption; wheel file under pip adoption) — see
`adoption.distribution_channel`."

**Layer 2 — installed-payload evidence.** `.standards/INSTALL.json`'s existing `files` mechanism
(`install_standard.py:311-322`, `356-368`), unchanged in shape: a locally-computed, per-file digest
of what actually landed in the adopter's own repository. This layer is not, and does not claim to
be, externally anchored — see the rejected alternative below for why it cannot substitute for
Layer 1.

**The checker continues to be vendored.** Whatever mechanism pip distribution uses to obtain
`surfaceplate`, the local install step still copies a snapshot of `check_conformance.py` into the
adopter's own `.standards/` (as `install_standard.py:81` already does today), and that snapshot
remains part of `files` — digest-protected exactly like every other fixed payload file. Pip
distribution does **not** mean the checker becomes an ambient console script resolved fresh from
whatever is currently `pip install`-ed. This is decided here, not left implicit, because DR-11
depends on it (see "The cross-record interaction").

Both layers, plus the vendoring commitment, are required together. None alone answers the question
this decision was asked to answer.

## Context and alternatives

**The governing question, restated:** by what evidence can an adopter later prove which version of
the framework they conformed to, on a machine that is not theirs? "Not theirs" is the load-bearing
phrase — it rules out any evidence whose only witness is the adopter's own machine.

**What the code does today, established by reading it, not documentation about it.**
`adoption.framework_digest` is, by its own schema description, "SHA-256 of the pinned release
archive" (`schemas/application-profile.schema.yaml:59-62`). It is validated for shape only —
`^[A-Fa-f0-9]{64}$` — and `framework_version` for shape only —
`^[0-9]+\.[0-9]+\.[0-9]+$`. Exhaustive grep across the repository confirms **no code path anywhere
reads or cross-checks either field** against anything real; the only other place either string
appears is `tests/validate_contracts.py:393-462`'s own negative-shape tests. `DR-7.md:117` already
records that even the worked example's digest is unverifiable and very likely fabricated. In other
words: **today's Layer 1 is a self-asserted string, checked for shape, never checked for truth.**
This decision does not fix that enforcement gap — closing it is implementation work — but it
constrains what the eventual enforcement must be able to check.

`.standards/INSTALL.json` (`install_standard.py:352-373`) has no source-provenance field at all —
not a source path, not a source repository URL, not a source commit SHA, not a release-archive
digest. It has `files: {relpath: sha256(normalise(text))}`, computed from
line-ending-normalised text (`install_standard.py:311-322`), which is a **different digest
algorithm** from `MANIFEST.sha256`'s raw binary chunked SHA-256 (`build_release.py:43-48`) — the
two are not cross-comparable without re-hashing one of them. `install_standard.py` never reads or
references `MANIFEST.sha256`, `zip`, or `framework_digest` anywhere (confirmed by grep).

**Today's git-clone Layer 1 is itself not reproducible, and this decision does not fix that either.**
`build_release.py:80-89` writes zip entries with `zipfile.ZipFile.write`, which embeds each file's
mtime. Rebuilding an identical tree therefore yields a different archive SHA-256 — the maintainer's
own tooling cannot reproduce the artefact whose digest a tag message or an adoption record cites,
only re-verify the one already built. This was already flagged, not actioned, when it surfaced
during `v0.14.0`'s own release. It is relevant here because the tempting fix —
`sha256(MANIFEST.sha256)` instead of `sha256(archive)`, since the manifest is a deterministic,
already-committed text file listing every payload digest — is a real, ready-made improvement to
git-clone Layer 1 that this decision does **not** make, because the packet scoped this record to
deciding pip's pinning model, not to redesigning git-clone's already-shipped one. Recorded so the
option is not silently lost: a future decision revisiting git-clone Layer 1 has a concrete,
already-evaluated candidate waiting. Pip's wheel-hash Layer 1 does not inherit this weakness — a
PyPI-hosted file's hash is not a function of when it happened to be built.

Today, pip distribution does not exist. Exhaustive grep across the repository — `pypi`,
`pip install`, `wheel`, `sdist`, `setup.py`, `pyproject` — returns zero hits that are not about
installing the runtime dependencies `pyyaml`/`jsonschema`, or prose in `adapters/python.md`
recommending `pyproject.toml` for *adopting* applications. No `pyproject.toml`, `setup.py`, or
importable `surfaceplate` package exists in this repository. This decision is entirely anticipatory,
and depends on a precondition it does not itself decide: **`install_standard.py`'s file-location
mechanism does not survive pip distribution unchanged.** `repo_root()` (`install_standard.py:58-59`)
resolves the default source to the repository root, and `build_payload` globs `standard/`,
`schemas/`, `core/`, `templates/`, `examples/`, `adapters/` as repository-root directories — none of
which are package data under a wheel install. Under a naive pip install, `verify_source()`
(`install_standard.py:106-107`) would find every one of those directories missing and refuse with
exit 2. Deciding *what an adopter pins to* does not require deciding *how the installer finds its
own payload under `importlib.resources`* — that is a packaging-mechanism decision this packet's own
constraints put out of scope ("no packaging, no CLI") — but this decision cannot pretend the
precondition is free. Recorded as a stated dependency, not solved here.

A second, related fact worth recording for the same reason: the self-install refusal in
`install_standard.py:424-426` (`if target == source: ... "refusing to install the standard into
itself"`) is pure path-equality. Under **pure** pip distribution it becomes permanently dead code —
a site-packages `source` path can never equal any adopter's `target`. But the hazard the guard
exists to catch does not fully retire with it: in a **mixed** scenario (the tool pip-installed, but
someone still points a hypothetical `--source` at a local clone) the guard's current form would not
catch a clone-onto-itself accident, because the paths genuinely differ even though the content is
the standard's own source. A future implementation would need a content-based guard (does the
target contain `standard/conformance-block.md` and `VERSION`) rather than a path-based one to
preserve the same protection. Recorded, not designed.

**Rejected: "digest of the installed payload, computed at install time" as the sole Layer-1 pin.**
This is exactly what `.standards/INSTALL.json`'s `files` already is. It has no external anchor — a
stranger auditing the claim, on a machine that is not the adopter's, has nothing to compare the
recorded digest to except trusting the adopter's own computation on the adopter's own machine. That
fails the governing question directly: it is evidence a stranger cannot check, only evidence the
adopter cannot contradict themselves. Kept as Layer 2 for what it is actually good at — proving
what got installed *here* — but rejected as the sole answer to the pinning question.

**Rejected: PyPI version string alone, with no distribution-file hash.** PyPI enforces
filename/version immutability as an operator policy, not as something the adopter's own tooling can
verify cryptographically, and that policy does not necessarily hold on a private index or mirror a
security-conscious adopter might be required to use instead. A hash is self-verifying by the
adopter's own tooling, independent of trusting any index operator's policy — the stronger property
the governing question actually asks for. Recording both costs nothing extra: pip's own
`--require-hashes` mechanism already carries the hash alongside the version in a lock file. The
right comparison for "how permanent is this record" is not PyPI versus an adopter's own retained
ZIP — it is PyPI versus GitHub release assets, which an administrator *can* delete and re-upload
under the same tag with no platform-enforced immutability at all. Against that comparison, PyPI's
per-file identity is the stronger record, not merely a convenient one. One caveat stated honestly: a
hash by itself is not reverse-lookupable to "which project, which version" — a verifier needs
`framework_version` alongside `framework_digest` to know what to ask PyPI about, which is exactly
why this decision keeps both fields rather than trying to make the hash carry that information
alone.

**Rejected: pin to either "the wheel or the sdist", leaving the choice open.** A pure-Python,
no-compiled-extension package like this one can in principle be installed from either, but the two
are built by different tooling paths (`package_data`/wheel-metadata versus `MANIFEST.in`/sdist
inclusion rules) and are not guaranteed byte-for-byte equivalent, nor guaranteed to cover exactly
the same file set. Leaving the choice open means one framework version could carry two legitimate,
disagreeing `framework_digest` values, which breaks the very cross-adopter comparability Layer 1
exists to provide — two adopters both honestly on "0.14.0-under-pip" could report different digests
and neither would be wrong. Decided instead: pin to the wheel specifically, because it is what pip
actually installs from pip's normal resolution path, and because it is the only one of the two
guaranteed to contain the exact files a future `importlib.resources`-based loader would read at
runtime — an sdist can be rebuilt into a wheel by a different build backend producing different
output, which would break the guarantee that Layer 1 identifies the exact bytes Layer 2 was derived
from.

**Rejected: retire the git-clone meaning of `framework_digest` in favour of a single pip-shaped
meaning.** Git-clone installation is not being removed by this decision, and there is no reason to
force every future adopter onto pip. A single field whose meaning depends on an undisambiguated
context is worse than two disambiguated meanings behind one new field
(`adoption.distribution_channel`) — the same reasoning `DR-6` used against forcing one meaning onto
the namespace version segment.

**Considered and set aside as premature, not rejected on the merits: PEP 740 attestations /
PyPI Trusted Publishing.** These add *authenticity* (who published this file) on top of the
*integrity/identity* this decision addresses (which bytes were published, and can they be
re-verified). `scripts/verify_release.py` already states explicitly that today's mechanism "does
NOT establish authenticity" for git-clone adoption — this decision does not newly need to solve a
problem it was never asked to solve, and does not claim to. Named here so a future decision does not
have to rediscover that pip is the first channel where a real authenticity primitive becomes
available essentially for free.

## Impact

- Numerical/model output: none.
- Contracts/schemas: `schemas/application-profile.schema.yaml`'s `adoption` block gains one new
  optional property, `distribution_channel`, and `framework_digest`'s `description` string changes
  from git-specific to channel-neutral prose. This is **additive at the schema level, but not
  costlessly backward-compatible for every already-vendored checker.** The `adoption` object is
  `additionalProperties: false` (`schemas/application-profile.schema.yaml:45`), and schemas are
  themselves vendored per-adopter into `.standards/schemas/`. A profile written against the updated
  schema and carrying `distribution_channel` would be **rejected** by any adopter still running an
  older vendored copy that predates this field — additive at the source, but not at every point of
  use, until that adopter re-installs. This is not a hypothetical risk this decision invents:
  `DR-6.md:113-115` already names it precisely, as an open limitation of its own namespace-version
  rule — *"a change that is additive in form but breaking for a real adopter — a new optional field
  an adopter's own `additionalProperties: false` extension rejects, for instance — is not covered by
  the list."* Adding `distribution_channel` is exactly that instance. It does not meet `DR-6`'s
  definition of a breaking schema change (no field removed, no type narrowed, nothing made
  required), so the namespace `$id` correctly does not bump — but that also means the `$id` carries
  no signal that an older vendored schema copy has fallen behind. This decision does not resolve
  that already-known gap; it is the first concrete case that instantiates it.
- Security/data: directly affects whether an adoption claim can be checked by anyone other than the
  adopter. Today it cannot; this decision states what would let it be checked, without yet
  implementing the check.
- Reproducibility/lineage: this is the decision's whole subject. It does not itself make anything
  more reproducible — no enforcement code changes — but it fixes the target shape a future
  enforcement change must build toward, so that work is not designed twice.
- Operations/release: no adopter-facing change yet, and no adopter exists to be affected (`DR-7`).
  This decision only fixes the direction future pip-distribution work must take, in the same sense
  `DR-1` fixed a direction for hook-chaining without implementing it.

## Limitations and follow-up

- **Decided, not implemented.** No schema change, no installer change, no checker change has been
  made. Implementation — adding `distribution_channel` to the schema, and whatever verification
  eventually reads and cross-checks `framework_digest` against a real distribution — is scoped to
  whichever release first ships pip distribution.
- The enforcement gap this decision does not close: nothing today, and nothing this decision adds,
  actually verifies `framework_digest` against a real release for *either* channel. That is a
  separate, larger piece of work (closing `check_conformance.py`'s complete silence on both fields),
  recorded here as a known, pre-existing gap rather than claimed as solved.
- The two incompatible-algorithm digest schemes already in the codebase — `install_standard.py`'s
  line-ending-normalised text digest, and `build_release.py`'s raw binary chunked digest — are not
  reconciled by this decision.
- The `sha256(MANIFEST.sha256)` improvement to git-clone Layer 1, and the PEP 740 authenticity
  question, are both named above as real, unresolved candidates for separate future decisions — not
  silently dropped, not decided here.
- The `repo_root()`/resource-loading precondition and the self-install guard's mixed-scenario gap are
  both named above as facts an implementation must confront; neither is designed here.
- See "The cross-record interaction" in `DR-11.md` for the dependency this decision's checker-
  vendoring commitment exists to satisfy, and the incompatible combination that commitment avoids.
