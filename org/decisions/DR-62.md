## Decision

**1.0 supports GitHub as the forge, and says so.** The installer keeps writing the GitHub Actions
conformance workflow; `README.md` and `INSTALL.md` state that on another forge the file is inert,
that everything else installed is forge-independent, and give the one command to run in any CI.
Item 3 closes as done with its scope stated. A per-forge CI emitter, GitLab first, is 1.x work
(`1.4` in the outline), taken up when an adopter on another forge appears.

## Context and alternatives

`ACT-041` narrowed the question from eight files to one: the conformance workflow is the only
installed file that assumes a forge, and the checker already reads `.gitlab-ci.d` as a CI
directory. Not chosen: adding a GitLab emitter now (a second installed CI file to keep current,
for no adopter who has asked; both real adopters are on GitHub); making the installer ask which
forge (the same plus a question on every install). Stating the scope costs nothing to reverse:
the day an adopter on another forge appears, the emitter is a bounded activity with a real user.
