# Decision Record

- Decision ID: DR-40
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — the shape of `surfaceplate adopt`'s interview.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change (`ACT-031`).
- Risk level: 3 — it changes the wizard's opening structure for every adopter, and it introduces a
  path where the tool proposes answers, which is adjacent to the one thing this package forbids.
- Related work item: `ACT-031`. Closes `F39`.

## Decision

**Ask the minimum, then offer to propose the rest. A proposal is shown with its origin and is never
written until a human approves it.**

1. **Experience, not prose.** The opening question was *"which register of explanation do you
   want?"* — a question about the tool's output, asked before any output has been seen. It now asks
   about the person, and the wizard derives the register. The maintainer's own suggestion after
   finishing a run: *"we should suggest simple or advanced explanations by asking what level of
   experience does the user have."*
2. **A fork after the minimum.** Identity, stack, risk and level are asked first — the four nobody
   can answer on an adopter's behalf, and the four every proposal depends on. Then: **Set defaults**
   or **Customise adoption**.
3. **Proposals have exactly three honest sources**, and a field with none is still asked:
   **discovered** (a real path, directory or CI step read from this repository), **example** (the
   worked prose this framework already ships), **computed** (today's date, the review horizon, a
   maintainer taken from the owner already given).
4. **One interaction model.** `[X]` for yes/no, `(●)` for pick-one, a dropdown for
   pick-one-from-many. The gate catalogue's chip row is gone.

## Context and alternatives

### Why a defaults path does not breach the binding rule

`org/RELEASE_PLAN.md` binds this wizard: *it asks, the human answers, the tool writes*.
`tests/test_provenance.py` enforces it by feeding sentinels to every field and allow-listing what
the framework legitimately contributes. A tool that fills in answers is precisely what that rule
exists to forbid, so the shape was put to the maintainer explicitly rather than chosen.

The answer he took is what makes it sound: **a proposal is a suggestion until a human passes a
screen showing it.** Nothing reaches disk before the profile review that has always ended this
wizard, and the defaults screen adds a second look before that. So an accepted proposal is an
answer, submitted the same way a shown default in a text box has been submitted since `DR-32` — and
`tests/test_provenance.py` needs no change at all, because the sentinel walk drives
`sections.build_profile` directly and never sees a proposal.

**The honest half is what is NOT proposed.** `defaults.py` proposes nothing for a gate's
`precondition_description`, nothing for `gated_description`, nothing for
`adoption.decision_record_id`. Those are judgements or identifiers, and inventing them would be the
`F32` defect deliberately reintroduced. `unanswered()` returns exactly what is left and the wizard
asks for it. A test asserts both directions: every discovered value came from the scan, and the
description fields and the decision-record id are absent from the proposals.

### Why the gates were blank, and why no test saw it

`F39` carries the detail. Short version: the app built the gate catalogue from a plan that had
never been given the repository scan, so every artefact field fell back to a text box. The
screen-to-plan join added at `ACT-028` compares field **ids**, which are identical whether a field
is a dropdown or a text box — and even after strengthening it to compare **kind**, it still could
not have caught this, because the join constructs both sides itself and the defect lives in the app
wiring two screens from different sources. Only a test that drives the real `AdoptApp` sees it.

That is worth stating as a general lesson rather than a bug note: **a join test proves the parts
agree; it says nothing about the assembly.**

### Alternatives rejected

- **Defaults written straight through, no review.** Offered and declined. It would have made the
  tool the author of rationales and gate decisions, and would have forced the provenance allow-list
  to absorb them — which is the point at which that test stops meaning anything.
- **Keep the chip row for gate status.** It was faithful to the approved mockup, and it was the
  third interaction model on one screen. Fidelity to a drawing is worth less than one rule an
  adopter learns once.
- **Open the dropdown on focus** rather than on click. Simpler, and it would fling menus open while
  arrowing through a form.
- **Show only the gates the level requires.** Considered for the catalogue's length; rejected
  because `standard` and above require every catalogue gate to be *declared*, so hiding them would
  only move the work.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none. The written profile is unchanged in shape.
- **Security/dependencies:** none.
- **Operations/release:** every adopter meets a different opening — one extra question (the fork),
  four fewer blank screens if they take the defaults, and an ending that says what was written and
  whether it passes.

## Evidence

- Ten suites pass: contracts 167, installer 183, adopt 71, provenance 5, adopt-tui 31, render 16,
  discover 14, identifiers 141, registers 10 (39 F codes), vendored 57 files.
- **The app-wiring test is seen to fail:** removing `found=` from the gate plan makes it report
  *"rendered as EditableInput - the scan did not reach this screen."*
- Proposals run against the real Plutos repository: 63 values — 27 computed, 17 discovered, 19
  example — with 17 left for the adopter. `work_registration` proposes `activity/register.md`, which
  is what `DR-34` independently identified as Plutos's real register, and
  `decision_before_implementation` proposes its real decision log.
- Ranking is cut **after** scoring, not before: capping first buried the register beneath a dozen
  files in `docs/archive/`.
- Both new screens read back as rendered text before being claimed.

## Limitations and follow-up

- **Keyword ranking is a heuristic** over file names. It orders; it never filters, and the adopter
  still chooses. A repository whose register is called something unexpected will see it ranked
  lower, which is a guess this record owns.
- **The defaults path has not been driven by a human yet.** Every previous round of this wizard was
  corrected by a real run, and this one will be no different.
- **`Select` has no type-to-filter.** Twelve ranked options is the mitigation; a longer list would
  need a searchable widget Textual does not ship.
