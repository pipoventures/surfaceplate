# Decision Record

- Decision ID: DR-83
- Date: 2026-09-11
- Application: Surfaceplate (the framework itself) — what a repository that keeps its own Git hook
  system declares, and which gates may claim `local_hook`.
- Decision owner: Mario Pipo (maintainer), who directed that all eight confirmed sweep findings be
  fixed including this one. Drafted by the agent under `ACT-095`; confirmed by merging.
- Status: accepted — implemented by `ACT-095`.
- Risk level: 3 — it changes what every `--chain` adopter's profile claims, and a claim is what
  makes the checker start enforcing something it was not enforcing before.
- Related work item: `ACT-095`; **closes `F156`** (chained case) and raises `H24`; implements what
  `DR-66` specified and nothing reached.

## Decision

**A repository installed with `--chain` declares its delegation, and its gates claim `local_hook`.**

1. `discover.installed_hooks(repo)` reads the install record's own `hooks` value — `installed`,
   `chained`, `declined`. **A fact about the tree, never a question**: the installer already wrote
   down what it did (`DR-73`'s reasoning, one control along).
2. A chained install is asked **one** thing: why it keeps its own hook system. That is a judgement
   and is the adopter's.
3. `adoption.hook_chain.delegates_to` is **derived** — it is where this standard installs its gate,
   not a choice. `DR-81`'s claim/clerk split: the adopter chose to chain; they did not choose the
   path. Its provenance origin is `fact of record`, not `typed`.
4. Gates written by a chained install carry `enforcement: [history_audit, local_hook, review]`.
5. **Nobody else is affected.** An `installed` or `declined` repository is not asked the question,
   writes no `hook_chain` key, and keeps `[history_audit, review]` byte for byte.

## Context

`F156` records the reproduction. The short form: `grep hook_chain surfaceplate/adopt/*.py` returned
nothing. The wizard had no concept of chaining, `local_hook` existed only as a permitted enum value
nothing proposed, and `sections.DERIVED_ENFORCEMENT` was `["history_audit", "review"]` for every gate
of every adopter.

Every one of the checker's hook checks is gated on `"local_hook" in gate["enforcement"]`. So
`DR-66` — which this repository designed, built, tested by effect with a probe, and dissolved
`SP038`'s old form to make room for — **could not fire for anybody through the documented path**. The
sweep reached it only by hand-editing a profile, which is why it was reported as a `--chain` problem
rather than the general one it is.

That is the finding under the finding, and it is worth stating plainly: a control can be built
correctly, tested thoroughly, and still be unreachable, because *nothing that writes a profile ever
made the claim that turns it on*. The tests all passed because they tested the checker against
hand-written profiles. Nothing tested that the wizard produces a profile the checker will act on.

### Why not claim `local_hook` for an ordinary install too

It is the obvious next question and it is **not decided here** (`H24`). A repository whose hook *is*
the standard's has a local hook that genuinely gates its staged changes, and claiming it would give
every adopter `SP038`'s protection rather than only chained ones. It would also mean every existing
adopter's next `adopt` run starts asserting something their previous profile did not, and a
repository whose hook has quietly stopped running would move from passing to failing. That is more
assurance and a larger blast radius, and which of those a standard should prefer at `0.18.0` is a
maintainer's judgement, not an agent's.

### Why the rationale is asked rather than derived

`DR-40`'s rule — ask what a human holds, derive what follows. *That* they chained is in the install
record. *Why* they keep their own hook system is not written anywhere and cannot be inferred, and the
schema requires it. It is one textarea, shown only to the adopters it applies to.

## Impact

- `discover.py`: `installed_hooks()`, and `Discovered.hooks`.
- `plan.py`: `adoption_plan(hooks=...)` prepends one conditional field.
- `sections.py`: `CHAINED_ENFORCEMENT`, `HOOK_TARGET`, `build_gate(hooks=...)`,
  `build_adoption`'s `hook_chain` block.
- `render.py`: writes the block, with the rationale as a literal block scalar (`DR-38` (3)) so it
  round-trips.
- `provenance.py`: a `FACT` origin for `delegates_to`, an answer route for `rationale`.
- **`build_profile` stays pure.** The chained state is derived from the answers — the plan asks the
  rationale only of a chained install, so its presence *is* the chained state — rather than from a
  fresh scan. Purity is what makes `--answers` replay deterministic and the matrix report
  comparable, and `DR-73` records the same reasoning for `build_controls`.

## Evidence

- **Both directions on a real repository.** Chain declared, no delegating hook in place: `SP038`
  fires, naming the gate and the hook Git would actually run. Delegating hook at the resolved hooks
  path: `SP038` clears, `PASS`.
- **A wrong turn worth recording.** The first attempt at the clearing half put the hook in
  `.git/hooks` on a machine with a **global** `core.hooksPath`, so Git never looked there. The
  checker said so precisely and was right; the fixture was wrong. This is the hazard
  `topics/11-concurrency.md` describes — establish what actually runs by reading the resolved hooks
  path, never by assuming the default.
- `tests/test_adopt.py::test_a_chained_install_declares_the_chain_and_claims_local_hook` — both
  directions plus both negatives (an unchained profile carries no `hook_chain` key and is never
  asked the question).
- `tests/check_code_registers.py::hook_target_agrees` — `adopt` and the checker name the same hook
  path. Two copies of one fact, and a profile declaring a path the checker did not look for would
  pass while guarding nothing.

## Limitations

- **Only the chained case.** `H24` holds the wider one.
- **Declaring is not delegating.** Nothing here makes an adopter's hook actually call the gate; it
  makes the profile say that it should, so the checker can find out. That is the whole point of
  `DR-66` and it is worth not overstating: a repository can declare the chain, fail `SP038`, and be
  exactly as unprotected as before — the difference is that it now knows.
