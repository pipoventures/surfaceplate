# Decision Record

- Decision ID: DR-82
- Date: 2026-09-09
- Application: Surfaceplate (the framework itself) — whether a list of discovered candidates is an
  offer or the set of permitted answers.
- Decision owner: Mario Pipo (maintainer), taken during his own walkthrough of `A-stranger`. Route
  and cap value both chosen by him; drafted by the agent under `ACT-093`; confirmed by merging.
- Status: accepted — implemented by `ACT-093`.
- Risk level: 3 — it changes what every adopter may answer on every structural field, and it
  relaxes a constraint rather than adding one, which is the direction needing most care.
- Related work item: `ACT-093`; **closes `F147`**; **amends `DR-38` (2)** in place; reads against
  `DR-54` (1) and `F38`.

## Decision

**A list of discovered candidates is an OFFER. It is never the set of permitted answers.**

1. Every field `plan._from_candidates` builds carries `plan.TYPE_A_PATH` as a row — *"… type a path
   we did not find"* — which reveals a text box the adopter types into. Above the candidates, so it
   is visible without scrolling.
2. **The field's own validator still rules, unchanged.** `tracked_path`, `ci_step` and
   `scanner_workflow:<name>` each re-check the repository, so a typed value is accepted on exactly
   the terms a picked one is and refused in the checker's own words otherwise.
3. `TYPE_A_PATH` is never a proposal. `defaults.propose_controls` filters it beside `spec.seed`,
   on the same ground: it is an action the adopter takes, not a thing discovery found.
4. **A dropdown states how many candidates were found, not only how many it shows** — `(12 of 30
   found)` where those differ.
5. `rank_for_gate` ranks and no longer cuts. `plan._from_candidates` is the one place that cuts.
6. With nothing found and no seed, the field still degrades to the plain text box `DR-38`
   specified. A one-row dropdown saying *"type a path"* would be a click bought for nothing.

**`discover.SHOWN` stays at 12.**

## Context and alternatives

`F147` records the reproduction. The short form: on a real 30-document repository the maintainer
reached a gate whose precondition he could name and the interface could not hold. The list showed
twelve `activity/ACT-nnn.md` files, the gate had no seed, and a `Select` cannot be typed into.

**The constraint was never the standard's.** `flow.py` does not check an answer against
`spec.choices`; the only gate is the validator. A scripted adoption (`--answers`) could always name
any tracked file. So the restriction lived in one widget, and `DR-38` (2) — *selection over free
text, but only where a candidate list is honest* — had been implemented as something stronger than
it said. **This record amends that clause in place rather than adding a banner beside it**: the
qualification *only where a candidate list is honest* is the operative half, and a list that cannot
be complete is not made honest by refusing everything outside it.

### Rejected: a keybinding to switch the field to free text

Discoverable only from the footer. `F147` was found by an adopter who could not see a way out; an
escape he would not have seen either is not one.

### Rejected: an editable combo box

Textual's `Select` is not editable, so this meant a bespoke widget — an `Input` with an attached
`OptionList` — replacing a widget three screens rely on, to gain what one extra row gains. `D4`.

### Rejected on measurement: raising `SHOWN` to 40

Proposed by the agent and initially accepted, **on a stated reason the register contradicts**. The
agent said twelve had been sized for an 80×24 terminal. `F38` set it at twelve on this maintainer's
own evidence from the Plutos run — *"too many options to know which one is the right one"*, about
forty candidates — fixed by ranking per gate **and** cutting to twelve. Raising it would have partly
reverted a fix he asked for.

Measurement then settled it against the raise on its own terms. The four trial repositories hold
**30, 186, 239 and 267** candidates. Forty would have shown all of the first and 40 of 267 on the
last: the truncation moves, it does not go. Ranking does not rescue it either —
`work_registration`'s keywords match **205 of 239** candidates on `B-no-deps`, so the ranked list is
barely more discriminating than the alphabetical one it replaced.

**No value of `SHOWN` is the mechanism for naming a file the list omits.** Typing is O(1) in
repository size where picking is O(n). The cap therefore decides only how long the *convenience*
list is, and twelve is the value the maintainer's own evidence already chose. The honest count is
what makes the remainder visible rather than silent.

### Noted, not decided: a dropdown may be the wrong instrument above ~50 candidates

At 186–267 candidates neither a cap nor keyword ranking discriminates. A type-to-filter list would.
This is recorded as a known limitation rather than fixed here — the escape row removes the dead end,
and building a filtering widget on a guess about how adopters would use it is what `D4` and topic 5
exist to refuse. Raise it as a finding if a second adopter meets it.

## Impact

- `plan.py`: `TYPE_A_PATH`; `FieldSpec.found_total`; the escape row in `_from_candidates`.
- `discover.py`: `rank_for_gate` no longer cuts; the `SHOWN` comment rewritten in place, since it
  asserted a duplicate cap that no longer exists and a rationale that was never the whole one.
- `defaults.py`: two `found_only` filters exclude the sentinel.
- `tui/screens.py`: `EscapableSelect` and `SelectOrType`. **The reveal is wired on the widget, not
  on either screen** — `F143` was one missing `@on(...)` on one of two screens that needed it, and
  a rule living with the widget cannot be half-installed. The controls form, the gate catalogue and
  the single-field change screen all get it without a line of their own; the event still bubbles, so
  each screen's own handler runs after.
- **`adopt --edit` stops silently dropping an off-list value.** `_widget_for` discarded a pre-filled
  value not among the choices, so a hand-maintained profile lost an artefact path and was re-asked
  for it. The escape row is what lets the interface hold it at all.

## Evidence

- `tests/test_adopt_tui.py::test_every_select_field_can_be_answered_off_the_list`, 13 checks. The
  invariant is stated for every `select` field on both screens, not for the one field driven; the
  fixture is built so the target is genuinely beyond the cap, and that is asserted before anything
  else, because a fixture that does not truncate would prove nothing. **Both directions**: a real
  tracked file off the list is typed, read back, and committed by `Ctrl+S`; a path that does not
  exist is refused at the field with `tracked_path`'s own words. An escape that accepts anything is
  a hole, not an escape.
- `tests/test_discover.py::test_the_cap_is_on_the_offer_not_on_the_answer` strengthened: the cap
  counts **candidates, never rows**, so the real cap cannot drift upward one action row at a time.
- All fifteen suites `PASS` in a CI-shaped environment. `test_install_and_check` fails on a base
  interpreter without `textual` — `FAIL - ENVIRONMENT/DEPENDENCY`, the no-terminal check taking the
  missing-dependency path (rc 2) instead of the usage path (rc 3); `PASS` at 351 checks where
  `textual` is present, which is what CI runs.
- `tests/test_adopt_snapshots.py`: **10 snapshots pass unchanged, and no regeneration was needed.**
  Predicted otherwise before the work; the prediction was wrong. The fixture renders three dropdowns
  including a seeded one, the hidden box and the `VerticalGroup` wrapper add no rendered height, and
  the prompt string is unchanged where found and shown agree. The escape row lives inside the
  collapsed overlay, which no snapshot expands — a real gap in that suite's reach, covered by the
  pilot test above rather than by a picture.
- `tests/test_adopt_matrix.py`: see `ACT-093`'s entry for the run and the report's state.

## Limitations

- **The escape trusts the validator completely.** That is the argument for it — the validator was
  always the real gate — but it means a field whose validator is weaker than its candidate list
  would now accept more than it should. None is today: all three re-read the repository. A future
  `_from_candidates` field with a weak validator would inherit a hole, so the validator is the thing
  to review when one is added.
- **Nothing here improves ranking**, which is the other half of why the right answer was hard to
  find. Declined above with the measurement that motivates it.
