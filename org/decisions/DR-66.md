# Decision Record

- Decision ID: DR-66
- Date: 2026-09-08
- Application: Surfaceplate (the framework itself) — the installer's hook behaviour, the profile
  contract, and what a `local_hook` enforcement claim establishes.
- Decision owner: Mario Pipo (maintainer), taken in this session
  (https://claude.ai/code/session_018oJ1Lx22WhxVF9moPuuMQn) from three mechanisms put with a
  recommendation. Drafted by the agent; the mechanism chosen by the maintainer.
- Status: accepted — implemented by `ACT-064`.
- Risk level: 3 — a security-boundary change. It alters what the local enforcement layer
  establishes in every adopting repository, and it makes `check_conformance.py` execute a script
  where previously it only read files.
- Related work item: `ACT-064`; implements `DR-1` (2026-08-30, accepted and unimplemented since);
  findings `SP038`, `F28`; supersedes nothing.

## Decision

**`DR-1`'s opt-in chaining is implemented, and a declared chain is verified by effect.**

1. **The installer's refusal stays the default.** An install into a repository whose
   `core.hooksPath` is already set elsewhere still stops and writes nothing. `--chain` is the
   explicit opt-in: it installs `.githooks/pre-commit` and **leaves `core.hooksPath` exactly as it
   was**, so the adopter's own hook keeps running and is responsible for calling the gate. The
   choice is recorded as `hooks: "chained"` in `INSTALL.json`, beside `DR-29`'s `"declined"`.
   `--chain` and `--no-hooks` are refused together: they are opposite answers to one question.
2. **The profile declares the chain.** `adoption.hook_chain` carries `delegates_to` and a
   `rationale`. It is **optional and additive**, so `schema_version` stays `"1.0"` and no existing
   profile migrates — `DR-50`'s precedent, stated in the schema's own comment.
3. **The checker verifies it by effect.** Where the active hook's digest does not match the
   shipped gate — which is what every *honest* delegation looks like — and a chain is declared,
   `check_conformance.py` runs the hook Git will actually run with `SURFACEPLATE_HOOK_PROBE=1`.
   The shipped gate answers by exec'ing the checker with `--probe`, which prints a token and exits
   without checking, staging or writing anything. The token coming back establishes that the path
   Git takes **arrives** at this standard's gate.
4. **Reaching the gate is not enough; the gate must be unmodified.** Before probing, the checker
   confirms `delegates_to` names the gate this standard installs and that the gate's digest still
   matches the install record. Reaching an edited gate establishes nothing.
5. **Declaring is the claim.** A chain that works but is undeclared still raises `SP038`. The
   finding is about what the profile asserts, not about hook topology.

## Context and alternatives

`DR-1` was accepted on 2026-08-30 and never implemented; it anticipated exactly the condition this
repository then produced. `SP038` compares the digest of the hook at the active hooks path against
the gate this standard shipped (`F28`'s remedy). That test is correct and cannot pass a delegation:
a delegating hook is a *different file* by construction, so the check fails every honest chain and
passes none. Meanwhile the gate genuinely ran.

**Two mechanisms were rejected, and the second is the one worth recording.**

- **Declared but unverified** — permit the declaration and report on every run that the delegation
  cannot be checked, in the shape of the existing declined-hook note. Rejected because it does not
  dissolve the condition, it renames it: the claim becomes uncheckable by design, which is the
  thing this framework exists to catch elsewhere. Choosing a corner is not the same as dissolving
  the trilemma, and this record says so explicitly so the two are not confused later.
- **Verified by static reference** — confirm the declared target exists, is executable, matches its
  recorded digest, and that the active hook's *text* names it. Cheap, deterministic, and no new
  execution surface. Rejected because a textual reference is not proof of reach, and the failure it
  admits is **`F28` repeating one layer out**: *"some hook exists"* would become *"some hook
  mentions the gate"*. `tests/test_install_and_check.py` now carries that exact hook — one that
  names `.githooks/pre-commit` in a comment and exits 0 — as a scenario that must fail. A static
  check passes it.

## Impact

- **Security/data: this is the substantive one.** `check_conformance.py` previously read files and
  ran `git`; it now executes the repository's active pre-commit hook when, and only when, a chain
  is declared and the digest test has already failed. Relative to Git, which runs that same script
  on every commit, this adds no new exposure — but it is a real change to what the checker does,
  and it is why this record exists rather than the change being made as an implementation detail.
  The probe is bounded by a 30-second timeout so a wedged hook is a finding rather than a stall.
- Contracts/schemas: one optional property. Additive; `schema_version` unchanged; no migration.
- Numerical/model output: none.
- Reproducibility/lineage: `INSTALL.json` gains a third value for `hooks`, so a later reader can
  tell whether `core.hooksPath` was this standard's doing.
- Operations/release: ships in `0.17.0`.

## Evidence

- **Verified by effect on this repository**, which is the case that produced the condition: with
  the chain undeclared, `SP038` fires; with it declared, `python3 .standards/check_conformance.py`
  returns `PASS - all conformance checks satisfied`, 22 days before the grace window closed.
- **`tests/test_install_and_check.py`**, `test_a_declared_hook_chain_is_verified_by_effect`, 18
  checks against real repositories with `core.hooksPath` genuinely set: a chain that reaches the
  gate passes; one that only *names* it fails; one reaching a different `pre-commit` fails; one
  reaching an *edited* gate fails; a working but undeclared chain fails; a declaration naming
  something other than the shipped gate fails; an undeclared foreign hooks path still refuses at
  install; `--chain` installs without refusing and leaves `core.hooksPath` untouched; `--chain`
  with `--no-hooks` is refused. `INSTALL_CONFORMANCE=PASS (265 checks)`.
- Independent review: none. No party outside this repository has examined it.

## Limitations and follow-up

**The probe detects a chain that does not reach the gate. It does not detect an adopter who
forges the token**, and is not meant to: the token is a constant in a public repository, and an
adopter willing to echo it could equally decline to claim the gate at all. This is the same ceiling
the framework declares everywhere else — detection, not prevention — and it is stated here rather
than left for a reader to infer from the code.

The probe requires the *whole payload* to be current: an out-of-date vendored checker does not know
`--probe`, so an adopter who upgrades the gate without upgrading the checker sees the chain fail.
That is correct behaviour and it is also the first concrete case for the currency check `F124`
records.

Untested against a chain more than one hop deep, and against Windows, where hook execution differs.
