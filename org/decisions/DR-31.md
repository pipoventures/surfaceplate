# Decision Record

- Decision ID: DR-31
- Date: 2026-09-01
- Application: Surfaceplate (the framework itself) — a decision about how it is packaged and
  distributed.
- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in
  `org/decisions/README.md`.
- Status: accepted — implemented in the same change.
- Risk level: 2 — it decides the payload's on-disk shape for every future distribution channel,
  and moves files every internal reference in this repository depends on.
- Related work item: `ACT-019`. Item 1 of `org/RELEASE_PLAN.md`. Amends `DR-12`. Raises `F30`
  again (see `GX-0002`).

## Decision

**The payload is physically nested under one package directory, `surfaceplate/`.**
`standard/`, `schemas/`, `core/`, `templates/`, `examples/`, `adapters/`, `VERSION`,
`MANIFEST.sha256`, and the two scripts that were `scripts/install_standard.py` and
`scripts/check_conformance.py`, all move there unchanged. `repo_root()` becomes
`Path(__file__).resolve().parent` — a single `.parent`, not `.parent.parent` — because this file
now lives inside the tree it locates.

## Context and alternatives

### What was actually left to solve

`DR-10` flagged, and left unsolved, that `install_standard.py`'s file-location mechanism does not
survive pip distribution: `repo_root()` and `build_payload()` resolved directories that sit outside
any importable package. `DR-12` committed to pip distribution as scope. No sibling repository
(mnemosyne, hermes, plutos, prometheus, actually-using-ai) has attempted this before — confirmed by
exhaustive search before design began.

**A correction found before any design started.** `DR-10`'s pinning mechanism — a wheel-file digest
disambiguated by `adoption.distribution_channel` — was superseded by `DR-14`, already accepted and
implemented: `framework_digest` is `sha256(MANIFEST.sha256)`, channel-neutral by construction,
identical whether the code arrived by git clone or `pip install`. `SP048`/`SP049` needed no changes.
`DR-12`'s prose still cited the superseded mechanism; corrected below rather than left standing.

So the genuine remaining work was narrower than `DR-10` framed it: **only the file-location
mechanism**, not pinning.

### The layout choice

Two options were surfaced. Physically move the payload under `surfaceplate/`, against mapping the
package to the repository root without moving anything (`package_dir={"surfaceplate": "."}`, with
explicit include/exclude globs reaching into `standard/`, `schemas/` and the rest in place).

**Physically moving was chosen**, on the maintainer's decision, accepting that every internal
reference across the repository would need updating. The alternative would have preserved every
existing path reference untouched, at the cost of a less idiomatic packaging configuration with no
working precedent anywhere in this session's evidence base, and a real risk of `tests/`, `org/` or
`.git`-adjacent content being swept into the wheel by an incomplete exclude list.

### The simplification the layout choice produced, and it was not anticipated going in

Because `install_standard.py` and `check_conformance.py` moved **inside** the payload tree,
`__file__`'s own parent directory became the payload root directly. The fix to `repo_root()` is one
line.

**No `importlib.resources` rewrite was needed.** Both research passes conducted before design began
this packet under the premise that one would be — reasonably, since that is the standard remedy for
"a package needs to locate its own data files reliably." It is not needed here because
`Path(__file__).resolve().parent` resolves correctly for a git checkout, a normal (unpacked)
`pip install`, and an editable install (PEP 660) alike — pip unpacks a wheel to real files on disk
in every ordinary configuration, and an editable install makes the existing source tree importable
without copying it. **Proven, not assumed**: the acceptance test below built a real wheel, installed
it into a virtualenv with no surfaceplate source tree reachable, and successfully installed the
standard into a fresh repository using only the pip-installed copy.

The one case this does not cover is a legacy zip-safe/zipapp-style install — essentially obsolete
for modern wheel-based pip, and something no adopter has asked for. Recorded as a deliberate,
stated boundary (D4 — least complexity the objective genuinely justifies) rather than built against
a hypothetical, the same way `DR-25`/`DR-26` record what pattern C deliberately does not attempt.

### Build backend

**Hatchling**, for `pyproject.toml`-only configuration with no `setup.py`. `packages = ["surfaceplate"]`
was sufficient with no further include/exclude configuration — verified by building a real wheel and
listing its contents directly: 54 entries, every one under `surfaceplate/` or the dist-info
directory generated for it. Nothing from `tests/`, `org/`, `activity/`, or anywhere `.git`-adjacent.

### What stays where it is, and why

`scripts/build_release.py` and `scripts/verify_release.py` are maintainer-only release tooling,
never part of what an adopter `pip install`s, so neither moved. `build_release.py`'s internal
references were updated to import from the new location and to read `VERSION`/`MANIFEST.sha256`
from inside it. `tests/`, `org/`, `activity/`, `governance/`, `.github/`, `.claude/`, `.standards/`
(this repository's own self-installed *target*, unaffected by where the source lives), and
`prompts/` are all untouched.

### The self-install guard, re-examined rather than assumed safe

After the move, `source` (`surfaceplate/`) and `target` (repo root) are always different paths by
construction, so a legitimate self-install can never trigger `target == source` — but this was
already true before this packet, since self-install has never used the bare default; it has always
extracted a fresh copy and pointed `--source` at it. Nor could `DR-10`'s flagged mixed scenario (a
pip-installed tool, `--source` pointed at an unrelated local clone of the same content) be caught by
path equality either way. **Still deferred, re-confirmed rather than silently carried over**: no
console-script exists yet (item 2), so the realistic footgun is not yet exercisable by anyone.

### `F30` fired again, immediately, on the next rename of the same file

`test_convention`'s precondition artefact — the testing-convention document — moved a second time
in one session: `standard/agent-instructions/tests.md` to
`surfaceplate/standard/agent-instructions/tests.md`. The history audit resolved the precondition at
its **current** path and reported the commit that made the *previous* rename (`DR-30`/`F29`) as a
violation, for the same reason `GX-0001` already exists. Cleared by a second exception,
`governance/exceptions/GX-0002.yaml`, covering the one affected commit.

**This is the sharper finding.** `F30` was recorded as an open limitation with a candidate remedy
(follow renames through git) explicitly left unbuilt. It has now bitten twice in the same session,
from two renames this project chose for its own good reasons. Two occurrences is stronger evidence
than the finding had when first written that the deferred remedy deserves higher priority — and it
is **still not built here**: it is real, non-trivial work (`git log --follow` is heuristic and
single-path), and building it as a side effect of a packaging packet would be exactly the scope
creep this project's own working method exists to catch. `F30`'s entry is not reopened or
re-severity-rated by this record; the evidence is added to it.

### Two pre-existing defects found and corrected while sweeping every reference

Neither is this packet's own creation, and both were found only because moving the payload forced a
line-by-line reading of every document that names its location.

- **`governance/authority-map.yaml`** pointed `activity/**`'s authority at
  `standard/agent-instructions/activity.instructions.md` — a Copilot-emitted filename, not the
  canonical one. Stale since `DR-30` dropped that suffix from the canonical instructions; nothing
  had caught it because nothing validates `governed_by` targets against the filesystem, by design
  (`DR-24` already records that a licence-boundary reader is trusted, not checked — the same shape
  applies here).
- The same file's note on `DR-14` said the pinning mechanism was *"decided but not implemented"* —
  false since `DR-14`'s own acceptance. Corrected in the same pass.

### Alternatives rejected

- **Mapping the package to the repository root.** The maintainer's decision, above.
- **Building `importlib.resources` machinery pre-emptively.** Rejected once the simpler mechanism
  was shown to work by an actual acceptance test; building the more complex version first and
  discovering it unnecessary would have been complexity ahead of evidence.
- **Building content-based self-install guard now.** Deferred, re-confirmed above.
- **Extending `GX-0001` to cover the second rename** rather than writing a second exception.
  Rejected: `GX-0001`'s rationale and remediation are specifically about the `DR-30` rename and
  would misdescribe the `ACT-019` rename if stretched to cover it. One exception record documents
  one incident.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** one schema description string corrected for accuracy (adopter-relative
  paths for the checker and the gates document); no `$id` change, since content is unchanged in any
  way that affects validation.
- **Security/data:** none. The acceptance test confirms the built wheel contains only
  `surfaceplate/` and its own dist-info.
- **Operations/release:** `pip install surfaceplate` now gives an importable package with the
  installer and checker inside it. There is still **no console-script entry point** — that is
  item 2, deliberately separate, so the CLI is a decision rather than a side effect of packaging
  becoming possible. Until then, invoke as `python -m surfaceplate.install_standard`.
- **Every internal reference in this repository was checked and, where necessary, updated**: five
  test suites, the self-check workflow, `README.md`, `INSTALL.md`, `NAMESPACE.md`, `ORGANISATION.md`,
  `RECONCILIATION.md`, `governance/authority-map.yaml`, and eight `gated_activity.paths` /
  `precondition.artefacts` entries in this repository's own `application-profile.yaml`.

## Evidence

- **The acceptance test.** A real wheel built with `python -m build` in an isolated environment.
  Its contents listed directly: 54 entries, all under `surfaceplate/` or its dist-info. Installed
  into a clean virtualenv — confirmed to have pulled in the pinned `PyYAML==6.0.3` and
  `jsonschema==4.26.0` automatically. From that virtualenv, with **no surfaceplate source tree
  reachable**, `python -m surfaceplate.install_standard --target <fresh throwaway repo>` installed
  the standard successfully, and `.standards/check_conformance.py --repo .` ran against it and
  produced a coherent result (a template-incomplete `WARN`, exactly the expected state of a fresh
  install — not a crash, not a missing-payload error).
- Five suites pass with identical counts to before the move (`164 / 170 / 121 / 10 / 57`),
  confirming the relocation changed no behaviour it was not meant to.
- The manifest rebuilt and verified from the new location; `PASS` on both the source and the
  self-installed vendored checker copy.

## Limitations and follow-up

- **`importlib.resources` is not used, deliberately**, and the one distribution shape it would have
  covered — a zip-safe/zipapp install — does not work. Stated as a boundary, not hidden.
- **No console-script entry point.** Item 2's work.
- **The content-based self-install guard `DR-10` anticipated is still not built.** The realistic
  footgun does not yet exist without a console script to invite it.
- **`F30`'s remedy — following renames through git — is still not built**, despite firing twice in
  one session. The evidence for building it sooner is now stronger than when the finding was first
  recorded; the decision to build it is not taken here.
- **The acceptance-test wheel's digest does not equal this repository's own pinned one, and it is
  not supposed to — checked directly rather than left as an apparent inconsistency.** Every field
  in the record above is verified, so this is too: the wheel's `MANIFEST.sha256`, extracted and
  diffed, is byte-for-byte identical to this repository's own on-disk copy, and both hash to the
  same value the acceptance test recorded. What differs is this repository's *own* pinned
  `framework_digest` inside `governance/application-profile.yaml` — and the reason is the
  self-reference the profile's own comment already documents: pinning the digest **edits the file
  whose bytes are part of the manifest being pinned to**, so the value written can never equal
  `sha256` of the manifest computed *after* writing it. `SP049` does not require that equality — it
  compares the profile's declared value against `.standards/INSTALL.json`'s recorded one, both
  frozen at the same install, and those agree. Confirmed directly: both read `fd25b54a…` in this
  repository as shipped. This is `F6`'s self-reference in the specific place `DR-14`'s own comment
  predicted it, not a defect introduced by this packet.
