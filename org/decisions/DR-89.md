# Decision Record

- Decision ID: DR-89
- Date: 2026-09-24
- Application: Surfaceplate (the framework itself). This decides whether the conformance checker
  accepts a YAML file that repeats a key in one mapping.
- Decision owner: Mario Pipo (maintainer). The three choices below were taken in session on
  2026-09-24, each from an explicit option set: a new SP code rather than an existing one, fail
  rather than warn or grace, and every parse site rather than the profile alone. Drafted by the
  agent under `ACT-115`; confirmed by merging.
- Status: accepted — implemented by `ACT-115`.
- Risk level: 3. It changes what the shipped checker asserts, and it can turn an adopter's passing
  run into a failing one on upgrade.
- Related work item: `ACT-115`; closes `F179`.

## Decision

**The checker refuses a repeated key.** It reports `SP061` in every file an adopter authors and
the checker reads:

- the working and staged application profile;
- records under a declared register;
- gate exceptions, working and staged;
- the workflow files searched for a CI step;
- a scanner's wiring file.

`SP061` replaces the site's own unreadable-file code (`SP011`, `SP041`, `SP043`, `SP056`) when a
repeated key is the cause, and it is **never graced**.

**One read stays lenient: a profile in a past commit** (`earliest_declared_effective_from`). A committed
profile cannot be corrected, and refusing one would change what the checker concludes about the
past. This repository's own history carries `F179`'s duplicate from 2026-09-19 to 2026-09-24, and
refusing it would drop those revisions from the effective-date history `SP034` depends on.

## Context and alternatives

YAML forbids a repeated mapping key. PyYAML's `safe_load` accepts one and keeps the **last**
value, with no warning. So the document the checker evaluates is not the one its author wrote, and
the discarded half is invisible to every tool that reads the file. `F179` is the instance: this
repository's profile carried two `adoption.hook_chain` blocks for five days, and the stale one
won. Nothing failed, because both named the same gate. That is the case that makes the defect
dangerous rather than harmless: a discarded declaration that differs from the survivor would fail
or pass for a reason nobody could see.

Alternatives, and why each was not taken:

- **Reuse each site's existing unreadable-file code.** That would say the file cannot be parsed,
  which is less than true, and hide the one cause an adopter can fix in a line. The loader error
  already names the key and both line numbers; a code of its own lets the report say what to do.
- **Advisory only.** It would leave the silent override in place while announcing it. A checker
  that reports a finding and still evaluates the discarded-half document is the
  declared-versus-verified gap this framework exists to close.
- **Fail after a grace window.** Softer for an adopter with a latent duplicate, but it would run a
  window in which the checker evaluates a document known to be wrong.
- **The profile alone.** It is narrowest, but it leaves the same defect live in exceptions and
  records one function away. That is `F176`'s shape: a sibling path left behind.

**How a workflow is handled**, the one site with a cascade. A CI step named by
`deterministic_tests` or `contract_tests` may sit in the workflow that could not be read, so
`SP053`'s "no such step" is not established there. It is suppressed while any searched workflow
is refused, and `SP061`, which is blocking, reports the cause. This is the rule that a negative
finding must show its observation could have succeeded, applied the way `DR-27` avoided an
`SP057` cascade behind `SP056`.

**Merge keys are not duplicates.** An explicit key overriding a `<<:` default is YAML's intended
use of merge, and it is accepted. Only keys written in the same mapping are compared.

**Standard-owned schemas** go through the same loader but keep their own codes (`SP014` and the
record-validator path). A repeat there is the framework's defect, not the adopter's. A suite test
asserts that every YAML file the standard ships is free of repeated keys, so that case is caught
at the source rather than in an adopter's report.

## Impact

- Numerical/model output: none.
- Contracts/schemas: a new finding code, `SP061`, blocking and never graced. No schema changes.
  The code-space declaration in `org/FINDINGS.md` and the generated catalogue in
  `core/CONFORMANCE_LEVELS.md` both carry it; `SP_TOPICS` maps it to Topic 12.
- Security/data: none.
- Reproducibility/lineage: none. The history read that `SP034` depends on is deliberately
  unchanged.
- Operations/release: **an adopter whose profile, records, exceptions or workflows repeat a key
  will fail on upgrade**, including inside the adoption grace window. The remedy is to delete one
  of the two keys. That is the decision, not a side effect.

## Evidence

- Code/configuration: `surfaceplate/check_conformance.py` (`DuplicateKeyError`,
  `unique_key_loader`, `parse_yaml`, `duplicate_key_finding`, `workflows_with_duplicate_keys`,
  and the call sites); `surfaceplate/rules.py` (`SP_TOPICS`).
- Tests/checks: `tests/test_install_and_check.py`,
  `test_a_repeated_key_is_refused_wherever_an_adopter_can_correct_it` and
  `test_every_yaml_file_the_standard_ships_is_free_of_repeated_keys`. Each case has a negative
  control. Shown failing against the unmodified checker (four failures, then an `AttributeError`
  at the loader test) and passing against the change. The suite had one latent duplicate of its
  own, a fixture that orphaned a `rationale:` line, and it is corrected in the same change.
- Runtime evidence: this repository's own profile, once corrected under `F179`, passes the
  checker with no `SP061`.
- Independent review: none. See `README.md`'s decision-maker convention.

## Limitations and follow-up

- `surfaceplate adopt` was out of this decision's scope. Its `--edit`, `--repin` and
  `--answers` read with `safe_load` and rewrite a whole profile, so a repeated key was resolved
  silently. That was confirmed by effect as `F180` and fixed under `ACT-116`: the wizard now
  refuses a repeated key with the checker's own loader before it writes anything.
- A key repeated across two *documents* in one file, or across a merge, is not a repeated key
  and is not reported.
