## Decision

**Every finding code belongs to one of the twelve topics, and every finding says which.**

1. `rules.SP_TOPICS` maps all 57 emitted codes to a topic. **No renumbering**:
   `SP001-SP035`, `SP037-SP043`, `SP046-SP060` are unchanged, and the gaps stay.
2. `Finding.__init__` looks the topic up — `self.topic`, `self.topic_name`. **No call site
   changes**, so none of the hundred-odd constructions in `check_conformance.py` moved, and none
   can be built with a topic that disagrees with the registry.
3. `render_json` emits `topic` and `topic_name`; SARIF carries both in the `properties` bag the
   specification provides for exactly this.
4. `check_code_registers.py` gains three assertions: every emitted code has an entry, the registry
   names no code the checker does not emit, and every value is one of the twelve.

## Context and alternatives

`DR-69` gave the reason: *a field nobody can query is not a field*. A report of fifteen findings
identified only by number cannot be read by subject, routed to whoever owns that subject, or
filtered. With the topic present, a fresh install's fifteen findings group as **1 authority,
1 confidentiality, 13 enforcement** without a lookup table.

**The rule that decides the hard cases, and it needed stating: a code's topic is the subject the
finding is ABOUT, not the mechanism that detects it.** `SP008` (the conformance block has been
altered) is detected by a digest — enforcement machinery — but its subject is the block that
declares what governs the repository, so it is Topic 1. `SP004` and `SP005` are detected the same
way and *are* about the installed standard, so they are Topic 12.

**Rejected: passing the topic at each call site.** It would have let a finding be constructed with
a topic contradicting the registry, and it would have touched every construction in a 3,900-line
file to gain nothing the lookup does not.

**Rejected: renumbering the codes into topic-shaped ranges.** Explicitly forbidden by the
programme's standing constraints, and rightly: the codes are cited in decision records, the
changelog, two test suites and adopters' own suppression lists. Renumbering breaks every citation
for a cosmetic tidy — `org/FINDINGS.md`'s own numbering convention makes the same argument about
`F` codes.

## The distribution, stated rather than smoothed

**Forty of the fifty-seven codes are Topic 12.** That is uncomfortable and it is honest, so it is
recorded rather than fixed by spreading codes about until the table looks balanced:

- **33** are the install, the profile, the levels and the gate machinery. Their subject genuinely
  *is* enforcement and change control. Most of what this checker emits is about its own apparatus,
  which is a true and slightly awkward fact about the tool.
- **7** are **control- or gate-generic** and cannot honestly carry one topic at all. `SP051` fires
  for `dependency_lock` (Topic 9) and for `assurance_findings` (Topic 6) alike, and the code does
  not know which until it fires. Topic 12 is the least wrong answer for them, and a consumer
  wanting the control's own topic has it: the finding names the control, and `CONTROL_TOPICS` maps
  it.

**Seventeen codes carry a specific subject**, and those are the ones the axis earns its keep on —
`SP046`/`SP047` to confidentiality, `SP054` to provenance, the adoption-record and canon codes to
authority, the deferral and exception codes to decision authority.

## Impact

- `--format json` findings gain `topic` and `topic_name`; SARIF results gain
  `properties.topic` / `properties.topicName`. Additive: a consumer reading the previous shape is
  unaffected, which is why `surfaceplate.format` stays `"1.0"`.
- `rules.py` gains `SP_TOPICS`. Payload, beside `CONTROL_TOPICS` and `TOPIC_NAMES`, so the three
  parts of the topic axis live together.
- `check_code_registers.py` 122 → 125 checks; `test_install_and_check.py` 333 → 339.

## Evidence

- A real fresh install, checked: 15 findings, every one carrying a topic number and its name, every
  number one of the twelve, and the name matching `TOPIC_NAMES`. SARIF carries the same in
  `properties`.
- `Finding("SP046", …).topic == 8`, asserted, so the registry is authoritative rather than
  advisory.
- The three register assertions fail if a code is added to the checker without a topic, if the
  registry names a code that is not emitted, or if a value is outside 1–12.

## Limitations and follow-up

**A control-generic code's topic is the least wrong answer, not the right one.** Resolving it per
*finding* — from the control the finding names — would be the right one, and would require passing
the topic at the seven generic codes' call sites, which this record rejected for a different and
still-good reason. If that trade ever looks wrong, the change is local to those seven.

**Nothing consumes the field yet.** It is emitted and checked, and no report groups by it. That is
the correct order — a field must exist before anything can read it — but it means the claim here is
*"the data is present and correct"*, not *"the data is useful"*, and only an adopter using it can
establish the second.
