# Decision Record

- Decision ID: DR-73
- Date: 2026-09-09
- Application: Surfaceplate (the framework itself) — what the `essential` conformance floor requires
  of a repository that has no dependencies.
- Decision owner: Mario Pipo (maintainer), taken in answer to `H22`, which was put with three
  costed routes; the maintainer chose **(1)**, *derive applicability and check it*. Drafted by the
  agent under `ACT-078`; confirmed by merging.
- Status: accepted — implemented by `ACT-078`.
- Risk level: 3 — it changes what every adopter's conformance check enforces, and it removes an
  obligation rather than adding one, which is the direction that needs the most care.
- Related work item: `ACT-078`; **closes `F132`** and `H22`; amends `core/CONFORMANCE_LEVELS.md`.

## Decision

**`dependency_lock`'s level floor does not apply to a repository that tracks no dependency manifest
of any kind. The exception is derived by the checker from the repository itself, never declared in
the profile.**

1. `rules.dependency_manifest(repo)` answers `found` / `none` / `unknown` from the adopter's own
   tracked files, against a deliberately generous list of manifest names and suffixes.
2. `check_conformance.report_waived_controls` lifts the `SP021`/`SP022` floor for
   `dependency_lock` when the answer is `none`, **and says so in the report on every run**.
3. The wizard reads the same function through `plan.level_floor`, so it cannot ask for something
   the checker has decided it does not need, nor omit something the checker will still demand.
4. `control_decisions` may now be empty. At `essential` the waived control was the whole floor, so
   `minProperties` moves from `1` to `0`, and the renderer writes `{}` rather than a bare key.
5. **Only the floor is lifted, never a check.** A repository that decides `dependency_lock`
   required anyway is checked by `SP051` exactly as before.

## Context and alternatives

`F132` was found by the maintainer on the **first screen of the first walkthrough**, on a real
257-file documentation repository, after 45,266 matrix checks had passed. `dependency_lock` is the
only control in `CONFORMANCE_LEVELS["essential"]`; `SP021`/`SP022` require a level's controls to be
decided `required`, so `deferred` and `excluded` both fail; `SP051` requires a real tracked file.
A repository with nothing to name could not conform at any level, while the profile schema's own
`stack` field says *"The kit does not require a UI, API, or specific language"*.

**Rejected: a declared `not_applicable` decision, verified by the checker (route 2).** It is the
idiom used by `hook_chain` and `adopter_canon`, and it would have worked. It was rejected on the
narrower ground that there is nothing here for a human to contribute: whether a repository has a
dependency manifest is a fact about their tree, not a judgement about their risk. A declaration
adds a sentence that can go stale, an enum value to the published contract, and a finding code for
the case where the sentence and the tree disagree — all to record something the checker must
establish for itself anyway. Where a declaration adds no information, it adds only ways to be
wrong. `F121`'s reasoning, one level along.

**Rejected on sight: allowing `excluded` with a rationale (route 3).** Any adopter with real
dependencies could write a sentence and drop the one control this standard applies to everyone.
`dependency_lock`'s own stated reason is *"supply-chain exposure exists regardless of output
materiality"*, and route 3 would have made it advisory.

**The manifest list is generous by design, and the asymmetry is the argument.** Believing a manifest
exists where none does returns a repository to `F132`'s dead end — bad, and visible to whoever hits
it. Believing none exists where one does silently waives a real control — worse, and silent. So the
list errs towards *has dependencies*, and includes lock files themselves.

**`CMakeLists.txt` and `Dockerfile` are deliberately excluded**, stated so they read as decisions
rather than oversights. Both imply a supply chain and neither has a lock file an adopter could name,
so including them would send C and container repositories to the same dead end this record exists to
remove. A repository that pins a base image and wants the control has always been free to decide
`dependency_lock` required and name what it pins with.

## Impact

- `core/CONFORMANCE_LEVELS.md` gains the exception and the three properties that make it safe.
- `surfaceplate/schemas/application-profile.schema.yaml`: `control_decisions.minProperties` `1` → `0`.
  Strictly a **relaxation**, so no existing profile becomes invalid and `schema_version` stays
  `"1.0"`. The real enforcement was never `minProperties`; it is `SP021`/`SP022` against the
  checker's own catalogue, and they are unchanged.
- `rules.py` gains `DEPENDENCY_MANIFESTS`, `DEPENDENCY_MANIFEST_SUFFIXES`, `WAIVABLE_CONTROLS`,
  `dependency_manifest()`. Payload, and shared with the wizard as `DR-48` requires.
- `SP021`'s remedy no longer tells an `essential` adopter to *"declare a lower level"*. There is
  not one, and `F132` is precisely the case where that advice sent a reader nowhere.
- `sections.build_controls` stays **pure**. The waiver reaches it as the absence of an answer the
  plan did not ask for, not as a fresh scan — purity is what makes `--answers` replay deterministic
  and the matrix's report comparable. The omission is gated on `rules.WAIVABLE_CONTROLS`, so a
  missing rationale for any other control still raises loudly rather than dropping it silently.

## Evidence

- `tests/test_adopt.py::test_a_repository_with_no_dependencies_can_still_conform`, 14 checks,
  asserting **both directions**: with no manifest the floor lifts, the wizard stops asking, and the
  written profile passes its own schema with `control_decisions == {}`; then a `package.json` is
  added and the floor returns, `SP021` fires naming the control, and the remedy does not mention a
  lower level. A waiver that could not be revoked would be a hole, not a waiver.
- **Verified by effect on the fixture and on three real repositories.** Removing the waiver makes
  the new test fail in the way the maintainer's own run failed — *"the flow asks for
  `controls.dependency_lock.implementation_reference` and the script has no answer for it"*.
  Live, re-read after the list was broadened rather than quoted from the earlier run:
  `A-stranger` (a 257-file documentation repository) `(None, 'none')`; `B-upgrade`
  `('requirements.in', 'found')`; `C-stranger-with-deps` `('package-lock.json', 'found')`; this
  repository `('pyproject.toml', 'found')`. `B-upgrade` reported `requirements.txt` before the
  broadening and reports `requirements.in` after it — the same repository, the same verdict, a
  different file matched first. The field names *a* manifest as evidence that one exists; it is
  not the `implementation_reference`, which the adopter still chooses.
- End to end on the repository that produced `F132`: install, `adopt --propose`, adopt the
  proposal, `check` → **PASS**. Add a `package.json`, `check` → `SP021`.
- `tests/test_adopt_matrix.py`: **208 cases, 44,774 checks, PASS**, and the regenerated report's
  diff is fully accounted for — **82 rows changed, every one of shape `bare`, each losing exactly
  six checks**; 82 × 6 = 492 = 45,266 − 44,774. `rich` and `mixed` are untouched. The six are the
  assertions about a lock-file field that a repository declaring no dependencies is no longer
  asked for. No row's verdict changed and no case's outcome moved.

## Limitations and follow-up

**The shared test fixture had been in `F132`'s state all along, and that is the more uncomfortable
finding.** `make_installed_repo` built a repository with no dependency manifest, and every scripted
answer supplied a lock-file path pointing at a file that did not exist. The suite was green because
the script answered a question no real repository of that shape could answer. The fixture now seeds
a `package.json` — a manifest, deliberately not a lock file — so the ordinary case is exercised, and
the new test removes it for the case that is not.

**`unknown` was got wrong first time, and the correction is worth recording.** The first
implementation returned `unknown` both when git failed *and* when the adopter owned no tracked files
at all. That made a freshly installed repository with nothing else committed unable to conform —
`F132` again, for a different shape. `unknown` now means only *git could not answer*. What matters
is whether the question was answered, not whether the answer was interesting.

**The first version of the manifest list waived a repository that had real dependencies, and the
combinatorial matrix caught it rather than anyone reasoning it out.** `test_adopt_matrix.py`'s
`mixed` shape is built deliberately as *"a pinned-dependency file no lock-file rule names"* —
`deps/pins.txt`, holding `PyYAML==6.0.3`. Against a list of standard manifest names that file is
invisible, so the floor lifted for a repository that has dependencies, pins them, and had been
naming that very file as its `implementation_reference` until this change. **That is the silent
direction, in the one shape built to represent it.** The list now also recognises a plain file whose
name says it pins things — `requirement`, `constraint`, `pin`, `dep`, `version`, `lock` in the name,
or a `deps/`, `dependencies/`, `requirements/`, `constraints/` directory — and the matrix returned to
asking. The lesson is the fixture's, not the reasoning's: a shape built to be awkward earned its
keep the first time the rules around it moved.

**No check establishes that a repository which declares no manifest genuinely has no dependencies.**
A vendored `node_modules` with no `package.json`, or dependencies resolved by a build system this
list does not name, would be waived. The boundary is the same one `DR-25` records for every control
here: this framework checks declarations against artefacts, and cannot check the world.

## Approval

Taken by the maintainer in answer to `H22`, route (1), on the costing recorded in `F132`. No agent
approved this. The risk level is 3 because the change removes an obligation from every adopting
repository, and a removal is harder to notice than an addition.
