## Decision

**`SP038` distinguishes three states, and reports a finding for only one of them.**

| The hook Git will actually run | Verdict |
|---|---|
| reaches this standard's gate | passes |
| **is present and does not reach the gate** | `SP038` — a negative this check establishes |
| **is not there at all** | *not established* — an advisory line, never a finding |

**And `local_hook` is then derived for `installed` and `chained` installs, never for `declined`.**

The order is the decision as much as the content: the claim is only safe *because* the check was
fixed first.

## Context

`F157` records the reproduction. The short form: `local_hook` is a property of a **developer's
checkout**, and `core.hooksPath` is local Git configuration that is **never tracked**. A fresh clone
therefore has no hook by construction — and a CI runner is a fresh clone, with no staged changes to
gate either. Asking there whether the local hook is in place has no answer, and `SP038` answered it
`False`.

That is `DR-74`'s rule, written in this repository for `F133`, applied to `doctor`, and never swept
across the checker. `SP038` is the case it missed.

**It also explains a silence nobody had read as meaningful.** `F156` found that the wizard never
claimed `local_hook` and treated that as the defect. It was also the only thing protecting adopters:
claiming it would have failed their CI thirty days after install, because `SP038` is `graceable` and
grace expires. `ACT-095` removed that accidental protection for chained adopters, one day before
this was found. **The previous activity introduced a regression that the decision answering its own
follow-up question caught.**

### Why not keep the finding and exempt CI

Considered and rejected. Detecting CI means keying on an environment variable — `CI`, or
`GITHUB_ACTIONS` — which is spoofable, vendor-specific, and wrong in both directions: a developer
with `CI=true` exported gets a silent check, and a self-hosted runner with a configured hooks path
gets an unnecessary exemption. The state the checker can actually observe is *whether a hook exists
at the path Git resolves*, and that is what it now reports on.

### The cost, stated rather than implied

**A deleted hook and a fresh clone are indistinguishable from inside the checkout**, because the
configuration that would separate them is untracked. So this trades *catches a deleted hook, breaks
every CI* for *never breaks CI, cannot catch a deleted hook*.

That is a real loss and it is the right trade: the local hook is one of three enforcement routes,
`history_audit` and `review` both still run, and a check that fails every adopter's CI thirty days
after they adopt would be removed by them rather than heeded. A control nobody can live with is not
a control.

### Why claim it at all, once the check is safe

Because `SP038` and `DR-66`'s probe were otherwise unreachable. Every hook check in
`check_conformance.py` is gated on a gate claiming `local_hook`; nothing the wizard wrote ever did.
With the check no longer asserting what it cannot see, the claim costs adopters nothing in CI and
gains them a verified control on the machines where commits actually happen.

## Impact

- `check_conformance.py`: `HOOK_ACTIVE` / `HOOK_WRONG` / `HOOK_UNESTABLISHED`;
  `active_pre_commit_hook` returns the state rather than a boolean; the advisory note; `SP038`
  raised only for `HOOK_WRONG`.
- `sections.py`: `CHAINED_ENFORCEMENT` becomes `LOCAL_HOOK_ENFORCEMENT`, gated on
  `HOOKS_WITH_A_LOCAL_GATE = ("installed", "chained")`.
- `build_profile` takes `hooks` from the caller, read from the **install record** — the same place
  `framework_version` and `framework_digest` come from, so the preview and the write cannot differ.
  Purity holds: `DR-73` forbids a fresh scan *inside* a builder, not a fact handed to one.

## Evidence

All three states verified by effect, on a runner-shaped checkout of this repository:

- hook active and reaching the gate → `PASS`, no finding;
- **nothing at the resolved path** → `PASS`, with the advisory naming the claim and the reason;
- **a foreign hook that never runs the gate** → `SP038`, `FAIL` under `--no-grace`.

`tests/test_adopt.py` asserts the derivation for all three install kinds — `installed` and `chained`
claim it, `declined` does not.

## Limitations

- The advisory tells an adopter their claim was not checked *here*. Nothing makes them read it, and
  a repository whose hook is genuinely gone will now pass in CI forever. `doctor` remains the
  command that answers "is my checkout set up", and it is not run in CI either.
- This says nothing about `ci` as an enforcement value, which no profile claims and nothing checks.
