- Decision owner: Mario Pipo (maintainer), per the decision-maker convention recorded in

- Status: accepted — implemented in the same change.

- Related work item: `ACT-014`. Closes `F20`. Raises `F23`.

## Decision

**A record-based control names a directory, and every record in it must validate. An empty
directory passes.**

`implementation_reference` names a **register** for the four controls `DR-25` assigned to pattern C:

| Control | Every `.yaml` in its register must satisfy |
|---|---|
| `overrides` | `override-record.schema.yaml` |
| `method_registry` | `method-registry-entry.schema.yaml` |
| `run_lineage` | `method-run-lineage.schema.yaml` |
| `provenance` | the same record type — two properties of one record |

`SP055` covers the register: named by nothing, missing, a file rather than a directory, or holding
untracked records. `SP056` covers a record inside it: unreadable, or invalid against its schema.
Both are graceable. Non-YAML files are ignored, so a register may carry a `README.md`.

With this, **every control this framework defines is checked at every level.** `F20` — *a gate is
checked against reality; a control is checked against itself* — is closed.

## Context and alternatives

### The finding this completes

`F20`, demonstrated rather than argued: this repository was made to claim `full` and declare
`provenance`, `run_lineage`, `method_registry` and `overrides` while containing no such records, and
**the checker raised zero objections about any of them.** Patterns D, A and B closed five controls
across `ACT-011` and `ACT-012`. These four were the remainder, and the only genuinely new mechanism.

### Why an empty register passes, which is the decision this record exists to make

A validator that demanded records would be a validator that **rewarded inventing them**.

That is not a hypothetical risk in this design; it is the line the whole sequence is arranged
around. Records are cheap and git-native, and are therefore a fair thing to require. Judgements are
expensive, and requiring them is where automated fabrication lives — the reasoning that keeps
per-change risk classification deferred. A repository that has made no overrides has an empty
overrides register, and that is the *correct* state, not a deficiency. Demanding a record would
produce a fabricated one, and the framework would have caused exactly the defect it exists to catch.

So a pass here establishes **no unvalidated record exists in this register** — never that records
exist. That sentence is in `core/CONFORMANCE_LEVELS.md` in those words, because a reader will
otherwise infer the stronger claim from the same green line, and the inference would be wrong.

The cost is stated plainly rather than minimised: **an adopter who simply never files a record
passes this control forever.** Nothing here detects a run that happened and went unrecorded. What is
caught is a register that is claimed and absent, one that is unreadable, one filed with the wrong
record type, and one whose records live on a single machine.

### Tracking is asked per record, and the first implementation was wrong

The register directory is not required to be tracked, because git does not track empty directories —
requiring it would make an empty register impossible and force the fabrication above. So the
question is put of each record.

The first implementation asked it with `git ls-files --others --exclude-standard` over the
directory. That reports **nothing** for a register that is gitignored outright, which is the single
case where every record in it is guaranteed to reach nobody. It was replaced with
`ls-files --error-unmatch` per record — the same call pattern A already uses — which answers the
question actually being put.

### Why this reuses the gate-exception loader rather than adding a second one

Gate exceptions have been records-in-a-directory, loaded and schema-validated, since `0.9.0`.
`exception_validator` is generalised into `record_validator(repo, schema_rel)` and the exception path
now calls it. A second loader would have been a second place to get the `jsonschema`-absent path
wrong — and that path matters more than it looks: falling silent would report *"no invalid records"*
from a look that could not have found one. `SP043` already handles it correctly by emitting a
finding, and `SP056` mirrors it exactly.

### Two things `DR-25` claimed that did not survive implementation

Both are amended **in place** in that record, because it says the first validator built is the real
test and that a pattern which does not fit means the record is wrong.

1. **Currency is not provable for these record types.** `DR-25` claimed pattern C would prove
   records are *"current"*. No schema carries an expiry or review date; `revalidation_trigger` is a
   free-text condition, not a deadline. Nothing is declared to check against — the same shape as the
   gate exceptions `F22` left open, found again one packet later in a different contract. Twice in
   two packets is a pattern worth naming: **this framework's schemas record when something was
   created far more often than when it stops being good.**
2. **`provenance` and `run_lineage` would have collapsed.** One *record type* serves both, which
   `DR-25` establishes correctly. One *check* serving both does not follow, and would have made
   declaring `provenance` indistinguishable from declaring `run_lineage`.

> **Amended 2026-08-31 (`ACT-015`), in place.** The sentence that stood here — *"They are separated
> in `C2` by which optional fields each obliges"* — was **wrong on a matter of fact**, and it was
> written into this record before the schema had been read closely enough.
>
> `method-run-lineage.schema.yaml` already requires `completed_at`, `input_hash`,
> `implementation_revision`, `configuration_version`, `configuration_hash` and `output_hash` on
> **every** completed run, and `input_references` (non-empty) on every run at all. There were no
> optional fields left to divide, so a split by field content would have obliged nothing from
> either control — precisely the collapse it was designed to prevent.
>
> `DR-27` separates them by **reference direction** instead: `run_lineage` obliges the run to
> resolve to the method that ran it, `provenance` to every override that adjusted the result. The
> correction was made before any code was written.

### Alternatives rejected

- **Require at least one record.** Rejected above; it is the fabrication incentive.
- **Infer the record type from its contents rather than from which register it sits in.** Each
  schema has a distinct discriminator, so this is buildable. Rejected because it removes the most
  useful failure this check produces — a valid override record filed in the run-lineage register is
  a real defect, and content-sniffing would silently accept it as an override.
- **A single register for all four controls.** Simpler for an adopter to set up, and it makes the
  misfiling case above undetectable by construction.
- **Recursing into subdirectories.** Deferred, not rejected. A register that grows will want
  `2026/`, and nothing here prevents adding it later. Doing it now, before any adopter has one, is
  complexity ahead of evidence.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** none. All three record schemas are consumed exactly as published, which was
  `DR-25`'s stated reason for choosing them over a speculative new one.
- **Security/data:** the checker reads and parses files an adopter names. Content is validated for
  shape and never interpreted as instruction.
- **Operations/release:** what `full` costs an adopter changes materially, as `DR-25` predicted.
  Before, four lines of YAML. Now, four directories that must exist, be tracked, and contain nothing
  malformed. That is the intent.
- **The golden example was the first thing this caught.** `examples/application-profile.full.example.yaml`
  declares all four controls and named no register, so it failed the moment the check existed. It
  now names three registers, and the harness seeds them — one holding a real override record, the
  others empty — so the worked example exercises both forms of the pass.

## Evidence

Ten probes, run before any permanent test was written. **The four negative controls are the half
that carries the evidence**: a check that rejected everything would pass the six positive cases
identically.

| Probe | Result |
|---|---|
| Control required, no `implementation_reference` | `SP055` |
| Names a path that does not exist | `SP055` |
| Names a file rather than a directory | `SP055` |
| Register holds an untracked record | `SP055` |
| Record missing a required field | `SP056` |
| Record that will not parse | `SP056` |
| **Register empty** | **passes**, and says what that does and does not establish |
| **`README.md` beside a valid record** | **passes** — non-YAML ignored |
| **Register holds a valid record** | **passes**, reporting the count |
| **Valid *override* record filed in the run-lineage register** | `SP056` |

`test_install_and_check.py` moves 128 → 138. The untracked case runs against a real git repository
rather than the lightweight fixture, because that fixture has only a fake `.git` directory and
`git_available()` is false there — the check would have been dead code asserted to work.

## Limitations and follow-up

- **Surfaceplate does not use this pattern on itself.** It sits at `standard` and has no material
  results, no governed methods and no overrides, so it declares none of the four. This is the first
  control in the framework proven **only by fixture**. `DR-25` recorded that a publisher failing its
  own controls would be evidence against the design; this is not that — the controls do not apply
  here — but it is a genuinely weaker position than patterns A, B and D, each of which surfaceplate
  satisfies live, and it should not be described as equivalent.
- **The declared-not-checked banner is now latent code.** With every control verified, it cannot
  fire for any level, and the test that manufactured an unverified level was **deleted rather than
  relocated** — there is no level left for it to be true of. The banner is kept for the next control
  added ahead of its validator, and nothing now proves it still works. Restoring an assertion would
  mean inventing a fake level, which tests the fixture rather than the framework.
- **Completeness is unreachable.** Nothing detects a run that happened and was never recorded. An
  adopter who files nothing passes forever.
- **Validity is not truth**, and no later packet changes this. A lineage record can carry an input
  hash computed over nothing.
- **`F23` was found while building this** and is open: the guard keeping the checker's gate
  catalogue in step with the standard matched on line shape rather than on the catalogue, and
  silently absorbed this packet's new dictionary. It failed on the count, which is the only reason
  it was noticed; a one-entry dictionary paired with one removed gate passes at 19 while iterating
  the wrong set. Constructed and run, not reasoned about. Fixed here by anchoring to the block, and
  recorded because the shape recurs.
- **No recursion into subdirectories**, deferred above.
- **Cross-references are `C2`'s work and are not checked here.** A run may name a method that was
  never registered, and it validates. Closed by `DR-27`.
