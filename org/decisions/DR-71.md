## Decision

**`DR-69` said the profile's flat control list would be replaced by per-topic decisions. It is
not, and this record amends that surface.** Three parts:

1. **The keys stay flat and canonical.** `control_decisions` remains a map of control id → decision,
   exactly as adopters have it. `schema_version` stays `"1.0"`. No profile migrates.
2. **The profile is *laid out* by topic.** `rules.py` gains `CONTROL_TOPICS` and `TOPIC_NAMES` —
   framework knowledge, shared by the checker and the wizard as `DR-48` requires — and `render.py`
   writes `control_decisions` grouped under generated topic headings, in topic order. An adopter
   opens the file and reads twelve named subjects.
3. **`WI-2`: `adopter_canon`**, an optional top-level array of `{artefact, rationale}`, modelled on
   `placeholder_scan_exemptions`. Declaring an artefact means: *where this artefact and this
   standard disagree, this artefact governs in this repository*. `SP060` checks the artefact exists
   and is tracked, so the declaration is verified rather than decorative.

## Context and alternatives

**Rejected: nesting controls under topics, as `DR-69` specified.** A control's topic is decided by
the framework, not by the adopter. Nested, every adopter's file would restate a fact the framework
already owns — where it can only be redundant or wrong. If the checker rejects a mismatched
placement, the adopter's placement carries no information; if it accepts one, the framework's own
taxonomy stops being authoritative. Neither is acceptable.

That is **`F121`'s defect one level up**, in `activity.md`'s own words as corrected in Topic 4 the
same day: *"a constant column carries no information."* This framework had just finished removing
that shape from its own activity register; reintroducing it in the published profile contract, in
the same session, would have been the clearer error of the two.

**What the rejected option was actually for, and how this keeps it.** The goal was never nesting —
it was that an adopter who answered twelve topic-shaped questions should open the file and see the
same twelve topics. Layout delivers that completely. Storage was never the part the reader
experiences.

**Rejected: doing nothing on this surface.** `DR-69`'s surface 2 exists because a flat list of
twelve controls and nineteen gates, in two unrelated blocks, is not intelligible to a stranger —
which is the standing non-negotiable. Leaving it unbuilt would leave the topic axis visible in the
documents, the wizard, the levels and the finding codes, and absent from the one artefact the
adopter actually maintains.

**Gates keep their existing six-group catalogue order, and are not re-cut into twelve topics.**
Nineteen gates do not divide cleanly across twelve subjects — several assignments would be
genuinely arguable, and an arguable taxonomy asserted as fact is worse than a stable one that
does not claim to be the topic axis. More decisively: `DR-69` kept `core/PREREQUISITE_GATES.md`
whole *as a specification*, and the six groups are that document's own internal organisation.
Re-cutting them here would undo the decision `DR-69` took two surfaces earlier. Stated so a later
reader finds a reason rather than an inconsistency.

## Impact

- Contracts/schemas: one optional top-level key. Additive; every existing profile stays valid; no
  adopter re-pins. `schema_version` unchanged at `"1.0"`.
- Numerical/model output: none. Security/data: none.
- Finding codes: `SP060` added; the declared space in `org/FINDINGS.md` extends to `SP060` and
  `tests/check_code_registers.py` checks it, as it does every code.
- Operations: a re-rendered profile reorders `control_decisions` and gains topic headings. YAML
  mappings are unordered, so this is a text diff, not a semantic change.

## Evidence

Recorded when this record was written; the implementing evidence is `ACT-069`'s own commit.
`CONTROL_TOPICS` maps all twelve controls with no control unassigned and none assigned twice —
four fall in Topic 10 (provenance, run lineage, method registry, overrides), which is one subject
and reads as such. Topics 2, 4, 5, 11 and 12 carry no control at all, and that is informative
rather than a gap: those topics are governed by rules and gates rather than by declared controls.

## Limitations and follow-up

**The layout is presentation, and presentation can drift from the map behind it.** Nothing
currently fails if `render.py` groups by a topic a control no longer belongs to, because the
grouping is generated from the same constant the checker reads — the two cannot disagree today
precisely because there is only one source. That property holds only while `CONTROL_TOPICS` stays
the single source; a second copy anywhere would be the drift `DR-48` exists to prevent.

**This repository's own profile does not exhibit the layout, and that is left as it is.** The
topic grouping is produced by `render.py`, which writes what `adopt` produces. This repository's
profile predates the wizard, is maintained by hand, and carries per-control commentary a rendered
profile cannot — histories, finding citations, the reasoning for each decision — which re-rendering
would destroy. It also already carries a different and equally real grouping: `# standard floor`
against `# Above the floor, because it is already met`, which says something topic order does not.

Annotating it a third way was considered and rejected: it would create a third shape for the same
data, on a property nothing checks and no adopter reads. So the publisher's profile shows the
topics' *content* without their *layout*, and this is the honest statement of that rather than a
claim that every profile looks the same. Nothing about conformance turns on it — the layout is
presentation, not contract.

**`adopter_canon` is checked for existence and tracking, and for nothing else.** Whether the named
artefact actually says anything about precedence, and whether the adopter honours it, is outside
what any check here can establish — the same honest ceiling `SP046`/`SP047` state about secret
scanning. Recorded so the declaration is not read as stronger than it is.
