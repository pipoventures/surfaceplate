# Decision Record

- Decision ID: DR-72
- Date: 2026-09-08
- Application: Surfaceplate (the framework itself) — what the conformance workflow installed into
  every adopting repository does, and whether it reaches the network.
- Decision owner: Mario Pipo (maintainer), taken this session in answer to `H20`, which was put with
  three costed options; the maintainer chose **(b)**, *"on by default, with an opt-out key in the
  profile"*. Drafted by the agent under `ACT-075`; confirmed by merging.
- Status: accepted — implemented by `ACT-075`.
- Risk level: 3 — it adds an outbound network request to CI in every repository that adopts this
  standard, present or future, and those repositories cannot edit the workflow that makes it.
- Related work item: `ACT-075`; completes `DR-68`; **closes `F124`** and `H20`.

## Decision

**The installed conformance workflow reports whether the standard installed in a repository is the
published one. On by default. Declinable, on the record, in the adopter's own profile.**

1. **`check_conformance.py --currency`** makes one request, to `https://pypi.org/pypi/surfaceplate/json`,
   compares the published version against `INSTALL.json`'s `standard_version`, and reports
   *current*, *ahead*, *behind*, or *unknown*.
2. **It is an advisory and can never be a finding.** Not blocking, and not graceable either — a
   graceable finding fails once the grace window ends, and a check that eventually failed on this
   would be telling adopters that pinning a version deliberately is a defect. It reports; the human
   decides.
3. **The flag is off by default and only the installed workflow passes it.** A local
   `surfaceplate check` and the pre-commit hook open no socket, exactly as before.
4. **`adoption.currency_check: {enabled: false, rationale: …}`** suppresses the request entirely.
   Absent means enabled, so every profile written before this key existed behaves as intended and
   `schema_version` stays `"1.0"`.
5. **The comparison moves to `rules.py`**, which `doctor --online` now imports rather than holding
   its own copy.

## Context and alternatives

`F124` is the highest-severity finding this framework has raised against itself: *"a repository can
sit an arbitrary number of versions behind, indefinitely, while its conformance check passes and
says nothing."* `DR-68` built the mechanism and stopped, because the remaining step was not an
agent's to take — it changes what runs in other people's infrastructure. That is why `H20` existed
and why this record is dated four days after the mechanism was finished.

**Why the opt-out had to be in the profile.** The installed workflow is integrity-checked. An
adopter who did not want the call could not delete the step without failing their own conformance
check, so "on by default" would have meant "compulsory" — which is what made option (a) the
intrusive one. The profile is the one file in the installed set that is theirs to edit, so that is
where the switch belongs. This is the same shape as `--no-hooks` and `--agents` (`DR-66`, `DR-67`):
the standard's default is opinionated, the declining is declared rather than silent, and the check
reports the declination on every run.

**Rejected: leaving it manual (option (c)).** Honest, costs nothing, and closes nothing. `F124`
would reach 1.0 open, and the stranger this whole programme is for — the adopter with no tacit
knowledge of this project — would have no way to learn their install is a year stale, because the
one command that would tell them is one they have never heard of.

**Rejected: making it a finding, graceable or otherwise.** It would eventually fail a build over a
deliberate version pin. `doctor`'s own docstring settled this before the question reached the
checker, and that reasoning is imported here rather than re-argued.

**Rejected: a separate workflow, or a separate step with `continue-on-error`.** Both put the result
somewhere a reader has to go and look, and `continue-on-error` produces a step that is green
whatever happened — the false green this repository exists to find. As an advisory line inside the
report the reader already reads, it is seen by whoever reads the check, and by nobody who does not.

**The rationale is required in both directions.** Declaring the call on deliberately is as much a
decision as declining it, and an unexplained boolean is the same omission-wearing-a-decision's-
clothes that `SP031` objects to in an undated deferral.

## Impact

- Every adopting repository's CI makes one HTTPS request to `pypi.org` per conformance run, unless
  its profile declines. Nothing else changes about what runs there.
- `surfaceplate/schemas/application-profile.schema.yaml` gains one optional object. Additive:
  `schema_version` stays `"1.0"` and no existing profile is invalid.
- `rules.py` gains the only outbound request in the payload. Importing it opens no socket; the
  checker imports it on every run, including from the hook, and must stay offline there.
- `doctor.py` loses its private `_version_key` and its own fetch. `DR-48`'s reason for `rules.py`
  existing now covers currency too: one implementation of *"is 0.9.0 newer than 0.17.0"*, a
  comparison with a known wrong answer when written naively.

## Evidence

- `tests/test_install_and_check.py::test_currency_is_reported_where_integrity_cannot_be`, extended
  to 17 checks. The by-effect ones: an unroutable proxy (`https_proxy=http://127.0.0.1:1`) makes any
  real request fail immediately, which is what distinguishes **made no request** from **made one and
  it failed** — two states a test asserting only the absence of a network cannot tell apart. With
  the profile declining, the unreachable-index wording never appears; without it, `currency: UNKNOWN`
  does.
- The verdict is compared against the **same repository checked without `--currency`**, not against
  a literal `PASS`. The fixture sits inside its grace window and reports `WARN` for unrelated
  reasons; what must hold is that asking the currency question cannot change the answer, and that
  is what is asserted.
- Run against this repository, live: `currency: installed 0.17.0 is AHEAD of the published 0.16.1`.
  The publisher's own tree is always ahead by construction, and reporting that as "upgrade" would
  be advice that is simply wrong.

## Limitations and follow-up

**An adopter behind a proxy that intercepts TLS, or on an air-gapped runner, gets `UNKNOWN` on every
run.** That is the correct answer — an unanswered question is not a passing one — but it is noise
for a repository that will never reach the index, which is why declining is a supported declaration
rather than something to be endured.

**Nothing verifies that the published version is genuine.** The request reads `pypi.org`'s JSON over
HTTPS and trusts it. A compromised index could under-report the latest version and the advisory
would go quiet; it could over-report and the advisory would tell adopters to upgrade to something
that does not exist. The consequence is bounded — this can never fail a build and never installs
anything — but it is stated rather than left to be discovered.

**The `pypi.org` name is hard-coded and this standard is published there.** A fork publishing
elsewhere would report its own installs as behind. Making the index configurable is deferred: no
fork exists, and a configurable trust anchor is a larger question than a URL.

## Approval

Taken by the maintainer in answer to `H20`, option (b), on the costing recorded there. No agent
approved this, and the risk level is stated as 3 because the change reaches infrastructure the
maintainer does not own.
