## Decision

No further implementation work proceeds in this repository until surfaceplate's own operating model
and controls are enforced against it. This is `DR-12`'s architecture; this record is what gates
building on it.

**Self-conformance, not self-installation — a distinction that must be stated precisely, because
the two are easy to conflate and the code itself invites it.** `scripts/install_standard.py:424-426`
refuses to run when its target and source paths are identical:

```python
if target == source:
    print("error: refusing to install the standard into itself", file=sys.stderr)
    return 2
```

This guard carries **no stated reasoning anywhere in the code** — verified by reading the complete
inventory of comments and docstrings in the file; the module's own four design rules
(`install_standard.py:2-23`) do not mention it, and there is no test for it in
`tests/test_install_and_check.py`. It is a bare mechanical guard, and this record does not assert
what it is "for" beyond what is written. The one characterisation that exists anywhere is `DR-10`'s,
which reads it as guarding against a clone-onto-itself accident — but that reading should not be
overstated either: ordinary path collisions at standard-owned locations already have their own
dedicated, well-documented mechanism (`detect_collisions`, `install_standard.py:110-118`, with a
stated rationale about not silently overwriting hand-written guidance), which makes it less certain
the path-equality guard exists for collision-avoidance specifically rather than as an unexplained
defensive check. What can be said with confidence: it is not, and cannot be read as, a statement
that the standard may not be conformant to itself. Treating it as a self-certification prohibition
would be an invented rationale, and would contradict this repository's own existing admissions that
non-self-conformance is a gap, not a boundary — `README.md:154-156`: *"This repository does not
install its own standard on itself... It is not, at present, conformant to what it publishes."* —
and `DR-7.md:129-132`, recording the same fact at `v0.13.0`.

**The checker carries no such guard at all — but its own prescribed remedy is exactly what the
installer's guard refuses, and that tension is real, not resolved here.** `scripts/check_conformance.py`
has no identity check of any kind — confirmed by reading its complete argument-handling and error
paths. Run today, directly, against this repository:

```
$ python3 scripts/check_conformance.py --repo .
Blocking findings (1) - never graced:
  [SP001] Surfaceplate is not installed
        what: .standards/INSTALL.json is missing.
        fix : Run install_standard.py from the surfaceplate repository.

FAIL - the conformance check found findings that cannot be graced.
exit=1
```

Read `SP001`'s own remediation text closely: *"Run install_standard.py from the surfaceplate
repository."* That is precisely the command the `target == source` guard refuses when run against
this repository itself. So self-conformance does not require defeating the installer's guard — it
requires this repository to independently carry the artefacts an adopter would carry, by some means
other than running the installer against itself, and then running the checker, which already works,
against them. **How those artefacts actually get produced — hand-authored, installed into a
separate working copy and merged back, or some other route — is exactly the kind of implementation
mechanism this decision record does not choose.** It is named here as a real mechanical question the
bootstrap must answer, not glossed over as already solved because the checker happens to run.

**What self-conformance comprises**, named against this repository's own instruction files rather
than paraphrased:

- an **application profile** — `governance/application-profile.yaml`, conforming to
  `schemas/application-profile.schema.yaml`;
- an **activity register** — `standard/.github/instructions/activity.instructions.md:16` names it
  "the repository's activity or development register"; `:25-27` requires one before `standard` or
  `full` conformance, and permits a single Markdown file at `essential`;
- the **conformance block** — the marked region in `.github/copilot-instructions.md`, digest-checked
  as `DR-11` now generalises;
- declared **prerequisite gates** — per the catalogue in `core/PREREQUISITE_GATES.md`, each
  `required`, `deferred`, or `not_applicable` with a reason;
- the **checker running in this repository's own CI** — `.github/workflows/standard-self-check.yml`
  today runs `validate_contracts.py`, `test_install_and_check.py`,
  `build_release.py --verify-manifest`, and `check_identifiers.py`. It does not run
  `check_conformance.py --repo .` against this repository. See "The open question" below.

**The bootstrap.** Establishing self-conformance is itself implementation work, and cannot be
governed by controls that do not yet exist — the same reason a scaffold is not held to the standard
of the building. It is therefore declared **the last ungoverned work in this repository.**

This is not a new exemption this record invents. By `activity.instructions.md:74-78`'s own rule —
*"Every implementation, test, and documentation change must be attributable to an activity ID...
Never invent an activity ID"* — **every packet of work delivered in this repository to date,
including this one, has already been unregistered work**, exactly as `DR-7.md:129-132` already
recorded at `v0.13.0`. This record acknowledges a state that already exists and names when it ends,
rather than opening a new one.

**Prerequisite gates take `effective_from` as the date self-conformance lands; history before that
date is out of scope.** `core/PREREQUISITE_GATES.md:91-92` states the mechanism this rests on
directly: *"A gate binds from a date. History before that date is out of scope. Without this,
adopting a gate would require rewriting the past, and no real repository would ever adopt one."*
Two properties of that date, both already enforced elsewhere in this codebase and therefore binding
here without further decision: it can never move forward once declared (`SP034`, never graced,
`core/PREREQUISITE_GATES.md:94-99`, `:275`) — so choosing the landing date is a one-way commitment
to *at most* that much retroactive scope, never less; it may move backward freely
(`:101-102`), which only increases the scrutiny this repository's own history invites.

**Accepted costs, stated plainly.** Implementation is delayed until this bootstrap completes. The
first real exercise of the gates this framework defines lands on the repository that defines them —
where a defect in a gate can block the very fix that would repair it. Both are accepted, not
minimised.

## The open question this decision forces, and does not answer

**Does this repository's CI fail on its own non-conformance?** Recorded as open. Not decided here.

This is not a hypothetical question. CI today does not attempt to answer it —
`check_conformance.py --repo .` is not one of the four steps
`.github/workflows/standard-self-check.yml` currently runs — and GitHub Actions demonstrably does
run on this repository (confirmed 2026-08-30, workflow run `33327048783`; `README.md:84-91`,
`org/ROLLOUT_RUNBOOK.md:18-21`). The moment this bootstrap lands, the question stops being
hypothetical, because the infrastructure to answer it either way already runs.

The tension, named without resolving it: wiring the check into CI in the same change that first
achieves self-conformance means that change must produce a passing check from the moment it lands —
artefacts and CI wiring committed atomically, a larger single change with no partial-credit state.
Wiring it in later, after the artefacts already exist, leaves a window in which this repository can
be described as "self-conformant" while nothing yet verifies that claim in the one place — CI — this
framework itself treats as durable detection. That undercuts the point of the bootstrap in a
different way. Neither option is decided here.

## Context and alternatives

**Rejected: implement first, register the gates retroactively once implementation is complete.**
This is precisely the shape `core/PREREQUISITE_GATES.md:13-18` explains a gate is designed to
defeat — "a decision record written after the fact... describing a choice that was actually made
three months earlier by accident." Applying that reasoning to this repository and not just to
adopters would be exempting the framework from the one property (order of events, not just artefact
existence) its own gates exist to guarantee.

**Rejected: defer self-conformance indefinitely, citing the bootstrap problem as permanent rather
than temporary.** The bootstrap problem is real — see "The bootstrap" above — but it is a reason to
sequence the work as the *last* ungoverned work, not a reason it never happens. Every other decision
record in this directory that is "decided, not implemented" (`DR-1` through `DR-5`, `DR-10`,
`DR-11`, `DR-12`) names a future point at which it becomes implemented; treating self-conformance as
permanently deferred would make this framework's own governing document the one thing it never
applies its own rules to.
