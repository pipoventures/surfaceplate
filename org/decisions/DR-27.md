## Decision

**Records must reference what they describe, and `provenance` and `run_lineage` are separated by
which reference each obliges.**

| Control | Reference it obliges | Live when |
|---|---|---|
| `run_lineage` | a run's `method_id` **and `method_version`** resolve to a method-registry entry | `method_registry` declared and fully readable |
| `provenance` | every id in a run's `overrides` resolves to an override record | `overrides` declared and fully readable |
| `overrides` | an override's `method_run_id` resolves to a run's `run_id` | either run register declared and fully readable |
| all four | no two records in one register claim one identity; no record carries another application's `application_id` | always |

`SP057` covers an unresolved reference; `SP058` covers register integrity. Both graceable.

**And the redundant `allOf` branch is removed from `method-run-lineage.schema.yaml`.**

## Context and alternatives

### The gap

A JSON Schema sees **one record at a time**. So a run-lineage record naming a method that was never
registered validates perfectly, and so does an override naming a run that never happened. `C1`
(`DR-26`) checks every record against its schema and therefore cannot see either.

`DR-25` had this in pattern C's definition from the start — *"reference what they describe"* — and
`C1` split it out rather than dropping it.

### The separation, and the answer that had to be corrected first

`DR-26` predicted that `C2` would separate the two controls **by which optional fields each
obliges**: `provenance` the traceability pair, `run_lineage` the reproducibility set.

**That was wrong on a matter of fact.** `method-run-lineage.schema.yaml` already requires
`completed_at`, `input_hash`, `implementation_revision`, `configuration_version`,
`configuration_hash` and `output_hash` on every completed run, and `input_references` — non-empty —
on every run at all. There were no optional fields left to divide. Both controls would have obliged
nothing, which is the collapse the split existed to prevent.

The correction was made before any code was written, and `DR-26` is amended in place rather than
left standing under it. The separation runs on **direction** instead: a run points *forward* to the
method that produced it and *sideways* to the overrides that adjusted it, and those are exactly the
two properties the controls name.

### Why the checks are conditional, and why silence would not do

A reference is checked only when the register it points into is **declared here**. Obliging
otherwise would mean declaring `run_lineage` silently required adopting `method_registry` — the tool
deciding an adopter's scope, which is the line this framework draws in every direction.

But a conditional check that falls silent is indistinguishable from a check that passed. So when a
target register is undeclared, **the run says so**. A green line that quietly skipped half its work
is the defect this project has recorded more often than any other.

### A defect the probe caught, in the design rather than the code

This record originally specified that records failing `SP056` are excluded from the reference index,
*"so one malformed record does not cascade into a spray of `SP057`s"*.

**Excluding them is what causes the cascade.** When the malformed record is the reference *target* —
a broken method-registry entry that a valid run names — omitting it from the index makes the run's
reference unresolvable, and `SP057` fires about a reference that was perfectly correct.

The remedy is not to omit a row but to know the register is **incomplete**. A reference into a
register that could not be fully read cannot be judged at all: an unresolved reference and a
reference to the broken record produce the same absence. So those edges are reported as *unchecked*,
never as *unresolved*.

This was found by the probe written to demonstrate the property, not by review, and it is the same
shape as `F23` and `F14`: an instrument whose negative result does not establish what it appears to.

### `affected_method` is deliberately not checked

An override's `affected_method` is `{type: string, minLength: 1}`. The published contract permits
prose; the worked example happens to use an identifier. Enforcing it as a reference would be the
checker **narrowing a published contract by inference**, and every adopter who wrote a sentence
there would fail for conforming to what the schema actually says. A candidate if the schema is ever
constrained; not a decision to take silently inside a validator.

### The redundant schema branch: removed, on evidence rather than taste

`method-run-lineage.schema.yaml` carried a third `allOf` branch requiring `input_hash`,
`implementation_revision`, `configuration_hash` and `output_hash` of completed runs at medium or
high materiality. Its condition and its consequent are both **subsets** of the first branch's, so it
could never add an obligation. `F24`.

Inert is not harmless here. As a *contract*, it tells a reader that a low-materiality completed run
escapes fields it does not escape.

Git history could not settle whether it was a leftover or a live intent: the public repository is a
single squashed commit (`DR-23`) and `CHANGELOG.md` had never mentioned materiality. The design
evidence settled it, and it is one line:

> `schemas/override-record.schema.yaml:45-48` is the **only** live use of `materiality` in any
> schema, and it grades **approval** — a material override requires approval. It does not relax
> record completeness: `evidence_reference`, `rollback_approach` and `calculation_impact` are
> required of every override at every materiality.

Where this framework actually expresses the principle, **materiality decides who must sign off, not
how complete a record must be.** The run-lineage branch graded the wrong axis, so it is removed
rather than made real.

**Making it real was considered and rejected.** Narrowing the first branch — so low-materiality
completed runs need fewer fields — would loosen a published contract against the one place the
principle is expressed, and would grade record completeness by a **self-declared** field, creating
an incentive to classify everything `low`.

Removal changes no instance's validity, so it is **not breaking** and the `$id` version segment
stays at `0.7.0`, as `NAMESPACE.md` requires.

### Two worked examples that had to exist

`examples/override-record.approved.example.yaml` has always named `RUN-2026-000412` and
`METHOD-SEASONALITY-001`. Both were **dangling**: the example set was designed as a coherent whole
and only one third of it was ever written, and nothing noticed because nothing read across records.

`method-run-lineage.example.yaml` and `method-registry-entry.example.yaml` are added, consistent with
the override, and `tests/validate_contracts.py` asserts the four links between them. This is
required by the change rather than scope added to it — the golden `full` example fails until they
exist — and it gives adopters the first worked instance of either type.

### Alternatives rejected

- **Check references across every declared register unconditionally.** Rejected: see the
  conditionality above.
- **Resolve `input_references` and `human_decisions` too.** They are free strings that name datasets,
  decisions and artefacts in whatever scheme the adopter uses. Resolving them requires knowing the
  stack, which `DR-12` forbids.
- **Treat a duplicated identity as a warning.** Rejected: two records under one identity make every
  reference to it resolve to whichever was read last, so the reference checks become meaningless
  rather than merely wrong.

## Impact

- **Numerical/model output:** none.
- **Contracts/schemas:** one schema edit, behaviour-preserving and non-breaking. No `$id` moves.
- **Security/data:** unchanged from `DR-26`. Record content is validated for shape and cross-checked
  for identity; it is never interpreted as instruction.
- **Operations/release:** at `full`, registers must now be mutually consistent, not merely
  individually valid. An adopter who files a run without registering its method now fails.
- **Surfaceplate still declares none of these controls**, for the reasons `DR-26` gives. The
  no-live-self-demonstration limitation carries forward unchanged and is not restated as new.

## Evidence

Nine probes. **The last three are the negative controls** — a check that rejected every reference
would pass the first six identically.

| Probe | Result |
|---|---|
| Run names a method that is not registered at all | `SP057` |
| Run names a registered method at an **unregistered version** | `SP057` |
| Run names an override nobody recorded | `SP057` |
| Override names a run that never happened | `SP057` |
| Two records in one register share an identity | `SP058` |
| Record carries another application's `application_id` | `SP058` |
| **The three worked records together** | **pass**, reporting 3 references resolved |
| **Same dangling reference, target register undeclared** | **passes**, and the run says it was not checked |
| **Target register holds a schema-invalid record** | `SP056` **without** an `SP057` cascade |

The version half of the method reference is asserted separately: matching on `method_id` alone would
have passed probe 2 and looked identical on every other row.

`test_install_and_check.py` moves 138 → 149; `validate_contracts.py` 144 → 152.

## Limitations and follow-up

- **Existence is not correctness.** A reference resolving means the named record is there. It does
  not mean it is the right one, or that it is honest. A run can resolve to a registered method and
  still be a record of something else.
- **Completeness remains unreachable**, unchanged from `DR-26`. Nothing detects a run that happened
  and was never recorded, and an adopter who files nothing still passes.
- **`affected_method` is unchecked**, deliberately, above.
- **The `application_id` check trusts the profile.** It confirms records agree with what this
  repository calls itself; it cannot confirm that name is right.
- **No cycle or orphan detection.** An override that no run references, and a registry entry no run
  uses, both pass. Orphans are normal — a method may be registered before first use — and
  distinguishing a legitimate orphan from an omission is a judgement, not a record.
