## Decision

Where an adopter has a GitHub organisation, **the recommended enforcement posture is an
organisation-level reusable workflow, called by a ruleset the adopting repository cannot edit.**
Recommended, not required.

Surfaceplate publishes the template and documents the posture. It does not host it, run it, or
operate anything — the reusable workflow lives in the *adopter's* organisation and is the adopter's
infrastructure.

This addresses finding `F8` (`org/FINDINGS.md`): the conformance workflow is vendored into the
adopting repository, so the checked party controls the checker, and the check that would report
tampering with that workflow is invoked by the workflow itself.

**Not required, deliberately.** Requiring it would make the framework unusable for any adopter
without a GitHub organisation, and for any adopter not on GitHub at all, and would do so for a
control that is proportionate only above a certain materiality. `core/CONTROL_PRINCIPLES.md:14`
(principle 12) requires the opposite: *"defer controls that do not reduce a demonstrated risk."*

## Context and alternatives

### The problem, stated precisely

`install_standard.py:74` vendors `.github/workflows/standards-conformance.yml` into the adopter's
repository, and `:32-33` of that workflow is what runs `check_conformance.py` in CI. The workflow
file is itself one of the digest-protected `files` entries, so modifying it is detectable —
**by a check the modification can disable.** `org/ROLLOUT_RUNBOOK.md:51-64` already names this in
general terms: at rung 2 *"a repository admin can delete it, and the check stops running."*

An organisation-level reusable workflow closes the loop because the org owns it: a repository admin
cannot edit what is not in their repository, and a ruleset can require the resulting status check.
That is rung 3 of the existing ladder (`org/ROLLOUT_RUNBOOK.md:39`), which this record is
recommending rather than inventing.

### What this assumes that DR-12 does not state

`DR-12` commits to enforcement *"via the adopter's own GitHub primitives — required status checks on
their organisation ruleset, their CI, their infrastructure, their support burden."* It does not state
the prerequisites that phrase carries. This record states them:

- the adopter has a GitHub **organisation**, not a personal account;
- someone at that organisation holds owner or admin rights sufficient to define a reusable workflow
  and apply a ruleset;
- their plan makes rulesets available at all.

**That last one is not hypothetical, and this repository is the evidence.** Branch protection and
rulesets both return `403 — "Upgrade to GitHub Pro or make this repository public"` here, verified
directly against the API. The publisher of this framework cannot presently apply the posture it is
recommending. Stating that is more useful than recommending a control while quietly failing to meet
its precondition.

### Does it survive DR-12's permanent no-infrastructure boundary?

**Yes, and the reasoning has to be explicit rather than assumed, because it looks like a violation at
first glance.**

`DR-12` permanently forecloses *"hosting, servers, user accounts, authentication, or database.
Ever."* A reusable workflow is none of those **for surfaceplate**, because surfaceplate does not host
it. The adopter creates it in their own organisation, from a published template, and runs it on their
own Actions minutes under their own administration. It is their infrastructure, their availability
problem, and their support burden — exactly as `DR-12` already says.

The precedent already exists in-tree: `org/ruleset-standards-conformance.json` is a ruleset template
this repository publishes for an organisation owner to apply, and has never applied for anyone.
`org/ROLLOUT_RUNBOOK.md:6-8` states the same division: *"Every step below requires GitHub
organisation-owner permissions. Whoever prepared this repository may not hold them."*

If surfaceplate ever hosted, ran, or administered such a workflow on an adopter's behalf, that would
cross the boundary. This record does not propose that and forecloses it.

### What remains true for an adopter with no organisation, or not on GitHub

They keep the local pre-commit hook, the history audit, and manual checker runs — rungs 1 and 2 of
`org/ROLLOUT_RUNBOOK.md`'s ladder. That is a real control and this record does not disparage it.

**But it is strictly weaker for the class of tampering `F8` describes, and saying otherwise would be
the overclaim this framework exists to avoid:**

- The local hook **is** an independent detector: `standard/.githooks/pre-commit:9-26` invokes the
  checker directly and reads nothing from `.github/workflows/`. A staged edit to the vendored
  workflow is caught as a modified `files` entry (`SP040`, `check_conformance.py:883-894`) and as
  `SP005` on the working tree — both non-graceable, both blocking.
- **But its activation is per-clone local Git configuration** (`install_standard.py:210`), which is
  neither cloned nor pushed; `INSTALL.md:66-68` requires re-running the installer in every later
  clone. Hook-inactive is therefore the default state of any clone but the installer's.
- **And the history audit does not cover this class.** `audit_gate_history`
  (`check_conformance.py:1264-1280`) is scoped to a gate's declared `gated_activity.paths` with a
  precondition-artefact test. It has no relationship to `record["files"]`, and there is no
  history-based integrity audit anywhere in the checker. `README.md`'s claim that *"the history
  audit remains the durable detector after a bypass"* is true for prerequisite gates and does not
  extend here — recorded as part of `F8`.

So for an adopter without an organisation: one independent detector, default-inactive, and no
history-based fallback for file integrity. That is the honest position, and it is the reason this
posture is recommended rather than dismissed as unnecessary.

### Rejected alternatives

**Rejected: require an organisation-level reusable workflow for conformance.** It would exclude every
adopter without a GitHub organisation and every adopter not on GitHub, converting a proportionate
control into an eligibility test. `core/CONFORMANCE_LEVELS.md:9-12` warns precisely against this
shape: a control surface that does not scale down produces *"small teams reject the framework as
disproportionate, or they claim adoption while implementing very little of it. Both are worse than
an honest tier."* It would also make the framework's own publisher non-conformant, since rulesets
are unavailable here.

**Rejected: change nothing, and leave the vendored workflow as the whole server-side story.** This
leaves `F8` with no stated remedy at all, and leaves `org/ROLLOUT_RUNBOOK.md:51-64`'s own analysis —
that rung 2 is bypassable by a repository admin — as a diagnosis with no prescription. A finding
this repository has already reasoned about deserves a recorded answer even when the answer is
conditional.

**Rejected: a surfaceplate-operated GitHub App.** Already permanently rejected by `DR-12`, which
considered it as *"the more plausible middle ground short of full hosting"* and declined it because
an installed app *"still requires operating always-on infrastructure … that inherits the same
unstaffed, unreviewed operational-duty problem"*. Cited rather than re-litigated.

**Rejected: make the local hook mandatory instead, and treat CI as optional.** This inverts the
problem rather than solving it. The hook cannot be made mandatory by anything in the repository —
`core.hooksPath` is local configuration by design, which is the whole reason `F8`'s mitigation is
default-off. A control whose activation cannot be verified remotely is not a substitute for one that
runs server-side.

## Limitations and follow-up

- **Decided, not implemented.** No reusable-workflow template exists. `org/ROLLOUT_RUNBOOK.md` is
  not amended. Nothing about the vendored workflow changes.
- **Untested, like the ruleset it accompanies.** `org/ROLLOUT_RUNBOOK.md:149` already records that
  the organisation ruleset *"has never been applied. It is untested configuration."* A reusable
  workflow recommended but never exercised is in the same state, and should not be described
  otherwise until someone has run it.
- **The publisher cannot currently demonstrate this posture**, because rulesets are unavailable on
  this repository's plan. Recommending a control one cannot exercise oneself is a real weakness of
  this record, stated rather than omitted.
- **`F8` is not closed by this record.** It is addressed for a subset of adopters, conditionally, and
  by a mechanism that does not yet exist. The finding stays open.
- Whether an equivalent posture exists for adopters on other hosts — or off GitHub entirely — is not
  investigated here. `DR-12`'s "git only" boundary bounds what is possible; it does not answer what
  is available on GitLab or elsewhere.
