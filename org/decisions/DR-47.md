## Decision

**What "asked" means, and a provenance record beside the profile.**

1. A value is *asked* when it is presented to the human with its origin and the human can
   change it before the profile is written. A form field is one way to present it; the annotated
   review of the whole profile is another. The rule's sentence — *it asks, the human answers,
   the tool writes* — is unchanged; this record fixes its reading after `DR-46`.
2. The tool may propose any value from the sources `surfaceplate/adopt/defaults.py` names —
   discovered, example, computed — plus two named here: a fact of record (a date, a version, a
   digest) and a scaffolded artefact (a file the tool itself creates and therefore knows). It
   must record the origin of every value it wrote in
   `governance/application-profile.provenance.yaml`, a machine-owned file beside the profile
   that carries, for every field, its origin, the framework version, and one document-level
   line recording when the review was approved.
3. The tool never records a proposed value as typed or accepted. It records typed values as
   typed, edits made on the review as typed with a timestamp, and approval at document level
   with a timestamp. Per-value "accepted" is not recorded, because scrolling past a line is not
   a recorded promotion.
4. The tool never supplies a scope decision, `not_applicable` included. A human presses a key
   per gate, or invokes an explicit bulk command; the provenance record writes the bulk command
   as one human act with its count.
5. `effective_from` is proposed as the adoption date and shown on the review, where changing
   it is one edit; it is recorded as computed unless the human changes it. This keeps `DR-46`'s
   substance — a narrower date is never chosen silently, because the value is shown and the
   human can only widen it — while removing the per-gate form field `DR-46` costed at
   +1/+4/+15.
6. The profile header states what the provenance record contains and no more. The sentence
   *"Every value below was typed by a human answering a question"* is withdrawn.
7. `tests/test_provenance.py` remains the enforcement, extended to the provenance record:
   every non-typed value carries an origin; no origin says typed for a value the human did not
   type; the document-level approval carries a timestamp.

## Context and alternatives

The adversarial review of 2026-09-02 found that the rule, implemented as one widget per field,
presented 32 to 96 fields, discarded its own proposals on the route the maintainer chose
(`F60`), and wrote a profile whose header claimed human authorship over the framework's example
prose and computed dates (`F62`). The maintainer's real first attempt carries that header above
seven gates filled with `asdf`. A prototype of the reading decided here produced, from eight
questions, a profile line-for-line identical to the one the wizard produced through 72 fields,
and it passed the wizard's own verification (report Part II §II.1).

Alternatives considered: keep `DR-46`'s per-field reading (rejected: measured cost above, and a
false header); drop the rule (rejected: the rule is what makes the profile worth reading);
record provenance as comments in the profile (rejected on the second reviewer's evidence:
`yaml.safe_load` drops comments, any round-trip drops them, and a comment is one keystroke from
gone).

## Impact

- Numerical/model output: none.
- Contracts/schemas: a new machine-owned file beside the profile; the profile schema is
  unchanged by this record (`DR-50` changes it separately). Existing profiles without a
  provenance record remain valid.
- Security/data: the provenance record holds paths and timestamps, no secrets; it must never
  hold a remote URL.
- Reproducibility/lineage: improved — every value's origin is recorded for the first time.
- Operations/release: the rule's wording in `org/RELEASE_PLAN.md` is amended by `ACT-044` in the
  same change that implements this.

## Evidence

- Code/configuration: none yet; the prototype under the review session's scratchpad is not
  repository code.
- Tests/checks: `tests/test_provenance.py`, extended by `ACT-044`.
- Runtime evidence: the prototype measurements in the report, Part II §II.1.
- Independent review: the second reviewer's report, summarised in Part II §II.6; it is what
  moved this record from comments-in-profile to a sidecar and removed per-value acceptance.

## Limitations and follow-up

use and happens after phase 0, before this is implemented; the second real use, after `ACT-044`,
is what tests this record.
