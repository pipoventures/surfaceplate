# Tests

Installed by Surfaceplate. Do not edit this file in an adopting repository.
Stack-specific commands belong in the repository's own `copilot-instructions.md`.

## Tests are evidence

A test exists to make a behaviour reviewable. Treat a failing test as information, not as an
obstacle.

**Never** weaken, delete, skip, disable, loosen an assertion, widen a tolerance, or rewrite a test
merely to obtain a passing result. If a test is genuinely wrong, say so explicitly, explain why,
and route it as a change with a reviewer — do not quietly adjust it inside an unrelated task.

## Golden and reference outputs

Golden, reference, snapshot, and reconciliation fixtures encode agreed behaviour.

An unexpected change in deterministic output is an **audit trigger**. Investigate the cause before
touching the fixture. Regenerating a golden file to absorb an unexplained delta destroys the only
evidence that something changed.

When a golden output legitimately changes, the change must carry: the cause, the output delta, the
affected methodology or contract authority, and a reviewer.

## Naming and organisation

Use a predictable, greppable convention so that a change can be routed to its tests
mechanically — for example `test_{area}_{description}`.

Declare the repository's test areas in its own `copilot-instructions.md` so that an agent can select
the focused subset for a given change rather than guessing.

## Which tests to run

Run the **cheapest focused check** for the slice you touched, immediately after each substantive
edit. Then widen.

Before handing work back, run:

1. focused tests for the changed area;
2. contract or schema conformance tests, where the repository has them;
3. deterministic replay, golden, or reference tests for any material output;
4. lint, format, type, and build checks appropriate to the stack;
5. dependency lock and vulnerability checks when dependencies changed.

For a change that affects material outputs or methodology, the guardrail subset must be green
before the change can be considered complete.

## Reporting

Report the exact command, quoted. Report the result as `PASS`, `FAIL - CODE`,
`FAIL - ENVIRONMENT/DEPENDENCY`, or `NOT RUN`.

Preserve warnings and skipped tests in the report. Distinguish a code failure from an
environment or dependency failure — they lead to different actions.

Do not claim a suite passed if you ran a subset. State exactly what you ran.

## New behaviour needs new tests

Any change to behaviour adds or updates a test. Where a defect is being fixed, add the failing
regression test **first** where practical, so the fix is demonstrably the thing that made it pass.

Where a behaviour genuinely cannot be tested, say so explicitly and record it as an evidence gap,
with the reason. Silence is not an acceptable substitute for coverage.
